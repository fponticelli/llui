# `@llui/compiler` invariants

_Detail behind the short rules in the root `CLAUDE.md` (Compiler invariants). Moved here verbatim so the always-loaded instructions stay small; read this before changing the area it covers._

**Note for future LLMs:** framework lint rules are compile-time ERRORS in `@llui/compiler` (run by `@llui/vite-plugin`), never ESLint rules. The signal lint set (`packages/compiler/src/signals/rules.ts`) covers `peek-in-slot`, `operator-on-signal`, `pure-derive-body`, `no-node-construction-in-body`, `empty-props`, `agent-annotation-syntax`, `tag-send-drift`, `imperative-dom-mutation`, plus the shared cross-file/agent/convention checks. Do NOT reintroduce `@llui/eslint-plugin` or recreate rules as ESLint rules: LLMs ignore lint warnings, so non-bypassable compiler errors are the only effective channel.

- **The dep analyzer may over-approximate but must NEVER miss a path.** A missed dependency → a mask that gates out a binding it actually reads → permanently stale UI. (Evaluate destructuring/param defaults, object-literal getters, etc.)
- **Signal recognition is by IMPORT PROVENANCE, not by identifier text, and `bindings` is a REQUIRED parameter so no caller can forget (#238).** `isSignalExpr` answers "is this expression a signal", and every value-position rule (`operator-on-signal`, `peek-in-slot`) plus the whole lowering path keys on it. Two of the shapes it must recognize are calls that produce a signal from nothing — `derived(inputs, fn)` and `constant(value)` — and the old test was `e.expression.text === 'derived'`, a BARE IDENTIFIER with no provenance. That one line was wrong in BOTH directions at once, which is the tell for this class: it reported a consumer's own `derived()` (a build-stopping error on code that did nothing wrong), and it did not know `constant()` at all (added later for the T1 stateless-widget tier), so `operator-on-signal` and `peek-in-slot` were silently OFF for every constant — in an ATTRIBUTE slot as well as a text one. TypeScript covers exactly the arithmetic and comparison directions on its own (`Signal<number> + 1` is `TS2365`, `=== 0` is `TS2367`); template / ternary / logical / unary are covered by NOTHING, and the worst of those is `text(constant('') || 'FALLBACK')` — a truthy handle makes `||` yield the HANDLE, so the fallback is silently swallowed and it renders `""` with no `[object Object]` tell. The one fact is now stated ONCE, in `extract-deps.ts:signalFactoryOf`, resolved through `HelperBindings.resolveCall` — the same gate that decides whether `div(…)` is the framework's — and consumed by all four sites that used to ask the name: `isSignalExpr`, `analyzeSignalExpr`'s rebasing branch, `lower.ts:valueSrc`'s producer branch, and (already) `rules.ts:isMappedSignalExpr`. It FAILS CLOSED: a module-scope declaration, a lexical shadow, a type-only import, an unresolvable/cyclic/unrelated import all resolve to "not a signal", i.e. NO diagnostic. Four things to keep straight. (1) **The parameter is required, not defaulted.** A permissive default silently restores bare-name matching at any site that forgets it, which is the defect itself; `PERMISSIVE_BINDINGS` is exported for expressions parsed in isolation by a unit test, and the requirement is pinned by a `@ts-expect-error` in `test/signals/extract-deps.test.ts` (the only thing that kills that mutation — no runtime test can). (2) **`transform-view.ts` routes every one of its ~20 sites through one local `isSignal` wrapper** reading the SAME ambient binding set `resolveCallee` uses, so signal recognition and callee recognition cannot disagree about one call. (3) **This fixed a silent MISCOMPILE, not just diagnostics.** `lowerHelperEach`'s DIRECT tier treats anything it does not recognize as a signal as STATIC, so a `constant(…)` in a row emitted `applyAttr(_r0, "data-unit", constant('mmol/L'))` and `_c2.data = String(constant(' · fixed'))` — both measured against the real runtime as `[object Object]`, with a clean build and a clean type-check. `@llui/dom`'s own `test/signals/constant.test.ts` is exactly that shape and passes only because that suite never runs the compiler. Recognizing the constant makes the tier decline (bail `each-direct: row-prop-unlowerable`) and the row lowers as an ARM where `el`/`text` consume the handle. That is the ONLY transform-output change across the repo: 1 file of 1504, 0 of the 829 in `packages/*/src` + `registry` + `examples` + `site/src`; the tier is lost at 1 `each` site of 84, and it is the file that demonstrates the bug, while a consumer's own `constant`/`derived` in a row KEEPS the tier (a re-optimization, pinned by its own test). **That closed the INSTANCE, not the CLASS — the class is #244, CLOSED in the next bullet.** (4) **`peek-in-slot`'s reach is whole-FILE and that is pre-existing, not new here.** `lintSignals` walks from `visit(sf, STATE_ROOTS, false)`, so a factory-produced signal is checked anywhere outside an `on*` handler or a `.map`/`derived` body — measured: HEAD already reports `derived([a],f).peek()` in a plain module-scope function, and `constant(…).peek()` now behaves identically. Zero occurrences pass the vite plugin's own lint gate anywhere in the repo (209 gated files of 1504); the one un-gated hit is `@llui/dom`'s `constant` test file. **But "pre-existing" was true of the REACH and not of the CONSEQUENCE, and that distinction was #245 — CLOSED two bullets down; the reach is no longer whole-file.**
- **A static row slot may not read a FREE identifier the row factory did not introduce (#244, CLOSED).** `lowerRowFactory`'s DIRECT tier emits everything it judged STATIC as `String(<expr>)` / `applyAttr(node, name, <expr>)`. "Static" meant "not recognized as a signal EXPRESSION", and recognition is by import provenance (#238), which reads the factory CALL in the expression — so a `Signal` HANDLE arriving as a bare identifier named no call at all, fell into the static bucket, and rendered `[object Object]`: `li({ 'data-unit': unit }, [text(unit)])` emitted `applyAttr(_r0, "data-unit", unit)` / `_c2.data = String(unit)` with a clean build, a clean type-check and no diagnostic. BOTH ways the identifier can be bound reached it — a view-helper PARAMETER and a CAPTURED module-scope `const unit = constant('mmol/L')` — and handing signal handles to plain view-helper functions is the composition pattern THIS FILE recommends, so it was the idiomatic shape rather than a corner case; the live in-repo instance was `packages/dom/test/signals/structured-dep-paths.test.ts`, green because `@llui/dom`'s suite never runs the compiler. **The string-edit transform has no `ts.Program`, so "is this identifier's declared type a `Signal`" is not a question it can ask** — the fix is `firstOpaqueFreeIdentifier` in `transform-view.ts`, consulted at the THREE positions that emit a static value: a `text()` slot, a non-`on*` attribute slot, and a ROW-LOCAL initializer. The local is the one a slot-only guard misses: `const u = unit` makes `u` a name the factory DID introduce, so the later `text(u)` sees a known identifier and the taint launders through. An identifier is opaque unless the ROW bound it (`item`/`state`/`index`, a row local), the slot expression bound it, it is an ambient global the module has not rebound (`Math`, `JSON`, `String`, …), or the file binds it EXACTLY ONCE to a `const` whose initializer is provably plain — a literal, an aggregate literal, a template/operator expression over plain operands, a `const` aliasing another plain `const` (cycle-guarded), or a function/class, since a function value is never a handle and that is what keeps a same-file `const fmt = (v) => …` usable. Five boundaries, each measured rather than assumed: (1) the CALLEE SUBTREE of a call is exempt, because what reaches the slot is the RETURN — that keeps `text(fmt(x))` AND `text(unit.peek())`, the sanctioned one-shot read the perf hint itself recommends; (2) an EVENT HANDLER is untouched, since a row legitimately closes over a handle to dispatch and the emitted factory stays lexically where the `each` was, so the free name still resolves; (3) resolution runs against the ORIGINAL module, never the synthetic file a helper inlining parsed, or every inlined row loses the tier; (4) NAME positions are not reads — tested through the generic `.name` slot rather than a hand-listed set, because the hand-listed version forgot a class `PropertyDeclaration`; (5) **the TRUST-WITHDRAWAL set is structural for the same reason, and a hand-list there is unsound BY CONSTRUCTION.** `moduleDeclaredNames` answers "has the module rebound this name", and a name it MISSES keeps the ambient-global allowance, i.e. miscompiles — so when the same hand-list discipline that (4) removed merely MOVED into it, it immediately lost `ModuleDeclaration` and `ImportEqualsDeclaration`: `namespace Math { export const PI = constant(3) }` emitted `applyAttr(_r0, "data-p", Math.PI)` while the `const Math = …` test passed beside it, i.e. #244 still open in the exact shape the fix claimed to close. It is now the generic `.name` test too. Its two consumers get SEPARATE views on purpose — a function/class EXPRESSION's own name rebinds inside its own subtree (so it must withdraw trust) but names the very value the enclosing `const` holds (so it must not make that `const` ambiguous); collapsing them made `const replacement = function replacement() {}` count twice and dropped the tier for every row reading it. **The COST is measured, not assumed, because the direct tier is the list hot path: ZERO tier losses across 825 files / 82 gated / 16 direct-tier `each` sites in `packages/*/src` + `registry` + `examples` + `site/src`, and the transform output is byte-identical for every one of them.** Widening the corpus to the test trees (1468 files, 210 gated, 41 direct sites) changes exactly ONE site — #244's own live instance, which becomes an ARM. **"Byte-identical output" is not "the predicate never fires in production", and the difference is worth stating**: it fires at ONE production slot today (`a2ui/src/render.ts`'s inlined `renderSurface`, on the view-helper parameter `fallbackCatalog` — a plain `Catalog`, so a conservative over-approximation), whose row already bailed for another reason, so the bail REASON token moves from `row-local-signal-alias` to `row-slot-free-identifier` and only the dev perf-warning line changes. A second site (`devmode-annotate`'s `STYLE_ROW`) fired until the plain-value proof learned `'…' + '…'`. Residue, stated as a limit: a call that RETURNS a handle (`text(makeUnit())`) is still unreachable without a checker; a property read off an object the file cannot prove plain now bails.
- **`peek-in-slot` is scoped to SLOTS, the walk starts OUT of slot context, and an EXIT is STICKY (#245, CLOSED).** `lintSignals` used to walk from `visit(sf, STATE_ROOTS, false)` — it entered the FILE already believing it was in a reactive slot — so any `.peek()` on a recognized signal anywhere in a module containing `component(` was reported, INCLUDING in a reducer body, where `.peek()` is the documented correct one-shot read and where this rule's own message tells you to put it. These are non-bypassable build errors, so the reach failed builds for code doing the right thing. The walk now starts `'outside'` and ENTERS slot context at the positions that build reactive output: a component `view` body (both the aliased-bag branch and the generic config-prop fallback — an undestructurable view's body is still built once), an element-helper call's ARGUMENTS (`div({…}, […])`, `el('li', …)`, `text(…)`, resolved by IMPORT PROVENANCE so a consumer's own `text()` opens nothing), and a structural primitive's reactive input / render arms. **The third state is the specification, not a detail.** On `main` the flag was MONOTONE — nothing below the root ever set it back — so once an `on*` handler or a `.map`/`derived` body had exempted a subtree, the whole of it was exempt. Adding ENTRY without stickiness re-enters those regions from the INSIDE, and measured five shapes `main` was silent on, every one a build error: a node built in an `on*` handler, in a `.map` body, in a `derived()` body, a STRUCTURAL primitive built in a handler, and a node built in a block-body render `const` — the SANCTIONED row idiom this rule's own message recommends. That is the class #245 exists to remove, reintroduced by its own fix. `'exempt'` is therefore sticky, which buys the checkable invariant that IS this change: **the report set is a SUBSET of `main`'s for every program — #245 may only remove a report, never add one.** **The evidence for each half is different, and conflating them overstates one of them.** The in-repo reports are 6 messages on 5 lines across 3 files, and a carrier probe (each entry removed alone, compiler rebuilt, corpus re-linted) attributes them: the `each` entry uniquely carries 2 (`a2ui/catalog/headless.ts`, `markdown/render.ts:138`), the `show` entry uniquely carries 1 (`browse-view.ts:727`), 3 are carried REDUNDANTLY by element-call ∨ `each`-arm (removing either alone keeps them; removing both loses all 3), and `branch` + both `view` entries carry NONE. So **the element-call entry carries no in-repo report on its own — it is justified by unit tests** (removing it reddens 4, three of them pre-existing `peek-in-slot` tests), not by the corpus; and do not say the reports "live in view helpers", since `browse-view.ts` contains two `component(` calls. Turning EVERY entry off takes the corpus to 0, so nothing reports by accident. Corpus deltas are 0 lint-report changes on both the 825-file and 1468-file sweeps — the fix removes a false-positive CLASS whose in-repo blast radius was already zero, which is why its evidence is a two-direction test matrix rather than a corpus delta.
- **There is exactly ONE dep analyzer, and everything that answers "which paths does this read" routes through it.** `signals/analyze-deps.ts` (per accessor body) + `signals/extract-deps.ts` (per signal expression, rebasing onto absolute paths) are the analysis; `signals/collect-signal-deps.ts` (per file, for `llui_static_collect_paths`) and `build-manifest.ts` (per exported helper, for the dormant `__llui_deps.json` producer) are DRIVERS over it, not re-implementations. A second one existed — `collect-deps.ts` + `accessor-resolver.ts` + `track-utils.ts`, deleted in #92 — and it diverged in both directions: it truncated every path at two segments, and it only recognized the pre-signal authoring surface (`text(s => s.x)`, `div({title: s => s.x})`, `scope`/`memo`/`track`, none of which `@llui/dom` still exports), so on every real component it reported ZERO paths while the tool presented that as the answer. Truncation is coverage-SOUND (a dep on a prefix covers its descendants, because an immutable update replaces the prefix reference), which is why it never showed up as stale UI and could sit there for a year. A new question about dependencies gets a new driver, never a new walker. `packages/compiler/test/collect-signal-deps.test.ts` pins the depth AND asserts parity with the `deps` arrays the transform actually emits.
- **A driver that walks owes the two disciplines every walker here owes, and the #92 replacement shipped without both.** (1) **An identifier is a root only where it is READ.** `forEachChild` yields identifiers in NAME position — an object-literal key (`connect({ state: state.at('x') })`), a binding `propertyName` (`({ el, state: sig }) => …`), a member name (`opts.state`), a parameter name — and root-matching those reported a whole-state read that never happened, putting a false `opaque: true` on the canonical `connect`/`overlay` wiring. The one name-position identifier that IS a read is a `ShorthandPropertyAssignment` in an object literal. (2) **Rooting is SCOPE-AWARE.** `each(state.at('rows'), key, (state) => …)` hands the arm a plain ROW handle reusing the name; carrying the root in invents top-level paths that do not exist in State. Prune roots with `scopeIntroduces` (exported from `signals/helper-bindings.ts`) — it is the repo's most complete shadowing predicate (params, block `const`/`let`/`var`, hoisted `function`/`class`, `for` initializers, `catch`) and re-deriving shadowing per walker is how the cases at the end of that list get forgotten. Both defects produce a CONFIDENT WRONG ANSWER to an agent, which is the very thing #92 exists to remove, so both are pinned by name in that test file.
- **A compiler A/B in this repo needs a `dist` REBUILD between swaps, or a "no difference" result is FABRICATED.** `packages/dom` consumes `@llui/compiler`'s built `dist`, not its source. Swapping in a baseline `src` without rebuilding measures the SAME build twice, so both arms agree — and the natural reading of that is "pre-existing, my change is innocent". Measured: a lane's first reproduction of a real stale-UI regression showed 8/8 failing on BOTH branches; after rebuilding per swap, main rendered correctly and the branch froze. The false result is the dangerous direction — it exonerates.
- **A corpus-diff count is meaningless without stating whether the PLUGIN GATE was applied.** `compile-plugin.ts`'s gate (`hasComponentCall || (importsDom && /\beach\s*\(/)`) decides whether a file is ever transformed in a real build. Measured on one change: wide sweep GATED = 3 diffs, UNGATED = 5. Two agents disagreed (3 vs 4) purely because neither said which they ran. Report both, or name the gate.
- **Parse per real filename ScriptKind** (`.ts`/`.mts`/`.cts` = TS, `.tsx` = TSX) — parsing `.ts` as TSX misparses generic arrows and both skips compilation AND emits bogus lint errors. **There is exactly ONE `ts.createSourceFile` call in the package** (`src/parse.ts`, pinned by `test/parse-module.test.ts`), and every entry point — lint, the transform, the four schema/annotation extractors, the cross-file resolver, `collectSignalDeps`, and `@llui/compiler-ssr`'s `'use client'` transform — takes a `ParsedModule` (lazy, memoized text+tree) instead of a `source: string`. Each of them used to parse the text itself, so ONE dev transform (`devMode || agent`, i.e. every keystroke-save) parsed the same module **17 times** and each sibling type file 8 times (#93). Two consequences to keep: (1) the plugin builds ONE `createModuleCache()` per `transform` and threads it into `ResolveContext.modules`, so reuse does not depend on any caller remembering — the ONLY legitimate second parse of a module is the lint autofix rewriting `code` mid-transform; (2) nothing may MUTATE the shared tree or hang state off a node (a pass that needs per-node state owns a `Map`). The extractors' old hard-coded `'input.ts'`/`'msg.ts'` filenames also meant every `.tsx` component's schemas came out of a TS parse of TSX. Error recovery masked that for most JSX (seven forms tried — self-closing, fragments, conditional, attribute arrows, generic, `/`-in-text — all kept their type aliases), but NOT where recovery swallows the following statement: a `.tsx` with `const list = <ul>{xs.map(x => <li key={x}>{x}</li>)}</ul>` above `export type State` extracted `null`, so an `agent: true` build shipped no `$ss` and nothing errored. With one tree threaded everywhere a wrong ScriptKind is now wrong everywhere at once, which is why `fileName` has no default anywhere and the Vite plugin parses under the query-stripped id (`Widget.tsx?v=abc` otherwise reads as TS — latent, no misparse demonstrated from it, closed anyway).
- **Schema metadata is computed per `component()` call**, not once per file.
- **The injected runtime import must dodge EVERY use of a helper name anywhere in the file, and the dodge must be decided BEFORE lowering.** `transform-component.ts` prepends `import { … } from '@llui/dom'` for the helpers it emitted; that declares top-level bindings, so a file with its own `const el = …` / `function el() {}` / `import { el } from './x'` got a duplicate declaration — a SyntaxError in code that compiled before (#90; the old check only looked at the file's other `@llui/dom` specifiers). `runtime-helpers.ts` plans an ALIAS per collision (`import { el as el$llui }`), threaded into the view transform (`setHelperEmitNames`) so every emitted call site carries it — an edit's text ALSO contains verbatim user code, where a bare `el(...)` legitimately means the user's binding, so a post-hoc rename of emitted text cannot work. Skipping the injection is NOT an alternative: it leaves the lowered call bound to the user's value, which compiles and silently misbehaves. **The collision test is deliberately the coarsest one — does the identifier occur ANYWHERE in the file (`allIdentifierNames`) — and narrowing it to top-level bindings is a REGRESSION, not a cleanup.** Two cases a top-level scan misses, both real: a `var` hoisted out of a block (`if (x) { var el = 1 }`) reaches module scope and re-declares the import; and a binding that merely SHADOWS it at the emitted call site (`view: () => { const el = …; return […] }` — block-body views ARE lowered) rebinds the lowered call to the user's value with no error anywhere. Over-approximating (a `type el = …`, a property name) only costs an alias nobody needed; under-approximating costs a SyntaxError or a silently wrong call. The one carve-out is the subtraction: a `@llui/dom` import binding the helper under its OWN name IS the helper, so it is emitted bare and not re-imported — but `import { text as el }` binds `el` to a different export and therefore collides.
- **Every agent annotation argument goes through ONE tokenizer** (`packages/compiler/src/annotation-args.ts`), never a per-tag regex. A `["“]([^"”]*)["”]` character class cannot express a quoted string — it stops at the first quote, escaped or not — so `@routeGated`/`@validates`/`@intent`/`@example`/`@warning`/`@emits`/`@should` each truncated a predicate carrying a quote, and the escape-your-quotes workaround the docs advertised produced a predicate ending in a backslash (#89). The damage is INVISIBLE: `@llui/agent` compiles these strings with `new Function` inside a try/catch, so a truncated `@routeGated` degrades to an ALWAYS-OPEN gate and a truncated `@validates` to ACCEPT EVERYTHING — no crash, on a security-adjacent annotation. Keep that try/catch (defence in depth) but never treat it as the guard. The grammar DROPS what it cannot read unambiguously and `agent-annotation-syntax` fails the build on the same input — TWO checks: the argument grammar, plus (for `@routeGated`/`@validates` only) that the captured predicate PARSES as JS, since `@validates("")` or an unbalanced paren is well-quoted and still degrades to accept-all. The rule is scoped to the JSDoc positions the extractors actually read (type alias, its union members, property signatures) because framework sources document the grammar in prose (`@emits("k1", "k2", ...)`) and flagging that would fail valid builds. `@llui/vite-plugin` runs it on NON-component modules AND — critically — on every sibling the cross-file resolver reads (`readSource`), because the canonical `import type { Msg } from './msg'` is erased by esbuild: `msg.ts` never enters the module graph, is never transformed, yet its annotations still ship as `$ma`. Report against the SIBLING's path, and COLLECT rather than throw from `readSource` (`findTypeSource` wraps it in best-effort try/catch that would swallow a `this.error`).
- **A `tagSend` variant list and the `type` its handler dispatches are ONE fact stated twice, and both halves are now checked.** `libraryVariants` becomes `__lluiVariants`, read at `packages/dom/src/signals/element.ts` and surfaced to the agent as "which Msg variants can this control emit" — so a drifted tag is a string that LIES to a model, with no runtime symptom (#118, the class of #89 and #92). The compiler-emitted tags are derived from the `send` call and cannot drift; every HAND-WRITTEN call site can. TWO guards, neither sufficient alone: the TYPE (`libraryVariants: readonly M['type'][]` — `tagSend` no longer takes `send: unknown`) rejects a name that is not a Msg variant at all, including where the handler is a named function no analysis can read (`tagSend(send, ['hide'], dismissOnEscape)`); and the `tag-send-drift` lint rule READS the handler and rejects a tag naming the WRONG variant, which type-checks fine since `'touch'` and `'blur'` are equally valid `M['type']`. The rule's two directions have DIFFERENT preconditions and the asymmetry is the design. DISPATCHED-BUT-UNDECLARED is reported whenever the dispatch is ATTRIBUTABLE — the `send` being called must still RESOLVE to the tagged dispatcher, and the code containing it must RUN when the handler runs. Neither is paperwork: `items.forEach(({ send }) => send({type:'inner'}))` and `const send = other` rebind the name to a different function, and a merely RETURNED closure never runs, so all three reported a variant the control cannot emit until the walk was pruned with `scopeIntroduces` (the repo's one shadowing predicate — never re-derive shadowing per walker) and taught to skip returned functions and nested `tagSend` handlers. RETURNED has TWO halves, and the position is not covered until BOTH are: what a returned value can sit INSIDE, and what can sit THERE. (1) The CONTAINERS are every position whose value can BECOME the returned value with NO CALL in between, not just the direct return operand — a returned object or array literal (`return { h: () => send({type:'inner'}) }`, `return [() => …]`), an erased `as`/`satisfies`/parenthesis/`!`, a conditional ARM, a `??`/`||`/`&&`/comma operand, a returned CLASS EXPRESSION's members, a class field's initializer — and attributing a closure in any of them was a direction-1 false positive on code that type-checks (#157). (2) The DEFERRED-BODY kinds are every node whose body does not run when the literal holding it is built: an arrow, a function EXPRESSION, a METHOD SHORTHAND, a getter, a setter, a constructor. #157 widened (1) and left (2) reading arrow-or-function-expression only, so `return { h() { send({type:'inner'}) } }` stayed flagged while the identical `return { h: function () { … } }` did not — the verdict decided purely by the SPELLING, and falling on the MORE idiomatic one (#182: the same defect one node KIND out instead of one position in, found by review of the #157 fix, on prose that had already claimed 'the whole of the position'). The boundary is still the call: `return items.map(() => send({type:'x'}))` and `use({ h: () => send({type:'x'}) })` DO run, and treating a call argument as just another container would switch direction 1 off for the most common dispatch shape there is (`setTimeout`/`map`/`forEach`). Several things inside a returned class run too, which is why a class expression is a transparent CONTAINER and NEVER a skipped subtree: a `static { … }` block and a `static h = …` initializer evaluate WHEN THE CLASS EXPRESSION DOES, i.e. inside the handler, and a heritage clause (`extends mix(…)`) is not a member. TREAT THAT AS A CHECKED LIST, NOT A CLOSED ONE — every widening of this function so far has been "the same thing one position/kind further out" (#157 → #182 → #194), and the honest statement is that these are the positions that have been ENUMERATED AND TESTED, not a proof that no fourth exists. The same exception recurs one level down, ON THE MEMBER NODE ITSELF, which IS skipped whole: a COMPUTED member name (`{ [k()]() {} }` evaluates `k()` when the literal is built) and every DECORATOR — the member's own and its PARAMETERS' — are evaluated at build time and are rescued by name in `memberBuildTimeExpressions` (a parameter DEFAULT is deliberately not: it runs when the member is CALLED, the deferred half). Decorators were the miss #194 caught, and its shape is the tell: rescuing one position by name silently answers "no" for every sibling position on the same node, so the next member-level position added to TypeScript is missed by DEFAULT. Rescued positions take the OUTER liveness, never the member's `inScope` — a computed key and a decorator are both evaluated outside the member's own parameter scope, so `{ [send({type:'KEY'})](send: unknown) {} }` must not be pruned by that parameter (the class expression's self-name still prunes, because it is bound one scope further out and is already in `live`). Membership is TESTED (`parent.properties.some(p => p === cur)`, never a bare `true`): an unconditional yes answers for positions it never looked at, and is precisely the shape that turns unsound the day a kind is added above it. THE SCAN MUST START AT THE HANDLER NODE, NOT ITS BODY: the nearest rebinding scope is the handler's OWN parameter list, so a walk beginning at `handler.body` prunes every shadow except the one closest to the tag — `({ send }: Ctx) => send({type:'inner'})` and `(send: Ctx['send']) => …` are the `forEach` case exactly one scope up, and both fired on code that type-checks clean. The parameter list is also CODE: a default runs on every call, so a call there costs completeness and a dispatcher mention there escapes (`(e = compute()) => …`, `(_h = register(send)) => …` both claimed a completeness the handler had not earned). Walk EVERY position a default can be written in — `p.initializer` (the default of a whole parameter) AND the defaults nested inside `p.name` when it is a BINDING PATTERN (`({ x = compute() })`, `([x = send({type:'a'})])`, `({ o: { x = compute() } })`), which hang off `BindingElement`s and are reached only by walking the pattern — and pass `!scopeIntroduces(handler, name)` as their liveness, since defaults evaluate in the parameter scope and so take the same liveness as the body. THIS DEFECT HAS NOW SURFACED FOUR TIMES, each one position further in (body-only → parameter list → parameter initializers → pattern defaults); the next walker that says "the parameter list" must mean the whole of it, or it will surface a fifth time. A plain identifier `p.name` is skipped on purpose: it IS the binding, so if it spells the dispatcher then `scopeIntroduces` has already made liveness false, and a name in DECLARATION position is never a read. - **A DOM write from a view's own event handler is a build error (`imperative-dom-mutation`, #231), and its SCOPE is three syntactic conditions — not "inside a component view".** A consumer app reasoned from build-once views to the opposite conclusion: "the label is a STATIC node, no signal binding depends on it, so the reconciler never rewrites it and swapping its `textContent` from the click handler is safe." - **`prefer-at-over-map` may only recommend `.at()` where `.at()` EXISTS, i.e. on a receiver that provably carries a state PATH (#267).** Its fix is `.at('x')`, and a `.map`/`derived` signal has no `.at` (type `never`, runtime `LluiFrameworkError`). The rule used to fire on any `.map` whose chain reached a root (`isSignalRootedAccess`), and every `show`/`branch` render param was added as a root unconditionally — so `state.map(f).map((p) => p.x)` and, the case that shipped, a `branch` arm's `v.map((s) => s.message)` over a mapped value were both build ERRORS whose only accepted fix threw at runtime (the component-gallery shell carried a workaround). Roots now carry a `RootShape`: `'path'` (the view's `state`, an `each` row's `item`/`index` — row handles are paths whatever the items signal is — and a narrowed param over a path condition), `'mapped'` (a narrowed param over a `.map`/`derived`/mapped-param condition — the runtime hands the arm the condition handle itself), `'unknown'` (a narrowed param over anything the walk cannot see through, e.g. a local alias). `prefer-at-over-map` requires `isSliceableSignalExpr` (a `'path'` root followed only by `.at(…)`); `at-after-map` reports `.at()` on a `'mapped'` root with a message naming the `.map((v) => v.x)` read. `'unknown'` gets NEITHER report — whenever the condition's type is not a path `Signal`, such a param's type has no callable `.at()` (`show` types it by the condition's own non-null view: `MappedSignal` for a mapped condition, `ReadSignal` for a `ReadSignal` of unknown kind; the `branch` overloads type it `MappedSignal`), so the type checker covers the alias case the syntax walk cannot. Do not collapse `'unknown'` into either side: into `'path'` re-opens this bug, into `'mapped'` reports valid `.at()` on an aliased path signal.
