# Packaging landmines and dormant architecture

_Detail behind the short rules in the root `CLAUDE.md` (Packaging, Active proposals). Moved here verbatim so the always-loaded instructions stay small; read this before changing the area it covers._

## Packaging landmines

- **`@llui/dom` (and any package owning the render context) MUST be a `peerDependency` (`workspace:^`) + `devDependency`, NEVER a `dependency`.** As a hard dep, `pnpm publish` pins the resolved version; a consumer on a different `@llui/dom` gets two physical installs, each with its own module-scoped `currentContext`, and every `provide()`/primitive from the consumer's view throws `provide() can only be called inside a component's view()` even though it is. This caused a production outage; the fix is the peer-dep pattern, not `pnpm.overrides`.
- **`typescript` is a `peerDependency` (`>=5.0.0 <7.0.0`) + `devDependency` of `@llui/compiler`, `@llui/compiler-ssr` and `@llui/vite-plugin`, NEVER a `dependency`** (issue #64). Same failure shape as the `@llui/dom` rule above: a hard dep pins the published version, so a consumer with its own TypeScript gets a second physical install and the compiler analyses their sources with a DIFFERENT `ts` than they compile with — two `SyntaxKind` tables, one silently wrong dep mask. The floor is 5.0 because the newest API in use is `ts.isSatisfiesExpression` (TS 4.9); the ceiling is a major because TypeScript does not follow semver. All three must carry the SAME range (they install together), and it must stay REQUIRED — `import ts from 'typescript'` runs at module load, so an optional peer trades an install warning for a MODULE_NOT_FOUND while Vite loads the config. `packages/compiler/test/typescript-peer-dependency.test.ts` fails the build if any of this drifts.
- **`tsc` does not clean `dist/`.** Deleted-source artifacts linger and ship unless cleaned before pack (`scripts/publish.sh` now `rm -rf dist` before building). Cross-package `@llui/*` refs are `workspace:*` (pnpm rewrites at pack). `__llui_deps.json` is no longer emitted into tarballs (see Active proposals).
- **`stripInternal` deletes any declaration whose LEADING COMMENT contains the internal JSDoc tag, and TypeScript's test for it is a raw substring search that cannot tell an annotation from the prose beside it (#253, CLOSED).** This is the repo's own "needle that also matches the prose" trap, except the needle belongs to TypeScript (`isInternalDeclaration` -> `hasInternalAnnotation`, literally `comment.includes(...)`) and the damage lands in a PUBLISHED artifact. `packages/lexical/src/nodewidget.ts` opened with an 80-line `//` header explaining the seam, which mentioned the tag twice in prose; the next statement was its `import { … } from 'lexical'`, so the WHOLE IMPORT was deleted from `dist/nodewidget.d.ts` and `LexicalNode`/`NodeKey`/`LexicalEditor`/`Klass`/`EditorDOMRenderConfig` shipped as five unbound names — `TS2304` for any consumer building with `skipLibCheck: false`. **Almost nothing in-repo could see it**: every workspace inherits `skipLibCheck: true` from the root tsconfig, so no package type-checks another's emitted `.d.ts`. The exception is how it WAS found — `examples/markdown-editor` stood alone and did not inherit it (github-explorer still does not). That example now sets `skipLibCheck: true` itself, for reasons written in its tsconfig, so the canary is deliberate rather than accidental. Five packages set `stripInternal` (`dom`, `lexical`, `lexical-collab`, `lexical-loro`, `markdown-editor`); the fix is to keep the tag UNSPELLED in prose, never to delete the documentation. **Do NOT take the fix the issue itself suggested — moving the header below the imports is WORSE, measured against real tsc**: the header then attaches to the next DECLARATION and `stripInternal` deletes that instead, silently dropping an export from the published API, and whether any binding check notices is luck (it shows up as a free name only if something that survived still references the deleted one — `WidgetPlacement` does, via `WidgetSpec.placement`; in the reduced repro nothing did, and the emitted `.d.ts` was well-bound and quietly missing an interface). Blank lines do not detach a header from the statement below it. `pnpm check:dist` gates BOTH directions as two arms of one guard (`scripts/lib/dist-type-bindings.mjs`): a DIST arm asserting every type name referenced in every publishable package's `.d.ts` is bound (measured: 3912 references across 558 files, 0 free), and a SOURCE arm asserting the tag appears only as a real JSDoc annotation and never in a `//` comment or as JSDoc prose. **The dist arm is a BINDING check, NOT a type check**, so it cannot resolve module SPECIFIERS — an `import('x').Y` binds nothing — and that hole cost two shipped defects (#257, CLOSED, next bullet). Both arms self-check against a known-bad input before giving a verdict, and the source arm additionally floors the number of files that reached the analyzer — a corpus floor counts files WALKED and cannot see a pre-filter silently dropping everything (measured: with #253 restored and the pre-filter broken, exit 0 under a GREEN line reading `0 of 109 source files scanned`).
- **A published `.d.ts` can name a module the package does not depend on, and a BINDING check cannot see it (#257, CLOSED).** The #253 dist arm is green on an unresolvable SPECIFIER by construction, and running the check it declined to be — ONE `ts.Program` over every publishable package's `.d.ts` with `skipLibCheck: false` — reported **11 diagnostics in 4.7-6.1 s** (identical under `types: ['node']` / `types: []` / no `types`), **8 in our own output**. Two were live defects. (1) `@llui/vite-plugin` leaked `import("rolldown").{TransformPluginContext,ModuleType,PluginContext,NormalizedOutputOptions}` into `dist/{compile,hud}-plugin.d.ts` — **6 x TS2307**. The mechanism is INFERENCE, not an import: the four `create*Plugin` factories returned an object literal `satisfies Plugin`, so TypeScript inferred the precise literal type and wrote each hook's contextual `this` under the module where vite DECLARES it, which is `rolldown` — an undeclared transitive living only inside vite's own pnpm dir, unresolvable from `packages/vite-plugin` under Bundler, NodeNext and Node10 alike. **The fix is a declared `: Plugin` return type on all four factories, NOT a `rolldown` dependency**: vite VENDORS AND PINS rolldown, so a hard dep installs a second copy whose `TransformPluginContext` is a different type identity from the one vite contextually types the hook with — the same class of hazard that makes `typescript` a peer dep of this very package — and a peer dep is worse still, since a consumer never installs vite's bundler directly. Annotating also closes the channel STRUCTURALLY rather than per symbol: `config-plugin`/`dev-server-plugin` leaked nothing only because their hooks happen to be typed in vite's own file, and one vite refactor moves them. **The public type surface is byte-unchanged, measured**: `dist/index.d.ts` (the only `exports` entry besides `./notes`) already read `export default function llui(options?): Plugin` and diffs empty; what widens is the four internal factory `.d.ts`, which no `exports` entry reaches. (2) `@llui/devmode-annotate-editor` emitted `import '@llui/markdown-editor/styles/editor.css'` into its published `dist/index.d.ts` — **1 x TS2882**, on its PUBLIC entry point. TypeScript never elides a bare side-effect import from declaration emit, and the runtime side effect is load-bearing (the HUD's light-DOM mode gets the editor stylesheet from it; only the `isolate: true` shadow path uses `shadowCss`), so the fix is on the OWNER: `@llui/markdown-editor`'s `./styles/*.css` subpath exports now carry a **`types` condition** pointing at a shipped `export {}` (`src/styles/css.d.ts`, copied into `dist/styles/` by the build). **A sidecar `editor.css.d.ts` beside the CSS does NOT work and was measured** — under `moduleResolution: bundler` the specifier resolves through the exports map, and with no `types` condition TypeScript never looks for a declaration file at all; a wildcard `declare module '*.css'` was rejected as a global augmentation a published package must not ship. `devmode-annotate-editor/src/css.d.ts` was narrowed to `*.css?raw` only, so that package's own `check` now exercises the real resolution. Measured clean under `bundler` and `nodenext`; `node10` ignores exports maps entirely and is deprecated in TypeScript 6. **The gate is now a THIRD arm of `check:dist`** (`distSemanticDiagnostics`), scoped STRUCTURALLY to `packages/*/dist/**` rather than by allowlist — 3 of the 4 surviving diagnostics are inside loro-crdt's own shipped types, exactly what `skipLibCheck` exists for, and allowlisting them would redden the gate on every dependency bump. `SEMANTIC_ALLOWED` holds ONE entry (`markdown-editor`'s deliberate `MarkdownListNode.$config`, #129) keyed `file` **+** `code` — a bare code excuses every occurrence in the repo — and is CLOSED AT BOTH ENDS: an entry that stops matching fails as OBSOLETE. It compiles a VIRTUAL probe `.d.ts` in the same program before giving any verdict, asserting it still reports TS2882 / TS2307 / TS2304, because a file count proves the walk ran and not that the program can still report — and the probe is placed INSIDE a real `dist` dir so its diagnostics travel the SAME path a genuine finding does (structural scope, allowlist lookup, push into `reported`). **Both of those were shipped WRONG in the first cut and are the reason to read this paragraph.** (1) The corpus check was a FLOOR of 100 against 558 files: dropping ONE package from the swept roots — a single edit — took the sweep to 535 and left the gate GREEN with `import("rolldown")` back in the published `.d.ts`, while 558 and 535 were printed one line apart in the success output with nothing comparing them. It is now an EXACT set size across THREE independent enumerations of the same corpus (invariant 1-3's `walk`, arm 4's `walkDts`, arm 5's own `walkDts`) plus what the PROGRAM actually loaded, so no single edit can silence it by narrowing both sides — measured, narrowing both `walkDts` consumers still fails on the integrity-walk oracle. This is CLAUDE.md's own rule (`assert an EXACT set size; a floor only detects under-collection`) applied one guard over. (2) With the probe classified OUTSIDE the report path, a mutation making the arm report nothing from our own output was killed only by the obsolete-allowlist check — i.e. only by an entry expected to VANISH once #129's TS2416 resolves, so the gate would have got weaker the day that was fixed. The allowlist matcher is also EXTRACTED (`semanticAllowanceIndex`) and unit-tested in both directions, because a matcher mutated to `a.code === code` leaves every entry well-formed, is green on the gate by construction, and is exactly the bare-code licence this file warns about elsewhere. Cost: `check:dist` 1.6 s -> **7.6 s** wall. **Say what it is not:** it root-names every `.d.ts` in `dist/`, which is STRICTER than a consumer — measured, `compile-plugin.d.ts` and `hud-plugin.d.ts` are unreachable from `@llui/vite-plugin`'s public entry points, so those 6 x TS2307 were not yet consumer-visible and would have become so the moment anything re-exported those factories. Being stricter is the point. The BINDING arm is retained though its reports are now a strict SUBSET: it carries no allowlist (so #253's exact shape cannot be switched off by one edit), it gives a message written for #253, and it is what the buildless unit tests exercise. **One second-order consequence, caught by `@llui/site`'s API test rather than reasoned about: turning a CSS subpath export from a STRING into a conditional object makes it look like a TypeScript entry point to anything that decides by reading `types`.** Four sites did (`site/src/generate-api.ts` plus three in `site/test/generate-api.test.ts`), all filtering on `target.endsWith('.css')` — which is a `.d.ts` path once the condition exists — so the two CSS subpaths were enumerated as public API and demanded reference sections. A CSS entry point is named by its SUBPATH, and that is now the predicate; testing only the target was already the weaker spelling and happened to work while every CSS export was a bare string.
- **The compiler↔runtime metadata ABI must move in lockstep, and its names must be FINAL at emit time.** `@llui/compiler` WRITES the six agent/devtools property keys (`$ms`/`$es`/`$ss`/`$ma`/`$sh`/`$cm`) onto every compiled `component({...})` literal; `@llui/dom` (debug registry) and `@llui/agent` (LAP handshake) READ them. Writer and readers land in DIFFERENT bundle chunks under any vendor split — stock `manualChunks: { vendor: ['@llui/dom'] }` is enough — so nothing may rewrite the name after emission. A post-bundle rename pass scoped to chunks containing compiled modules did exactly that and left the runtime chunk reading the old name: every schema silently `undefined` in production `agent: true` builds, with no error anywhere (issue #45). The table is declared TWICE — `packages/compiler/src/emit-names.ts` and `packages/dom/src/signals/compiler-keys.ts` — because `@llui/dom` must stay dependency-free while the compiler pulls in `typescript`; `packages/dom/test/signals/compiler-metadata-abi.test.ts` fails the build if the two diverge. Change a key in BOTH, and treat any value change as breaking: a consumer on a new compiler with an old runtime reproduces #45 and the runtime CANNOT detect it (an absent key is indistinguishable from a build that emitted no metadata). `@llui/vite-plugin` therefore carries a `@llui/dom` peer range so the package manager catches the skew; `@llui/compiler` cannot declare one — a dev-dep edge back to `@llui/dom` would make the workspace graph cyclic, since `@llui/dom` dev-depends on the compiler for its tests.
- **Do NOT resurrect deleted code.** Off-limits (git history has it if ever needed): the v2c compiler-module registry (`module.ts`/`ModuleRegistry`), the introspection/devtools factories, the `@llui/compiler-{introspection,devtools}` packages, the cross-file walker (`walkProgram`/`cross-file-walker.ts`), the second dep analyzer (`collect-deps.ts` / `accessor-resolver.ts` / `track-utils.ts`, #92), `@llui/eslint-plugin`, and the two-word bitmask / `elSplit` / `__dirty` reactivity model. Docs live in `site/content/` — `docs/designs/` was removed; do not reference it.

## v2 compiler proposal status

- **v2 Compiler Architecture** (`docs/proposals/v2-compiler/`) — partially realized by the signals migration: `@llui/compiler` is a standalone package (extracted from `@llui/vite-plugin`), and cross-file Msg/State/Effect analysis is live (`cross-file-resolver.ts`, wired into the vite-plugin). The **live** transform path is `transformSignalComponentSource` (a single string-edit signal transform); it emits agent/devtools metadata **inline** (its own `sharedMetaProps`), NOT through a registry.

  **Superseded/removed (do not resurrect without a reason):**
  - The v2c compiler-module registry (`module.ts` `CompilerModule`/`ModuleRegistry`), the introspection/devtools factories (`introspection-factory.ts`), and the `@llui/compiler-{introspection,devtools}` packages were **deleted** — they were only ever driven by the `transformLlui` orchestrator, which the signals migration replaced with `transformSignalComponentSource` (inline metadata emission). The extraction functions live in `@llui/compiler` (`msg-schema.ts`, `state-schema.ts`, `msg-annotations.ts`, `schema-hash.ts`, `binding-descriptors.ts`) and are called inline by the transform.
  - The legacy cross-file dep-analysis **walker** (`walkProgram`/`crossFileAccessorPaths` in `cross-file-walker.ts`) was **deleted** — it was the v2b transform path, removed from the live route when the signal transform became the only compilation route. The live cross-file work uses `cross-file-resolver.ts` (Msg/State/Effect schema resolution) + the signal transform's own dep analyzer (`analyze-deps.ts`/`extract-deps.ts`).

  **Dormant-but-kept:** The cross-package library ABI (`__llui_deps.json`, schema v2). The producer tooling (`build-manifest.ts`, `scripts/emit-deps.mjs`) is kept in-repo but **no longer emitted into published tarballs** — `scripts/publish.sh` stopped shipping it (it was ~191 KB of dead weight across the stack for a consumer that doesn't exist). The **consumer** narrowing is **not wired into the live transform** (it needs a `ts.Program`/checker the string-edit transform lacks; phase 3 was evidence-closed 2026-06-10 — zero qualifying call sites in real consumers). `manifest-resolve.ts` is kept as dormant forward-compat. The producer's per-parameter read analysis is `signals/analyze-deps.ts`, the one live analyzer — it used to be `collect-deps.ts` / `accessor-resolver.ts` / `track-utils.ts`, which #92 **deleted** (see the compiler invariants above); nothing in the repo imports them and they must not come back. If a checker-backed consumer ever lands, re-enable the emit in `publish.sh` (producer + consumer + E2E test together). See the status note in `docs/publishing-a-precompiled-library.md`.

  Note there is no runtime `track()` _primitive_ in `@llui/dom` — only the compiler annotation. The proposal predates the signal runtime, so its references to the legacy runtime (`update-loop.ts`), the deleted `@llui/eslint-plugin`, and the two-word bitmask are historical — read it for the module-system direction, not the runtime model.
