# CI and the repo's own gates

_Detail behind the short rules in the root `CLAUDE.md` (CI). Moved here verbatim so the always-loaded instructions stay small; read this before changing the area it covers._

## CI — where it differs from what you run locally

Reproducing CI means mirroring `.github/workflows/ci.yml` **step for step, filters included**. Two differences have already cost a red `main`:

- **`--filter=!@llui/site` applies to the BUILD step ONLY.** `pnpm turbo check` and `pnpm turbo lint` run UNFILTERED, so the site is type-checked and linted in CI even though it is excluded from the build. Carrying that filter across to `check` in a local pre-merge run is how a genuine break reached `main`. **`@llui/site` and `@llui/registry` are the only PACKAGES that type-check a file importing `vitest.shared.ts`, and since #252 they are not the only GATE** — all **29** files named `vitest.config.ts` (26 packages + `registry/` + the site + `examples/component-gallery`, #267) import it, as do the two specially-named ones (`packages/lexical-loro/vitest.stress.config.ts` and the root `vitest.scripts.config.ts`, #249) for **31** configs in total, but the packages' tsconfigs include only `["src", "test"]`, while the site's additionally lists `"vite.config.ts", "vitest.config.ts"` and the registry's `tsconfig.test.json` (#272) lists `["test", "vitest.config.ts"]`. So among packages the repo's root config is checked in exactly two places, by virtue of two `include` arrays; `pnpm check:scripts` is a third gate, and it is not a package. The instance: `vitest.shared.ts`'s duration reporters carried `as const`, making the inner `['json', {…}]` a `readonly` tuple, which vitest's `reporters` type (`ReporterName | Reporter | [name, options]`) does not accept. It compiled everywhere because almost nothing type-checked the file — and the site gained its `check` script (#176) in the same batch that added the reporter (#193), so the two halves landed together and neither lane's own verification could see it. Type root config against vitest's own exported config type rather than reaching for `as const`; the hygiene that looks free here is a type error at the one call site that checks it. (Widening the other `include` arrays would close the hole generally — nobody has, and the cost is unmeasured.) **`scripts/` is the second gate (#252, CLOSED).** `pnpm check:scripts` (`tsconfig.scripts.json`, a CI step and a `verify` step) covers `scripts/**/*.ts` + `scripts/**/*.mjs`, and its program transitively pulls in `vitest.shared.ts` plus `packages/lexical-loro/vitest.config.ts` and `vitest.stress.config.ts`, so the `as const` defect described above would now redden two gates rather than one. **Name the CARRIER correctly if you are about to delete one of these tests, because the two roots are carried differently** — measured by removing each file and re-running `--listFiles`: the two lexical-loro configs come ONLY from `scripts/test/lexical-loro-stress-lane.test.ts`, which imports them statically, while `vitest.shared.ts` is carried REDUNDANTLY by BOTH tests — removing either one alone still leaves `vitest.shared.ts` in the program, and only removing both drops it (that redundancy is about `vitest.shared.ts` alone; the lexical-loro configs have a single carrier and go with it). `vitest-config-baseline.test.ts` is the file you would GUESS carries the configs and it carries none of them — its reference to them is a computed `import()` that tsc cannot resolve, so its only static contribution is `vitest.shared.ts` itself, and that is redundant. **The LINT half is `pnpm lint:scripts` (#256, CLOSED)** — a separate root script over the same two globs, because `turbo lint` still runs per package and the root is still not a workspace member, so no amount of turbo configuration reaches these files.

Before it, NOTHING type-checked `scripts/`, and the shape of the gap is the thing to remember: `tsconfig.benchmarks.json` names an explicit `files` list, which reached **26 of the 62** `.ts`/`.mjs` files there (9 of the 26 test files) and went stale silently as `scripts/test/` grew — **a config with a `files` list is green precisely when it is ignoring you.** Measured baseline before the fix: a plain `const AA_NORMAL_TEXT: number = 'not a number'` inserted into `scripts/test/token-contrast.test.ts` survived `turbo check --force` (59 tasks, 0 cached), `turbo lint --force` (28 tasks, 0 cached), `check:benchmarks` AND `format:check`.

**Quote the invocation with the number, because it swings by an order of magnitude** — and re-measure rather than citing these, since they track the size of `scripts/`. Extending the root `tsconfig.json` with `types: ["node","vitest/globals"]`: over `scripts/**/*.ts` with `checkJs: false` gave **15 errors in 4 files** when #249 measured it and **20 in 6** at #252; `checkJs: true` **116 in 10** then, **150 in 12** at #252; adding `scripts/**/*.mjs` to `include` **163 in 20** then, **197 in 22** at #252 — which is the shipped configuration, and all 197 were fixed with real JSDoc types rather than suppressions (**9** now-unused `@ts-expect-error` directives deleted, **0** added). **The tsconfig gate is NOT an `any` ban and cannot be one** — `JSON.parse` returns `any` and there are ~38 call sites under `scripts/` — which is why the ban is a LINT concern and lives in #256 below. (Correct one figure it carried: it counted two surviving explicit `any`s, and only ONE was TypeScript. `scripts/lib/jfb-trace-start.ts`'s `entries: any[]` sits inside a template literal — source text this script splices into an upstream JS file — so no gate here has an opinion on it, and a grep that counts it is counting a string.)

**`checkJs` is the half that is easy to drop and it is NOT redundant**, measured by mutation rather than asserted: with `checkJs: false` a drift ACROSS the import boundary is still caught (TypeScript infers a shape for the `.mjs` even unchecked — reinstating the dead `floorMs` option below reddens either way), but a typo INSIDE a helper (`comparison.judgeable` → `judgable` in `formatComparison`) SURVIVES `checkJs: false` and is killed by `checkJs: true`. `scripts/test/scripts-typecheck-coverage.test.ts` therefore asserts the resolved options as well as the covered SET — the set by EXACT equality in both directions, enumerated with `git ls-files --cached --others --exclude-standard` and never a filesystem walk, because `.claude/worktrees/` is a full checkout of every sibling lane and a `length > N` floor cannot detect over-collection.

The gate found one live drift the day it was switched on: `scripts/test/test-durations.test.ts` passed `{ factor: 3, floorMs: 200 }` to `compareDurations` in FOUR places, and `floorMs` is not an option — it is the OLD clamped-denominator design that `minDeltaMs` replaced. All four silently ran at the default 400 ms floor while their source claimed 200. **State its severity honestly: none of the four discriminates 200 from 400** (their growths are 10 000 / 0 / 10 000 / 399 000 ms), so the suite was green before and after and no verdict was ever wrong — what was wrong was the source describing a run it was not making, which is exactly how an untyped boundary hides a drift that DOES matter.

**And `scripts/` is LINTED by `pnpm lint:scripts`, type-aware, which the packages deliberately are not (#256, CLOSED).** Same gap as #252, other tool: `turbo lint` runs the `lint` task per WORKSPACE PACKAGE and the root is not a member, so nothing linted these 66 files. (It was not only the root — **#259, CLOSED**. Of the 28 `lint` scripts, **25 named `src` ALONE**, and all 25 of those packages have a `test/` directory, so most packages' test files were linted by nothing. Type-CHECKED throughout, since the tsconfigs `include: ["src", "test"]`, which is why it was lint-only and silent. The census found more than the issue did: `registry`'s `eslint llui` was a third shape missing its own `test`, `packages/vike/test-types` and `site/pages` were two more directories in the same position, and the 12 `examples/*` apps plus the 6 benchmark apps had NO `lint` script at all — 46 workspace members, 18 linted in full and 28 in part or not at all, with `turbo lint` reporting 28 green tasks over them. Every gap was measured before it was closed: **38 errors over 654 files in 11 packages** in the packages' `test/`, **7 across `examples/`**, and **0** in `site/pages`, `vike/test-types` and all six benchmark apps. `turbo lint` now runs **46** tasks. Three of the 38 were `prefer-const` on a `let` READ between its declaration and its single assignment — which cannot become a `const`, so the rule's own `ignoreReadBeforeAssign` is the fix rather than a suppression; it only RELAXES, so it cannot dirty a currently-clean file. The one real defect the sweep surfaced was in `confirm-dialog.test.ts`: a helper returned a `getState(): Ctx` backed by a `stateRef` nothing ever assigned, so it answered `undefined` while its type promised `Ctx` — dead, uncalled, and deleted. `scripts/test/lint-package-coverage.test.ts` pins SELECTION, COVERAGE and INVOCATION, with **no exemption list**: an 18-entry allowlist of "not linted for now" is the thing that rots, and a package that genuinely must skip a directory says so in `eslint.config.ts`'s `ignores`, which is one fact in one place rather than a silently missing word in one of 46 `package.json` files.) The root script is `eslint --max-warnings=0 'scripts/**/*.ts' 'scripts/**/*.mjs'` — **the quotes are load-bearing**, since `sh` has no `globstar` and an unquoted `scripts/**/*.ts` expands as `scripts/*/*.ts`, silently dropping every top-level script and exiting 0. `eslint.config.ts` gains ONE `files`-scoped block for those globs; everything else in that file is untouched, so `turbo lint` is unchanged (asserted, not assumed — a package source must still resolve no `parserOptions.project`).

**Quote the rule set AND the corpus with the number, and derive each probe from the SHIPPED config rather than writing one** — swap only the preset, hold the corpus (`git checkout main -- scripts/`, 65 files) and every other setting fixed. Doing it the other way produced three wrong figures that all looked plausible. Measured, load ~220 (errors are load-independent; read the wall ratio, not the level): the repo baseline with the block off **2 errors / 2 files / 2.0 s**; `recommendedTypeChecked` **95 / 25 / 5.6 s (2.8x)** — shipped; `strictTypeChecked` **317 / 43 / 5.8 s (2.9x)**. Two decompositions to get right, both of which an earlier draft got wrong: raising `no-explicit-any` to error contributes **ZERO** (the preset already sets it to error and the one site that would fire carried an inline disable — so 95, not "94 plus one"), and the baseline row's **2** versus a **3** from "the block on, preset swapped to `recommended`" is the `files` GLOB, not the preset — measured with `--print-config`, `prefer-const` is scoped to TS EXTENSIONS in the baseline, so a `.ts` under `scripts/` resolves it with the block deleted while a `.mjs` does not, and naming `.mjs` in the glob pulls those files into that TS-scoped baseline under either preset. (Both numbers are right for their config. The first version of this sentence asserted the preset was the cause, stated it with certainty, and was FALSE — a mechanism inferred from one behavioural difference and written specifically to explain a number that had already been wrong once. **Adding `.mjs` to a `files`-scoped block widens the baseline rule set for those files independently of the preset**, which is the reusable half.) Reject `strictTypeChecked` on CONTENT: of its 222 marginal errors 116 are `restrict-template-expressions` (118 total, 2 already firing above) and 73 are `no-non-null-assertion`; the remaining **33** are worse than noise, since the 10 `no-unnecessary-condition` hits are the rule being WRONG about runtime validation (a `schemaVersion !== 1` guard on a `JSON.parse` cast; `cur !== undefined` walking `ts.Node.parent`, whose root parent IS undefined at runtime) — adopting it would put pressure on deleting real defences. All 95 were fixed with real types across **25 files**: **0 `eslint-disable` comments added, 0 rules turned off, 1 removed** (`a11y-audit.ts`'s `no-explicit-any` suppression, replaced by axe-core's own published types through an erased `import type`).

**`any` does not make an assertion vacuous, and saying so is the easy overclaim here** — `expect(undefined).toBe('x')` fails loudly, and a `Record<string, unknown>` seam admits a misspelled key just as happily (both measured). What `any` actually costs is everything DOWNSTREAM: `JSON.parse(...).label.toUpperCase()` compiles, the `unknown` spelling does not, and nothing states the shape a test depends on. Say that, not the stronger thing.

**The `no-unsafe-*` family is why the gate is type-aware, and the `.mjs` half has exactly one working spelling.** In a `.ts` file `JSON.parse(text) as Manifest` is a real AST node and the rule sees the assertion. In a `.mjs` file the JSDoc cast idiom — `const held = /** @type {X} */ (JSON.parse(raw))` — satisfies `tsc` and NOT typescript-eslint: the rule resolves the INNER expression and gets `any`; both spellings of it in `scripts/lib/worktree-lock.mjs` reported `no-unsafe-assignment` while `check:scripts` was green on the same lines. That is the observed BEHAVIOUR, measured in both directions; the CAUSE is deliberately not stated, because nobody has read typescript-eslint's source to confirm it. The obvious explanation — the parser dropping the parentheses the tag hangs off — is an inference, and the `prefer-const` sentence above is what a confidently-asserted inference of exactly this kind cost this batch. What DOES work is `any` -> a DECLARED non-`any`: `/** @type {unknown} */ const parsed = JSON.parse(raw)` on its own line, then the cast. Two related traps in the same family: `Array.isArray` is typed `arg is any[]`, so guarding an `unknown` hands you `any[]` and every read off the loop variable is unchecked (re-declare as `readonly unknown[]` first — an `unknown[]` input is unaffected); and `new Promise(executor)` infers NOTHING from the executor's `resolve` calls, so an inline `async () => new Promise(...)` callback made a generic `withLock`'s `T` unresolved and put an `any` into `process.exit`.

`scripts/test/lint-scripts-coverage.test.ts` pins it in three separable parts, because each can fail alone: SELECTION (the `lint:scripts` globs equal `tsconfig.scripts.json`'s `include`, whose expansion the #252 test already pins to the git enumeration by exact set equality — one walker, borrowed, never a second one); RESOLUTION (every git-enumerated file resolves the type-aware block, is not ignored, and carries the five `no-unsafe-*` rules plus `no-explicit-any` at ERROR — type-aware parsing with the type-aware rules off costs the full 4.1 s and finds 2 errors instead of 95); and INVOCATION (root script, `verify`, and an un-neutered CI step, matched inside a structural step boundary so a COMMENT quoting the run line cannot open the window). It deliberately does NOT call `lintFiles` — that is the honest 5.4 s of really linting all 65 files and is what CI is for; `calculateConfigForFile` answers the same questions in ~1.4 s total. It also fails on any file under `scripts/` whose extension is outside BOTH gates (a `.cjs`, a `.js`, a `.mts`): compiled by nothing and linted by nothing is #252/#256 re-opened one extension over, in the same silent way.

- **`check:docs` TYPE-checks README examples, and until #255 it checked NOTHING.** `scripts/check-readme-examples.mjs` wrote a file-level `// @ts-nocheck` as the SECOND LINE of the synthetic file it compiles, ahead of any statement, which disables ALL semantic checking — so `tsc` reported only PARSE errors. Measured both directions: a README block reading `const x: number = "not a number"` PASSED, `const x: number = = 1` failed. The file's own header claimed the opposite ("with `@ts-nocheck` removed"), so the intended design was in the prose and the reverse was in the code. **State the residue as a NUMBER, because the prose version understates it: with the shipped harness but that one line restored, the whole workspace reports ZERO errors on READMEs carrying five genuine defects.** Two figures reproduce, and both name the README state they were taken against — `packages/*/README.md` at merge-base `3c2802b2`, after `pnpm turbo build --filter='!@llui/site'`, invoked as `node scripts/check-readme-examples.mjs`: **298** for the ORIGINAL harness with only the `@ts-nocheck` dropped, and **161** for the SHIPPED harness. Do not read the gap as 137 errors of stale documentation — it is mostly the harness, and the honest form is an ABLATION of the shipped harness against that same fixed state, one decision per row: root cache instead of the package's own **206**, no `@llui/*` link farm **184**, no relative-import exemption **232**, no `DOC_ONLY_MODULES` **201**, no list-fence dedent **164**, no `vite/client` reference **164**, `strict: false` **162**, no `*.css` ambient **161** (that one is defence for a `.css` import outside an `exports` map and currently costs nothing). **Each row is ONE toggle off the shipped harness, so the rows DO NOT COMPOSE — they are not a ladder and they cannot be summed toward the 298; measuring a combination means measuring that combination.** **`strict: true` is counter-intuitive and correct, but its magnitude is small — do not restate it as a rung.** Under `strict: false` a bare `[]` infers `any[]` rather than `never[]`, so the canonical effect-free `init: () => [state, []]` FAILS where `strict: true` accepts it; decomposed line by line, `strict: false` INVENTS 2 (both at `packages/components/README.md`) and MISSES 1 real (`packages/effects` `TS2366`), the other differences being the same defect reported under a different code. The five defects the gate surfaced are the point: `@llui/test` documented a `ComponentDef` export and a `harness.flush()` that do not exist, `@llui/components` documented an entire `xClasses()` layer that had been DELETED, `@llui/agent`'s `identityResolver` read `req.cookies` off a Web `Request`, `@llui/vike`'s `createOnRenderHtml` examples omitted a REQUIRED `domEnv`, and `show`/`branch` arms were documented returning a `Mountable` where the signature demands a `Renderable`. **ALL THREE ESCAPE HATCHES CAN SILENCE REAL STALENESS, and the narrative form of that is invisible in the rendered page** — measured against a control that fails `TS2305` on a renamed export: a `@doc-setup` DECLARING the renamed symbol makes it pass when the block's own import is dropped (a byte-identical rendered snippet), `@doc-skip` on every block leaves a whole README unchecked, and a `DOC_ONLY_MODULES` entry stubs a module outright. Two of the three are now gated: an entry naming a workspace `@llui/*` package or carrying an empty reason FAILS (they must be RESOLVED, since stubbing one silences exactly the renamed-export drift this gate exists to catch), and an entry the README no longer imports fails as obsolete. `@doc-skip` is deliberately ungated and therefore the one to watch — unbounded, reason-free, invisible in rendered docs, 12 in use. A `@doc-setup` group is dropped for any block that already binds one of its names, so it cannot shadow a real definition, but it CAN stand in for one the README stopped importing. Review these the way you review an allowlist, not as configuration. Two things stay unchecked by design: a RELATIVE import names a file in the reader's project, so its "cannot find module" is dropped (its downstream consequences are not — the binding is `any`); and `noImplicitAny` is off, which is NOT free — an implicit-any BINDING makes every downstream member access on it unchecked, though a contextually-typed callback parameter, which is most of what a README writes, is still checked.

- **A gate that passes only because an EARLIER gate created a directory is green by accident of STEP ORDER, and it is the mirror image of the `.claude/worktrees/` trap above** — there local reddens while CI stays green; here **CI stays green while local reddens**, which is the harder one to attribute because the failure arrives on a developer's machine with no CI run to compare against. The instance: `scripts/test/readme-examples.test.ts`'s `packageRootedFixture` `mkdtemp`s into `packages/<pkg>/node_modules/.cache`, which is gitignored and which pnpm does not create. It was created as a SIDE EFFECT by `check-readme-examples.mjs`, and `ci.yml` runs `pnpm check:docs` at step ~190 and `pnpm test:scripts` at ~287 — so CI was green and `rm -rf packages/*/node_modules/.cache && pnpm test:scripts` failed with `ENOENT ... mkdtemp`, exactly what a fresh worktree gets. Reordering the steps would have reddened `main`. Fix it at the ASSUMPTION (`mkdirSync(dir, { recursive: true })`, which the production script already did at its own equivalent site) — never by pinning the CI order, which preserves the dependency and hides it better. Measured over all 68 files under `scripts/`: this was the ONE site writing into a repo-internal directory it did not create; every other fixture roots in `mkdtempSync(tmpdir())`, and the full suite now passes 248/248 from a genuinely absent `.cache`.
- **`verify` fails FAST, and its step order hides the rest.** `Type check` runs ahead of `Test`, `Test root scripts` and `Smoke-test example bundles`. A run that goes red at `Type check` has told you **nothing** about the suite — do not read it as "only the types are broken". Run the later steps locally before assuming they pass.
- **The Component Gallery's visual gate is REQUIRED in CI and self-bootstrapping (#268).** A screenshot baseline is valid only on the browser build and platform that recorded it, so `examples/component-gallery/test/visual-baselines/manifest.json` records that environment and a run compares only in it. The `Test` step sets `LLUI_VISUAL_REQUIRED: '1'`: a run that cannot compare (no baselines, or a new Playwright image) FAILS instead of falling back to the local determinism check, and every run writes its captures under `LLUI_VISUAL_OUTPUT` as a complete candidate set, which `Upload visual gate output` publishes as the `visual-baselines` artifact on failure. Recording is therefore either `pnpm gallery:visual:update` (Docker, CI's own image on linux/amd64 — an Apple Silicon host emulates it) or committing a reviewed artifact. Bumping `playwright` means bumping the container tag (as before) AND re-recording; `scripts/test/visual-container.test.ts` pins the image, the variables and the upload step.
