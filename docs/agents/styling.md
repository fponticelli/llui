# Styling and the component registry (`registry/`, `@llui/cli`)

_Detail behind the short rules in the root `CLAUDE.md` (Styling & registry). Moved here verbatim so the always-loaded instructions stay small; read this before changing the area it covers._

- **A class string that no build compiles is not tested, however many assertions it has.** `packages/components/src/styles/classes/*` was 62 files of Tailwind recipes with 62 test files asserting `expect(cls).toContain('max-w-lg')`, zero consumers in this repo, and **116 utility occurrences across 55 of those files that emitted NO CSS at all** — every transition instant, every dialog/popover/tooltip unstacked. The suite was green throughout, and `tailwindcss` was not installed anywhere in the repo. The layer is DELETED; recipes now ship as registry source, and `scripts/test/tailwind-classes.test.ts` runs the REAL Tailwind build over every class the registry emits and fails on one that produces no rule. Do not add a class-string layer without that check, and do not weaken the check into a substring assertion.
- **Tailwind v4 namespace names are load-bearing only in `tailwind.css`.** Durations come from `--transition-duration-*`, z-indexes from `--z-index-*`, and spacing from `--spacing-*`; `--duration-*` / `--z-*` / `--space-*` do not generate those utilities. The copied-registry entry maps shared semantic values such as `--llui-duration-fast` and `--llui-z-dialog` into those namespaces. Baseline family CSS reads the `--llui-*` values directly and never enters a Tailwind pipeline. Verify registry namespace changes by compiling them.
- **Registry recipes are shadcn/ui's, ported VERBATIM — do not "simplify" them into LLui inventions.** Measured at a mean 98% class-set match across the 45 components with an upstream counterpart, 38 of them at 100% (`registry/README.md` carries the breakdown); the shortfall is almost entirely classes that CANNOT be ported (Radix positioning vars like `origin-(--radix-…-transform-origin)`, and `cmdk`'s `[&_[cmdk-*]]` selectors). Byte-identical recipes are what make a shadcn theme, screenshot or tutorial still describe what you get. The shared idioms recur on every control: focus is `focus-visible:border-ring ring-[3px] ring-ring/50` (NOT a 2px solid ring); hover is an ALPHA of the base colour (`hover:bg-primary/90`), never a `--primary-hover` token; control borders are `border-input`, not `border-border`; `shadow-xs`, not `shadow-sm`; invalid is `aria-invalid:border-destructive aria-invalid:ring-destructive/20`. The derived tokens in `semantic-tokens.css` exist for the BASELINE stylesheet and are not used by recipes. Note `active:` appears nowhere — shadcn does not use it either, so its absence is parity, not a gap.
- **A recipe that names an attribute its machine never publishes is dead CSS, and `scripts/test/registry-attrs.test.ts` is the only thing that finds it.** This is the registry's most expensive bug class: the class compiles, the part spreads, the type-check passes, and the rule simply never matches. FIVE shipped at once — `scroll-area` styled `data-[orientation=…]` against a machine publishing `data-axis` (the thumb rendered at ZERO pixels); `carousel`'s indicator used `data-[state=active]` against a bare `data-active` (the current dot never highlighted); `calendar` used react-day-picker's `data-[state=…]` throughout (no today marker, no selection fill, no range, no focus ring on any day, under a comment claiming that spelling was "the shape the machine publishes"); `rating-group` styled `data-[highlighted]`/`data-[state=half]` against `data-fill`; `steps` styled `data-[state=complete]` against a `data-status` whose values are `pending|current|completed|error`. A SIXTH was the machine's fault, not the skin's: `menu-machine` published `data-state="highlighted"` while `select`, `combobox`, `listbox`, `tags-input`, the baseline stylesheet AND every registry menu recipe use a bare `data-highlighted`, so every dropdown/context-menu/menubar item had no highlight at all. Three rules for that test: (1) it is ONE-DIRECTION — a recipe naming an attribute nobody emits is always a bug, while a machine publishing an attribute nothing styles is normal; (2) its allowlist is keyed **`file.ts: attr`, never by attribute name alone**, because a bare-name entry switches the check off everywhere — allowing `calendar`'s upstream `data-[state=today]` globally would have silenced the `carousel` bug the test exists to catch, measured; (3) an upstream-parity allowance must name the LLui spelling that carries the same state as `pairedWith`, and the test then requires that spelling to be present too — without it, deleting the working half leaves only the dead upstream spelling and the allowance approves it (measured: the `scroll-area` bug replayed green until the pairing was added). The MACHINE_OF map has its own vacuity test so a new skin cannot silently fall out of coverage.
- **The attribute cross-check has TWO arms, and the second one is about VALUES.** A recipe can name the right attribute and still match nothing, because upstream and LLui spell the same boolean state differently: shadcn writes `data-invalid="true"` / `data-disabled="true"`, and every boolean `data-*` in `@llui/components` is published BARE (`'' | undefined`) — the package-wide convention, used by roughly forty machines. `field.ts` shipped THREE such rules and the NAME arm was green on all of them: the `Field` root's `data-[invalid=true]:text-destructive`, and `group-data-[disabled=true]/field:opacity-50` on both `FieldLabel` and `FieldTitle`. An invalid field never turned red and a disabled one never dimmed, against machines that were publishing the state correctly the whole time. The fix is the documented bind-both pattern (`registry/README.md`), not picking a side. Four rules for the value arm, each measured: (1) `data-part` / `data-scope` are SKIPPED — they name a part, not a state, and a registry component legitimately declares parts of its own (`select-value`, `sidebar-menu-action`); (2) an attribute with a NAME-level allowance is skipped too, because that allowance already says it is not machine state in that file; (3) an OPEN declared type gets NO VERDICT rather than a guess — but "open" no longer means "not spelled inline" (#248, CLOSED, see the next bullet); (4) `VALUE_ALLOWED`'s `pairedWith` is checked against the BARE spelling set, never the attribute-name set — the dead bracketed form contributes its own name, so a name-level pairing would be satisfied by the very rule it is meant to justify.
- **A NAMED type is FOLLOWED to its union, and what the resolver still declines is PINNED (#248, CLOSED).** "No verdict on an open type" is right, but it used to fire on a type that was not open at all — merely named. `meter` declared `'data-state': Signal<MeterThreshold>`, so the value arm was silent while the shipped skin styled `data-[state=critical]` / `data-[state=suboptimal]` against a machine emitting `low`/`optimal`/`high`: the range painted `bg-primary` in every state for a release, NAME arm green throughout (#235). The exposure was **66 declarations / 19 distinct aliases** across `components/` + `patterns/`, `aria-*` included — where a wrong value is an accessibility defect, not merely dead CSS. `scripts/lib/registry-attrs.mjs` now follows a name through the file's own top-level `type X = …` and through RELATIVE imports and named re-exports inside the SAME package, recursively. Spelling all 66 inline (the `ChartParts` idiom) was the other option and it loses on measurement AND on principle: it is ~66 mechanical edits that trade a readable alias for a guard's convenience at every site, and nothing stops the 67th from being an alias again. Four things to keep straight. (1) **It FAILS CLOSED, and that direction is not negotiable** — a wrong verdict here is a build failure for a consumer who did nothing wrong. Declined: a bare/cross-package specifier, a path leaving the package root, a missing file, a GENERIC alias or any reference carrying type ARGUMENTS, a type PARAMETER, an interface/mapped/conditional type, and a cycle. A candidate that resolves to a DIRECTORY is SKIPPED rather than read — that one is not a decline but a fall-through, and it is in this list because omitting it was a CRASH: an extensionless `./sub` made candidate 0 the directory itself, which `existsSync` accepts and `readFileSync` rejects with `EISDIR`, so a guard whose whole contract is to fail CLOSED failed LOUD instead. With the `isFile()` stat it falls through to `sub/index.ts`, the answer TypeScript gives. Latent while nothing under `packages/components/src` imports extensionlessly — and the residue pin below exists precisely to push new declarations through this resolver, so an enumerated decline list has to be TOTAL rather than merely correct about the cases in the tree today. The type-parameter check is the one that is load-bearing on its own rather than redundant: everywhere else a parameter also fails the alias lookup, but a parameter SHADOWING a module-level alias of the same name (`type Scope = …` beside `interface P<Scope extends string>`) would otherwise resolve to a completely different type. (2) **The companion guard is the residue pin** — `UNRESOLVED_ALLOWED` lists every `file.ts: attr` whose declared type NAMES something unfollowable, with a reason, so a NEW aliased declaration the resolver cannot read fails the build instead of silently re-opening the hole at site 67. Today it is two entries: `menu-machine`'s `data-scope` (a genuine type parameter) and `table`'s `data-row-index` (`typeof HEADER_ROW_INDEX`). A plain `string`/`number`/`boolean` is deliberately NOT residue — it is honestly open, and listing 200 of them would drown the pin. Its vacuity check asserts every allowance is still MATCHED, because a reporter that returned `[]` for everything would otherwise pass. (3) **Resolution introduced exactly ONE false-positive shape and it is per-file allowlisted, not generalised away**: a DESCENDANT selector names another machine's state — `field.ts`'s `has-data-[state=checked]` is upstream's checkbox-row highlight, and `checkbox`/`radio-group`/`switch` all publish it, while the value arm resolves `data-state` against the field's own `FormStatus`. Do NOT "fix" that by skipping `has-`/`group-`/`peer-` candidates: `field.ts`'s own `group-data-[disabled=true]/field` bug is exactly that shape, and a faithful mutation confirms the arm judges those pairs today. (4) **The gain is 46 recipe pairs moving from unchecked to checked** — every overlay's `data-state=open|closed`, every drawer/sheet `data-side`, `steps`' four `data-status` values, `rating-group`'s `data-fill`, `image-cropper`'s handles, `slider`/`tabs`/`toolbar`/`resizable` orientation — 45 of them already live, plus the one false positive above.
- **The BASELINE STYLESHEET had a name arm and no value arm, and that asymmetry cost the same thing on the other styling path.** Adding `themeAttrValuesByScope` found TWO live dead rules the day it was written: `[data-scope='menu'][data-part='item'][data-state='highlighted']` and the identical `context-menu` rule, against a `menu-machine` that publishes a BARE `data-highlighted` — while `select` and `combobox`, four rules away in the same file, already used the bare spelling. **The keyboard-highlighted item in a baseline-styled dropdown or context menu had no highlight at all**; only the `:hover` rule beside it worked, so a mouse user saw the component behaving and a keyboard user saw nothing. This is the residue of the machine-side fix for that same bug (the "SIXTH" one two bullets up, where `menu-machine` was changed to publish bare) in the surface that fix did not reach — which is the standing argument for making a check symmetric across BOTH styling paths at the time it is written, rather than adding the second arm a release later. The arm carries its own vacuity assertion (`judged > 20`): without it, an extraction that stopped matching would report a clean sheet. It is keyed per SCOPE (`THEME_VALUE_ALLOWED`), not by bare attribute name — the NAME arm beside it reads `ALLOWED['*: ' + attr]`, a global bare-name key of exactly the shape the registry arm's per-file keying exists to avoid, and per-FILE keying is meaningless in a one-file corpus so per-scope is the analogue. Measured, the inherited star list was skipping 5 of 48 judgeable pairs (`drawer: data-side` x4, `pagination: aria-current=page`) and hiding nothing: the scope-keyed list is EMPTY and the arm still reports 0, so those 5 are now genuinely checked. And note which guard actually terminates alias resolution: `MAX_ALIAS_DEPTH` and the cycle `seen` set are REDUNDANT (either alone is sufficient — dropping `seen` is measured green), so a test named for "recursing forever" pins neither; the depth cap is the only one that also answers a deep ACYCLIC chain.
- **A registry component that upstream ships as ONE export must not be split into two.** `command`'s filter field is one shadcn component — the bordered row, its search glyph and the `<input>`. Ours was `CommandInputWrapper` + a bare `CommandInput`, which made the wrapper something a caller had to remember, and one of two call sites forgot: the searchable-select demo rendered a filter with no border, no padding and no glyph, flush against the top-left of the popover. Upstream cannot be got wrong that way because upstream has nothing to forget. Splitting a component to "expose the pieces" trades a real footgun for flexibility nobody asked for; the class guard and the attribute guard are both blind to it, and only a render shows it.
- **Four systematic translations, and only four (#264 review item 9 added the third, #265 the fourth).** `focus:` → `data-[highlighted]:` on every menu-like surface (dropdown, context menu, menubar, select, combobox, command): Radix moves real DOM focus onto the highlighted item, LLui keeps focus on the CONTENT and tracks the highlight in state (`aria-activedescendant`), so a ported `focus:` would never match. `data-slot=` → `data-part=`. A leftover `data-slot` is dead CSS that can never match — `navigation-menu` shipped with one. And a physical Tailwind utility → its EXACT logical-property equivalent for RTL support (`-left-12`/`-right-12` → `-start-12`/`-end-12`, `pl-`/`pr-` → `ps-`/`pe-`, and so on) — never a substitution to a DIFFERENT value or position (`carousel`'s arrows going from upstream's `-left-12`/`-right-12` to `start-2`/`end-2` was not this: it moved the arrows INSIDE the frame, a different design, not a direction-aware restatement of the same one — reverted to `-start-12`/`-end-12`). And a Radix positioning variable LLui's floating engine ALSO writes → the LLui variable: `max-h-(--radix-…-available-height)` → `max-h-[var(--llui-floating-available-height,calc(100dvh-2rem))]` (published by `attachFloating`'s `size` middleware; the viewport fallback covers the frame before the first measurement). A Radix variable with no LLui equivalent (`--radix-…-transform-origin`) is still dropped, never faked. Everything else stays byte-identical to upstream; do not invent a fifth systematic translation without writing it down here first.
- **Icons come from the Iconify HTTP API by `prefix:name`, and the response is UNTRUSTED MARKUP.** The loader lives in `@llui/components/icon` (`packages/components/src/icon.ts`) — `icon('lucide:star', props?)` names any Iconify glyph, takes a `Signal<string>` for a glyph that follows state (a monotonic request token keeps a slow response for the PREVIOUS name from landing over the next), and the body is fetched at mount, batched to ONE request per prefix per tick. `registry/llui/ui/icons.ts` is the shadcn-shaped surface over it: a FACTORY per glyph (`CheckIcon()`) with the caller's `class` merged through `mergeClass`, nothing else. The reactive name is wired with `registerBinding` + `onMount` rather than `foreign()`, because `foreign` creates its host with `createElement` — an `<svg>` needs the SVG namespace. Three things are load-bearing. (1) The result is a real `<svg>` element — never an `<img>` and never the `iconify-icon` web component, both of which would break every `[&_svg:not([class*='size-'])]:size-4` hook in the recipes silently, exactly the way an un-rewritten `data-slot` does. (2) The body is NEVER assigned to `innerHTML`; every node is REBUILT from an element and attribute allowlist that fails closed, so a `<script>`, an `onload`, an `href` or a `style` in the response is dropped rather than passed through — `registry/test/icons.test.ts` pins each. (3) A FAILURE IS NOT CACHED, only a resolved glyph, so a request lost to a dropped connection is retried by the next mount instead of becoming a blank box for the life of the page. The costs are real and are the accepted price of naming glyphs instead of copying paths: icons are ASYNC (an SSR render emits the sized empty box and the glyph arrives after hydration) and they need the NETWORK (a CSP that does not allow `api.iconify.design` gets the empty box — point `iconConfig.api` at a self-hosted Iconify to remove the third-party dependency). `registry/` gained its own vitest setup for this; before it, nothing in the repo could execute registry source at all.
- **shadcn's components RENDER THEIR OWN ICONS, and porting only the class recipes ships components with nothing to draw.** `SelectTrigger` emits a chevron, `Checkbox` a tick, `DialogClose` an ✕, `BreadcrumbSeparator` a chevron — upstream imports them from `lucide-react`. A recipe-only port leaves every `[&_svg:not([class*='size-'])]:size-4` hook with nothing to hook, which is exactly why the Select rendered as a bare box with a text arrow. `registry/llui/ui/icons.ts` inlines the ten Lucide glyphs shadcn uses and thirteen components render them. Two rules for that file: the glyphs carry NO size class (the recipes size them, and a size here silently beats every recipe — the Tailwind guard enforces it via a CHECKED `RECIPE_FREE` list asserting zero candidates), and a component that renders one must still honour caller children (`children.length > 0 ? children : [Icon()]`) so the default is an affordance, not a cage.
- **`@layer base` in `tailwind.css` (reached through `tokens.css`) carries TWO rules from shadcn's `globals.css`, and both are invisible until you look at a rendered page.** Tailwind v4 defaults a bare `border` to `currentColor`, and shadcn's recipes write plain `border` everywhere (`Card`, `Dialog`, `Popover`, `Select`, the `outline` Button) — without `* { border-color: var(--border) }` they paint a hard BLACK outline. And Tailwind v3's preflight set `button { cursor: pointer }` while **v4 REMOVED it**, so without `button:not(:disabled) { cursor: pointer }` every control on the page shows the default arrow; shadcn's own components never write `cursor-pointer` (only `cursor-default` on menu items, `cursor-not-allowed` on disabled, `cursor-text` on input addons) precisely because it comes from here. Neither is detectable by the class guard, which asks whether a class produces CSS and never whether the page looks right.
- **The components DEMO renders `dist/styles/`, not `src/styles/`, so a source edit is invisible until you rebuild.** `examples/components-demo/src/main.css` imports the BARE SPECIFIER `@llui/components/styles/theme.css`; the package `exports` map sends that to `./dist/styles/`, whose exact CSS artifact set is reconciled by `scripts/publish-component-styles.mjs` during the package build. A `src/styles/*.css` edit therefore describes nothing the running demo shows until `pnpm --filter @llui/components build` — and it fails SILENTLY, with correct source on disk. Two consecutive probes returned a pre-fix value this way. It is NOT a Vite watcher problem: measured and refuted, a sentinel appended to `dist/styles/theme.css` (outside the app root, through the pnpm symlink) produced an HMR update and reached the served CSS within seconds, in both directions. The export hop fully explains it.
- **A `cssRules` walk does not descend into an `@import`ed sheet** — those hang off `CSSImportRule.styleSheet`, not `.cssRules`. This is the SAME trap as the `@layer` one above, one variant out, and it fails in the SILENT direction: a token-pair scan returned ZERO pairs and would have "confirmed" that no exceptions exist. Guard any such scan with an emptiness assertion, or derive the names from source text instead.
- **`scripts/test/token-contrast.test.ts` is the THIRD registry guard, and the only one that measures whether a pair is LEGIBLE (#250).** `tailwind-classes` asks whether a class produces a rule; `registry-attrs` asks whether a selector names an attribute a machine publishes; both are green on a pair nobody can read, and two AA regressions escaped in one session with no component involved — `--destructive-foreground` not inverting (2.767:1), and #241's specificity fix letting a `:root`-only override win in dark mode (6.207:1 -> **3.750:1**). It discovers every app entry stylesheet that transitively reaches a public or semantic token stylesheet by an `@import` walk (today the two demos), compiles each through the REAL Tailwind build (so it reads workspace SOURCE, not the demos' `dist/styles/`), and asserts ≥ 4.5:1 for all eleven surface/foreground pairs in **all six** (preference x OS) cells. Six cells is not thoroughness: regression 2 failed in `os=dark x pref=system` ONLY, and measured clean in the other five. The allowlist is keyed **`file: pair: cell`** with a reason — the discipline `registry-attrs` documents — and it is **CLOSED AT BOTH ENDS**: an entry that no longer describes a sub-AA pair fails as obsolete, and each entry additionally names the ratio it was MEASURED at (`atLeast`) so it cannot approve a value nobody has seen. The floor is not decoration — measured, with the entries in place but no floor, degrading `--muted-foreground` to `oklch(0.93 0 0)` took light-mode `muted` to 1.124:1 and the file still reported 7 passed, which is the exact property the allowlist claims to prevent. Green on day one with ONE exempted PAIR (`muted`, 4.349:1, shadcn's own secondary-text value) spelled as SIX keyed entries — 2 files x 3 light cells, which is what the per-file-per-cell triple key buys. It also asserts that each pair's token RESOLVES: a `var()` naming a token that is absent, **or declared with a non-colour value**, is invalid at computed-value time and falls back to `transparent` (surface) or the inherited ink (foreground) — both of which measure as something plausible, so one `--card: oklch(1 0 0)px` typo left all seven tests green until the surface-opacity / inherited-ink probes were added. ~2 s of test time (4-5 s wall), no timing, no rAF, no network; CI's `verify` already runs it inside the Playwright image via `pnpm test:scripts`, and the whole 11x6x2 matrix re-measured BYTE-IDENTICAL inside that image — **on aarch64, so that evidences linux-vs-macOS and NOT the x64 CI runner, which is unverified** (an amd64 run under emulation could not launch Chromium). The tightest row, `destructive` at 4.570:1, is **two** 8-bit levels from the floor; what makes that defensible is `--force-color-profile=srgb` in playwright's launch args, not the headroom. It measures the CONTRACT, not what a component paints (`button.ts`'s destructive variant uses `text-white` and never reads `--destructive-foreground`). Complements `packages/components/test/styles/token-cascade.browser.test.ts`, which sweeps the same six cells asking which DECLARATION wins — a cascade can be entirely correct and still resolve to 2.767:1.
- **A uniform ~1.00:1 contrast table is the signature of a BROKEN INSTRUMENT, not a finding — and it has TWO unrelated causes.** Measured on one component by two agents independently: (a) parsing a CSS Color 4 string as if it were `rgb()`, and (b) a partial-transition freeze in a hidden tab. Both produce a clean uniform ~1.00. Assert the instrument on a KNOWN pair (`#000` on `#fff` must read 21:1) before trusting any sweep. **But black-on-white ALONE cannot validate the arithmetic**: 0 and 1 are FIXED POINTS of the sRGB transfer function, so replacing the gamma decode with a bare `n / 255` leaves every 21:1 canary reading exactly 21:1 (measured). A known MID-TONE is what catches that — `token-contrast.test.ts` uses `rgb(0 0 0 / 25%)` over white, which is rgb(191,191,191) at 1.838893:1, and 25% rather than 50% because 0.75 x 255 = 191.25 rounds unambiguously where 127.5 does not.
- **CSS Color 4 syntaxes round-trip VERBATIM through BOTH `getComputedStyle()` and `canvas.fillStyle`** (Chromium 147). Legacy sRGB still normalizes (`red` -> `rgb(255, 0, 0)`), but `oklch(...)`, `oklab(...)`, `lab(...)` and `color(display-p3 ...)` come back unchanged from both. A naive `match(/[\d.]+/g)` then reads them as sRGB — near-black for every token. **PAINT the colour and read the pixel back** (`fillRect` + `getImageData`). The trap fires even where nobody wrote oklch: this repo's derived tokens are `color-mix()`, which Chromium resolves TO `oklab()`.
- **The hidden-tab trap has a PLAUSIBLE-LOOKING variant: a PARTIAL transition list.** `transition-[color,box-shadow]` transitions `color` but not `background-color`; in a hidden tab the ink froze at its light value while the fill jumped to dark, the two coincided, and the probe reported a clean **1.000:1 for every chip**. Unlike a frozen-value artifact this does not look broken. Kill transitions outright (`* { transition: none !important }`); never reason about which properties a rule covers. `requestAnimationFrame` also NEVER FIRES in a hidden tab — awaiting one hangs an eval to its timeout.
- **`sr-only` on a `<table>` does not measure 1x1** — table layout treats `width: 1px` as a MINIMUM. Sheet-dependent: 237x1 under the baseline stylesheet, 237x240 under Tailwind's `sr-only` (`ChartTable` measures 129x112 the same way). Clipped, out of flow, harmless — but a probe asserting a 1x1 box fails for the wrong reason.
- **`duration-fast` / `z-dialog` are LIVE in the registry build.** `tailwind.css` maps `--transition-duration-fast` and `--z-index-dialog` to the shared `--llui-duration-fast` / `--llui-z-dialog` values with `@theme inline`; spelling `--duration-*` / `--z-*` still generates no matching utility. The baseline never depends on either Tailwind namespace. A class name's liveness is a property of the mapping that backs it — verify by compiling, never by recognising the name.
- **A source-scanning guard whose needle also matches the PROSE beside it is the two-occurrences trap, one layer out.** A tripwire written `/data-scope/.test(source)` failed on the four mentions in the comment written next to it. It fired LOUD there, which is luck — as an allowlist it would have been SILENT. Parse the module and look for a published property, with a vacuity assertion that the walk finds a control property.
- **A contrast probe must prove BOTH tokens resolve to a colour of their own, and the two halves fail DIFFERENTLY.** An invalid value is IACVT, so it falls back rather than erroring: a bad SURFACE falls back to `transparent` and the probe silently measures whatever is behind it; a bad FOREGROUND falls back to the INHERITED ink, which is a plausible colour on a correct surface and therefore the more convincing lie. Measured: `--card: oklch(1 0 0)px` and the same typo on `--card-foreground` both passed a guard checking only for an ABSENT token. Test the surface by painting it over white AND black and requiring the readings identical (a translucent surface makes the ratio a fiction about its backdrop); test the ink by resolving it under two different inherited inks.
- **Batch an inherited-property probe per PAGE, not per pair.** Writing `wrapper.style.color` invalidates inherited colour for the whole subtree, so set/read/restore per pair forces a full style recalc against the entire compiled stylesheet: measured **10.4 s interleaved vs 2.4 s batched** over the same 11 pairs.
- **Playwright launches with `--force-color-profile=srgb`**, which pins the colour pipeline rather than leaving it display-dependent. That — not a wide numeric margin — is why a contrast reading is portable across machines. The margin at the tightest shipped pair is TWO 8-bit levels, not "several": surface +2 or ink −2 both land below 4.5.
- **Verify interaction states by RENDERING, not by reading CSS — two probes of mine reported the opposite of the truth.** A regex that stopped at the first `}` missed the alpha living inside Tailwind's `@supports (color-mix)` block and reported `hover:bg-primary/90` as identical to the base colour; a `cssRules` scan that never descended into `@layer` reported every hover and disabled rule as absent. Both said "no mouse state" about components that had it. The reliable check is a real hover plus `getComputedStyle` — `lab(100%)` → `lab(96.52%)` is what a working `hover:bg-accent` looks like, and shadcn's default hover really is only a ~3.5% lightness shift.
- **A HIDDEN tab pauses CSS transitions, and `getComputedStyle` there reports the value the property is STUCK at — not what the cascade says.** This is the trap on the other side of the rule above: rendering is the right check, but an automated probe usually runs against a tab whose `document.visibilityState` is `'hidden'`, and every conclusion it draws about an animated property is then wrong in a way that looks like a real bug. Measured: the registry demo's sidebar reported 224px in BOTH states with its `--sidebar-width` custom property and every `data-` attribute updating correctly, which read as "`width` does not apply to this flex item" — inline `width: 48px !important` was ALSO reported as 224px, and `min-w-0`, switching `w-` to `basis-`, and dropping the transition each appeared to fix it. None of it was real; with nothing mid-flight the plain `w-(--sidebar-width)` goes 224px ↔ 48px and `min-w-0` changes nothing. A carousel indicator's `data-active:bg-primary` reported the same shape (attributes swapped, colours frozen at the previous endpoints). **The probe is two lines and settles it: read `document.visibilityState`, and transition a scratch element between two LITERAL colours** (`red` → `blue`, no `var()`, no Tailwind) — in a hidden tab it stays red. Run it before believing any computed-style result about a property carrying a `transition-*` class, and prefer removing the transition class for the duration of a measurement over reasoning about the number you got.
- **`tw-animate-css` is a real dependency, not optional polish.** `animate-in` / `fade-in-0` / `zoom-in-95` / `slide-in-from-*` are NOT Tailwind core; they are the entire enter/exit vocabulary of every shadcn overlay. The registry's `utils` item declares it, `llui init` prints the `@import`, and `scripts/lib/tailwind-compile.mjs` imports it so the guard can resolve those classes — of the 231 distinct classes in shadcn's vocabulary, these 24 were the ONLY ones that did not already compile against LLui's theme.
- **The class extractor must follow a `createVariants({ variants })` SHORTHAND to its module-level const.** `button.ts` and `badge.ts` are written that way, and until `registry-classes.mjs` resolved the identifier their entire variant maps were invisible to the Tailwind guard — while the files still reported plenty of candidates from their base recipe, so the hole was silent rather than obvious. Named `group/<name>` / `peer/<name>` markers emit NO rule and are excluded from the dead-class assertion; they are checked from the REFERENCE side instead (a `group-…/<name>:` with no matching marker is always dead CSS, whereas an unreferenced marker is a legitimate public hook and upstream ships several).
- **`tokens.css` and `theme.css` are independent products and MUST NOT both style the same component parts.** `theme.css` is the ordinary-CSS baseline aggregate: shared semantic light/dark tokens, foundation, family modules, and motion. It imports no Tailwind construct. `tokens.css` is the copied-registry entry: the same semantic values plus the isolated Tailwind v4 mapping and no baseline selector. Unlayered baseline selectors still beat `@layer utilities` if a consumer explicitly combines the two paths. `scripts/test/tailwind-classes.test.ts` compiles registry utilities from `tokens.css` / `tokens-dark.css` and asserts the result contains no `[data-scope]` selector.
- **An exit animation on a node that is never unmounted RESTS AT THE START VALUE, and the class guard cannot see it.** Every shadcn overlay pairs `data-[state=…]:animate-out` with Radix UNMOUNTING the node once the animation ends — `hidden`/`closed` is a state it passes THROUGH, never one it rests in. A part that stays mounted (because nothing can unmount a node after its own exit animation) inverts that: the default `animation-fill-mode: none` releases the animation's hold the instant it finishes, so the element snaps back to the cascade — measured on `navigation-menu`'s indicator, which faded out and returned to `opacity: 1`, fully visible with `data-state="hidden"`. Stacking a static `opacity-0` under the animation fixes the resting state and then plays the exit ONCE AT MOUNT, flashing the element in on every page load, because the `exit` keyframes start from `--tw-enter-opacity` (1). The answer for an always-mounted part is to drive visibility from the CASCADE (`opacity-0` + `data-[state=visible]:opacity-100`) with `transition-opacity` for the motion, keeping upstream's `visible` classes — `animate-in fade-in` composes correctly on top of a cascade that already resolves to `opacity-100`. Both guards are blind to this: the class compiles and the attribute is published, so `tailwind-classes.test.ts` and `registry-attrs.test.ts` are green on an element that is visibly wrong. It was found by rendering the page — and NOT by the first computed-style read of it, which reported `opacity: 1` for the closed state in a hidden tab where the transition was frozen mid-flight (the hidden-tab trap above, in its other direction: strip the `transition-*` class and re-read to get the cascade value).
- **`overlay()` gives the consumer neither the positioner's position nor a backdrop.** `createOverlay` builds `div(opts.positioner, opts.content())` itself, and the part bag it spreads carries only `data-*` — nothing positions it. The class for that node now arrives through `positionerClass` (`utils/overlay-engine.ts:positionerProps`, threaded through all ten `overlay()` exporters); the consumer supplies `fixed inset-0` and the z-index, and renders the backdrop themselves INSIDE `content()` (hence `absolute inset-0`, not `fixed`). Both were invisible for as long as the baseline stylesheet was the only styling path, because it does all of it in CSS. `positionerProps` returns its input UNCHANGED when no class is given, so every existing call site keeps its exact props object; `test/components/overlay-positioner-class.test.ts` pins that identity and the no-`class`-attribute default in both directions.
- **Shared values are plain CSS; only registry mappings go through `@theme inline`.** `semantic-tokens.css` / `semantic-tokens-dark.css` own shadcn base colours and the `--llui-*` radius, shadow, duration, z-index, spacing, focus, disabled, and animation conventions. Baseline family modules consume those names directly. `tailwind.css` independently maps them to Tailwind v4's `--color-*`, `--radius-*`, `--shadow-*`, `--transition-duration-*`, `--z-index-*`, and `--animate-*` namespaces. Consequently `theme.css` requires no Tailwind install or preprocessing; `tokens.css` remains explicitly Tailwind v4.
- **"Pastes in VERBATIM" was false, and the corrected claim is "the `:root` half pastes in; the dark half needs one find-and-replace, plus a twin block if you support `'system'`."** Two independent defects made the advertised shadcn workflow not work, both measured in Chromium across all six (preference x OS) cells and both now closed. (1) **#241, SPECIFICITY.** The media guard was `:root:not([data-theme='light']):not(.light)` — **(0,3,0)**, because `:not()` takes its argument's specificity and two of them stack — while every consumer override shape (`:root`, `.dark`, `[data-theme='dark']`) is **(0,1,0)**. On a dark OS the library's own block therefore outranked the consumer's for EVERY preference and regardless of source order, INCLUDING an explicit `'dark'` where the consumer's selector matches perfectly well and still loses. It is now `:root:where(:not(…)):where(:not(…))` — (0,1,0), so source order decides. **Do not wrap `:root` itself**: `:where(:root)` is (0,0,0), loses to `semantic-tokens.css`'s own `:root`, and breaks dark mode outright while every override assertion stays green. (2) **#242, the `.dark` class.** Nothing in `@llui/components` writes it and nothing will: `.dark` names a RESOLVED theme, so maintaining it in `applyTheme` reintroduces the JS `prefers-color-scheme` resolve #233 removed, and a class that goes STALE on an OS flip does not merely fail to help — it SUPPRESSES the media query that was correct with no JS (measured, preference on `'system'`: stale `.dark` renders dark on a light OS, stale `.light` renders light on a dark one). The selector STAYS in the stylesheet because `next-themes`/shadcn tooling set the class themselves and a generator-verbatim block then wins in every cell; dropping it would take dark mode away from those consumers. The residue is structural and no CSS change can remove it: under `'system'` on a dark OS there is no attribute and no class, so NOTHING a consumer can select on is present — the twin block under the media guard stays the documented answer for that one cell. **Lowering the guard has a consequence to state to consumers**: a `:root`-only override now reaches dark mode in every cell, where before it leaked on a light OS and was overruled on a dark one. `components-demo` overrode `--destructive` in `:root` and relied on being overruled; after the fix the light red sat under the library's dark near-black foreground at **3.750:1**, below AA, until the dark twin listed it. `packages/components/test/styles/token-cascade.test.ts` pins the specificity RELATIONSHIP (a parser, self-checked against hand-computed values — a string assertion on the selector cannot see any of this) and `token-cascade.browser.test.ts` measures the real six-cell cascade in Chromium.
- **Derived interaction tokens are `color-mix()` toward `--foreground`, never a second palette.** `--primary-hover`, `--accent-strong`, `--border-hover`, `--primary-soft-foreground` and `--destructive-hover` are LLui additions the baseline sheet needs and shadcn expresses per-component. Mixing toward `--foreground` makes the SAME expression darken in light mode and lighten in dark, so they need no `.dark` override and are defined once, OUTSIDE the blocks a theme generator overwrites. Do not restate them in a dark block; a generator that emits them is emitting noise.
- **Registry source is TypeScript that nothing in the repo would otherwise compile.** `registry/` is a private workspace member with its own `tsconfig.json` (whose `@/lib/*` paths mirror what `llui add` rewrites to, so the source is checked in the shape it is authored) and `pnpm check:registry` runs in `verify` and in CI. That check found two real defects the day it was added — `interface X extends ElProps` silently DROPS `ElProps`'s index signature (so `props.class` stops existing and every spread `data-*` key errors; use an intersection), and `mergeClass`'s override parameter must be `unknown` rather than `AttrValue` because it is destructured out of an index signature that also admits event handlers.
- **`mergeClass` exists because `cn` alone corrupts a reactive class.** `class` is `AttrValue = Reactive<string | …>`, so a caller may legitimately pass `state.at('open').map(…)`; handing that handle to `cn()` stringifies it to `"[object Object]"` — a silently stuck attribute, the exact failure `applyProp` guards against for raw props. Every registry component routes `class` through `mergeClass`, which maps the signal instead. Note also that `cn` is NOT `cx` from `@llui/components/styles`: `cx` concatenates, so a caller's `p-2` loses to a recipe's `p-4` by source order.
- **A recipe the class extractor cannot see is a recipe that can quietly die.** `scripts/lib/registry-classes.mjs` reads recipes from named positions only — `cn` / `mergeClass` / `classPart` / `classPartWithDefaults` arguments, and `createVariants`'s `base` / `variants` / `compoundVariants[].class`. That is deliberate (a liberal scan of every string literal would flag `'button'` and `'horizontal'` and fail for the wrong reason), and it is why `classPart` was hoisted out of three per-file copies into one shared seam: the per-file version was a position the extractor did not name, and three components' recipes were invisible. A template literal contributes its STATIC text only — an interpolated span is unknowable — so prefer `createVariants` for a conditional recipe, which is read in full. Both facts are enforced by a vacuity test asserting every `ui/` file yields at least one candidate.
  - **A recipe passed BY IDENTIFIER at one of those positions is now RESOLVED, never silently skipped (#264 item F2).** `const TABLE_CONTAINER_CLASSES = '…'; … mergeClass(TABLE_CONTAINER_CLASSES, viewportClassName)` used to reach the extractor's string-reader as a bare `Identifier`, which no branch handled — silently contributing zero candidates, so a dead class hidden inside a hoisted recipe const compiled clean (M1 in the #264 review's mutation table). `stringConsts` (the string-typed sibling of the pre-existing `objectConsts` map that already followed a `createVariants({ variants })` shorthand to its object) now resolves a module-level `const NAME = '…'`/template literal by name at every recipe position. The resolution is SCOPE-AWARE: an identifier bound by an enclosing function parameter or a local/destructured variable (`mergeClass(recipe, className)` inside `classPart`'s own definition, where both are the helper's OWN parameters) is a genuinely dynamic, caller-provided value and is skipped exactly as before; an identifier bound by an `import` is resolved and checked in ITS OWN file, not here, so it is also skipped (a missed check in this one file at worst, never a false failure); `classPart`/`classPartWithDefaults`'s own FIRST argument (the element tag, e.g. `div`) is skipped structurally, never treated as an unresolved recipe. Anything else reaching a recipe position as a bare identifier — a typo, or a recipe helper this file does not know how to follow — now **FAILS LOUDLY** (throws) rather than silently reporting zero candidates, because a silently-skipped identifier is exactly how the hoisted recipe above went unchecked.
  - **The `*Recipe`-suffixed fallback (for a recipe forwarded through a bespoke local helper the extractor cannot trace at all, e.g. `pagination.ts`'s `paginationPreviousRecipe`/`paginationNextRecipe`, whose parameter flows into `cn(…)` as a locally-bound identifier) is now case-INSENSITIVE** (`/recipe$/i`, was `.endsWith('Recipe')`) — the case-sensitive version is exactly what let `TABLE_CONTAINER_CLASSES` (SCREAMING_SNAKE_CASE, ending `CLASSES` not `Recipe`) evade it; general `stringConsts` resolution by NAME reference (above) is what actually covers that shape now, so the naming-convention fallback stays narrowly scoped to `Recipe` rather than growing a second convention.
- **The state-driven styling idiom is `data-*`, not a computed class.** Every `connect()` part bag already emits `data-state` / `data-disabled` / `data-orientation` / `data-side` (624 `data-part`, 124 `data-state` across the package) and **no `connect()` emits a `class`** — which is what makes a skin layer purely additive and unable to regress focus, dismissal or ARIA. Write `data-[state=open]:bg-muted` in the recipe. The alternative reads state in the view and hits `operator-on-signal`, which is a build error by design.
- **A state attribute styled on the WRONG PART compiles, passes `registry-attrs`, and paints nothing (#266).** `registry-attrs.test.ts` checks that a recipe's `data-*` names and values are ones the machine publishes — not that it publishes them ON THAT PART. Three specialized-tools skins shipped dead state rules: signature-pad's `data-drawing`/`data-readonly` and image-cropper's `data-dragging` were written as a bare `data-x:` on a CHILD part, but the machine publishes them on the root; floating-panel read its root through an unnamed `group`. Read root-published state from a child through a NAMED group (`group/signature-pad` on the root, `group-data-drawing/signature-pad:` on the child); an unnamed `group-*` variant matches ANY ancestor carrying `group`, including a consumer's own wrapper. Only a live render catches it.
- **`outline-none` silently cancels a later `outline-2`.** Tailwind v4's `outline-none` sets `--tw-outline-style: none`, and `outline-<n>` only sets the width and READS that variable, so `outline-none … forced-colors:outline-2 forced-colors:outline-[Highlight]` computes `outline-style: none` under forced colors. Spell `outline-solid` next to it. Most buttons carry `outline-none` through `buttonVariants`, so any forced-colors outline on a button needs it (#266: image-cropper crop box, calendar range day).
- **A `buttonVariants` SIZE survives `size-auto`.** shadcn's calendar day button is `size="icon"`; porting it with the default size kept `px-4`, which `size-auto` does not undo, so every day grew to ~50px min-content and the `w-fit` calendar stretched past `--cell-size`. When porting `<Button size=…>`, port the size too (#266).
- **Specialized-tools renderers are VIEW code and must pass the framework lint rules.** `examples/baseline-css` runs no Vite plugin, so nothing would lint the baseline renderer; `specialized-tools-baseline-renderer.test.ts` runs `lintSignalSource` over both renderers directly. A finding in the registry renderer is a 500 in the live-render fixture, which used to time out every registry case; the fixture now fails fast and names the module.
