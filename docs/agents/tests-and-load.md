# Tests, load and timeouts

_Detail behind the short rules in the root `CLAUDE.md` (Tests, load and timeouts). Moved here so the always-loaded instructions stay small; read this before changing the area it covers._

## Budgets and load

The workspace `testTimeout` is 30 s (#180) and `hookTimeout` 60 s, both set once in `vitest.shared.ts` (whose header records how they were measured). The 30 s budget cost the repo its accidental performance canary — the old 5 s default, which only ever fired on a saturated machine where it could not tell a regression from contention. **No gate replaces it, deliberately:** a per-file duration baseline was built and later removed because maintaining it cost more than the rare regression it could resolve. So a test that silently gets slower is caught by nobody; when one approaches its budget, the fix is a cheaper test, never a bigger number.

**The budgets only bind a config that actually REACHES `vitest.shared.ts`, and one did not (#249).** `vitest.scripts.config.ts` — the root config behind `pnpm test:scripts`, a CI step of its own — defined itself standalone, so `scripts/test/**` ran on vitest's stock **5 s** `testTimeout` while every other suite ran on 30 s. Invisible by construction: each config is a separate module, `test:scripts` is green on a quiet machine, and it only bites under load, where a red reads as a flake rather than as a misconfiguration (two lanes in one batch hit it and both re-ran). Measured on 18 cores: `registry-attrs.test.ts`'s heaviest case 710 ms quiet → 2.77 s at load ~750, `tailwind-classes.test.ts` (a real Tailwind build) 684 ms → 3.59 s — 1.4x margin against 5 s, 8.4x against 30 s. `scripts/test/vitest-config-baseline.test.ts` now gates the config SET rather than that one file: every config must resolve the shared budgets (allowlisted per FILE **and** FIELD — a bare-field key excuses every config in the repo, measured), the scripts config must discover only `scripts/test/**`, and no config may carry a discovery glob whose directory does not exist. That last one is the general form of the trap: **`mergeConfig` CONCATENATES `test.include`**, so the obvious spelling of this fix leaves the shared `test/**/*.test.ts` glob in place beside the new one — harmless today, silently live the day someone adds a root `test/`. Spread instead (`{ ...shared, test: { ...shared.test, include } }`), as `packages/lexical-loro/vitest.stress.config.ts` already does.

**A load TRANSIENT is a different hazard from load, and the two want opposite fixes (#246).** Two more gates degrade under parallel load, by different mechanisms, and neither is answered by a bigger number. (1) `@llui/site`'s `documents every symbol exported by every public entry point` measured **1.0 s quiet and 32.8 s — a FAILURE against the 30 s budget — at load ~350**, i.e. a 33x load factor eating 30x of headroom. The cost is a FIXTURE, not an assertion: `ts.createProgram` parses 1280 files to resolve 182 entry points and the per-package export walk is under a millisecond, so the program moved into `beforeAll` (budgeted by the 60 s `hookTimeout`, sized for exactly this kind of unavoidable floor) and the assertion split into one `it` per package. Measured after, at the harsher load ~580: fixture 26.6 s of a 60 s hook, worst test 2.47 s, suite green. **That has a cost worth knowing generally: work moved into a hook leaves the TESTS without leaving the machine.** At identical load this file's tests went from 6987 ms to 1247 ms while its wall time stayed ~6.8 s, so a fast test is not evidence that its fixture stayed cheap. Trimming the program is NOT the lever — `types: []` / `noLib` / both give a bit-identical export set and no reliable saving, and interleaved on a loaded machine the four variants ranged 591 ms to 8529 ms with the order of their medians unstable. (2) `@llui/lexical-loro`'s `projects in sub-quadratic time` is a wall-clock RATIO, not a timeout, so no budget applies at all — and **the observed noise exceeds the signal**: quadratic growth for its 4x size step is 16.0 and the flake has been seen at 16.47 and 29.53, so no threshold both tolerates the noise and rejects a quadratic. The mechanism is a burst, not saturation: under SUSTAINED load ~740 the ratio was min 3.07 / p50 4.07 / max 6.19 (0 of 8 over 12), because a steady slowdown scales both windows and cancels, while a burst landing in one window does not — and the large window is 4x longer, so the error is always UPWARD. Four cheaper estimators were measured in the same trials and all rejected: `process.cpuUsage()` (helped one tail, hurt another, read 19.20 in the flaking trial), equal-length windows (gain inside the noise, and doubles the test's cost), best-of-N (structurally wrong — the minimum lands on the DENOMINATOR too; max 16.35/37.39), and INTERLEAVING the two sizes (the most promising, by far the worst: p50 7.70, p90 40.30, 5 of 14 over 12, because alternating two working sets destroys each size's cache locality). **The estimator cannot be fixed; the SIZES can, and that is what shipped.** `{ retry: 2 }` looked free and is REJECTED on numbers: measured against a faithful quadratic mutant (`out.sort(...)` replaced by an insertion sort with identical output), 16 trials each at load ~220, healthy goes over 12 in **5 of 16** runs and the quadratic comes in UNDER 12 in **5 of 16** — a coin flip in BOTH directions — so retry cuts false reds to ~3% while raising MISSES from 31% to ~67%, buying quiet by more than doubling the thing the test exists to prevent. **Never read a perf-ratio flake as one-directional, and never measure only the healthy arm**: the same transient that reddens healthy code also greens a real regression, retry looks free until the mutant's distribution is measured, and the shipped 500/2000 configuration was missing a genuine quadratic **half the time** (12/24 under harsh bursts) while its comment claimed a 16x signal. The fix is BIGGER SIZES: at 500/2000 the projection's O(n) Loro reads still dominate the sort so the mutant medians ~13, while **1000/4000 improves BOTH directions** — false red 21% → 12.5%, miss **50% → 6%** — for **~6x** the wall time (0.33 s steady / 0.60 s harsh → 3.51 s p50 / 6.97 s max), i.e. headroom against the 30 s budget falling from ~10x to ~3–4x. Two methodology rules came out of it. **Measure THROUGH the shipped test, never a replica** — a standalone `tsx` harness copying `project()` line for line produced a plausible distribution matching the old numbers and was wrong, because `tsx` runs ~2x slower than vitest's build and compresses the quadratic signal back into the Loro-read floor. And **a ratio breaks on TRANSIENTS, not on load**: at sustained saturation it was 0 of 12 and 0 of 20 over 12, because a steady slowdown scales both windows and cancels.

**Three "load timeouts" in the #267/#268 batch were not load, and the fix for each was a root cause, not a number (#268).** Read a timeout that only fires under a parallel run as a question about WHERE the cost lands, and measure before touching a budget.

- **`examples/component-gallery` `dev-server.browser` — a RACE, not slowness.** The shell's dev server and the two path documents' own Vite servers all defaulted `cacheDir` to the package's `node_modules/.vite`, so three dependency optimizers shared ONE `deps/_metadata.json`, each re-optimizing for its own dependency set and overwriting the others' browser hash. A document's in-flight dependency requests then came back `504 Outdated Optimize Dep`, it settled `error`, and the test — which waited for `ready` only — burned a 150 s wait under a 330 s test timeout. Load only widened the race; with a cold cache it failed alone. Fixed with one cache per build (`CACHE_DIRS` in `gallery.config.ts`) and a wait that accepts either settled status and then REQUIRES `ready`: ~4 s cold, back on the 30 s workspace budget with both overrides deleted. A wait for the happy state only is how an error becomes a timeout.
- **`packages/cli` `presentation-scenarios-boundaries` "node budget" — work in the wrong place.** Each budget's boundary was binary-searched in the `describe` BODY (collection time: unbudgeted — 16 s of the file's 28 s, quiet), and the one test then compiled, JSON-round-tripped AND clone-round-tripped a ~288k-node family (3.6 s quiet; 32 s under a parallel `turbo test`). The search and the compile are now a `beforeAll` fixture, the three round trips three tests (worst 1.25 s), and the search GALLOPS down from the budget before bisecting (the boundaries sit a few units under it) — the file went 28 s → 19 s with every assertion unchanged.
- **`registry` `navigation-data-live-demos` charts test — a cold compile billed to whichever test came first.** The file boots two demo apps on Vite DEV servers; the first navigation to each compiles the whole app on demand (hundreds of modules through the LLui compiler), and that landed inside the charts test (3.6 s quiet, past 30 s at load ~6 on 4 CPUs). The fixture now warms both demos in `beforeAll`; the charts test measures 1.0 s. The same caveat as #246 applies: the cost left the test, not the machine.

**Browser suites BUILD their fixture once and serve it static — never a per-file Vite dev server (loose-d, after #268).** The #268 charts fix above warmed the dev servers and the test still timed out under load, because a warm-up removes only the first of three costs a dev-server-backed suite bills to its tests. Measured at ambient load ~20 on 4 CPUs: (1) the on-demand compile of the first page (7.3-9.0 s for a demo app, 2.2-3.2 s for a menus fixture — the ContextMenu virtual-pointer test paid 5.3 s / 3.2 s of it); (2) per-page module fan-out, since every test opens a fresh context and re-fetches the unbundled graph (218 requests / ~1.7 s per `components-demo` page, 259 / ~1.6-2.0 s for `registry-demo`, 107-134 / 0.4-0.7 s per fixture page — per test, and a toast test opens 18); and (3) ONE dependency-optimizer cache per root, the gallery race again: every suite serving the same example or the same `test/browser` root from a concurrent worker shares its `node_modules/.vite/deps/_metadata.json`, a concurrent run of four of these files rewrote it between two config-hash families four times in 3 s, and a dependency discovered mid-run re-optimizes and force-reloads open pages. `scripts/lib/prebuilt-fixture.mjs` builds the needed HTML entries in `beforeAll` (the root's own `vite.config`, `mode: 'development'`, unminified, a private temp `outDir` AND `cacheDir`) and serves the output on a loopback port, so a page is one document plus its bundles and there is no optimizer to race; a fixture whose hooks are assigned synchronously is ASSERTED ready right after `goto` (naming the page's own error) instead of waited for. All 18 such suites in `@llui/components` and `registry/` use it. Measured interleaved A/B, the four named files run concurrently with 8 busy loops on the same 4 CPUs (load ~18-21): `menus-overlays-live-render` 607.9 s with 16/33 tests failing at 30 s, and 205.7 s with 1 failing → 85.5 s / 66.5 s with none (ContextMenu virtual pointer 24.1 s / 30.1 s-FAIL and 21.5 s / 6.9 s → 1.8 s / 0.4 s and 1.1 s / 0.4 s); `navigation-data-live-demos` beforeAll failed (14 not run), then 32.8 s with 1 failing → 13.6 s / 12.3 s (charts test 2.8 s → ~1.0 s); `forced-colors-chart-series` 42.3 s / 36.1 s → 19.1 s / 9.8 s; `overlay-presence-motion` 23.7 s / 23.1 s → 13.4 s / 10.5 s. The #246 caveat applies in full: the build is hook time, billed to no test. A flip-removed mutation of `packages/interactions/src/floating.ts` still reddens the popover flip test on both paths through the prebuilt fixture, so a suite that aliases `@llui/*` to source still builds live source (the four registry suites that deliberately resolve built `dist/` — toast, both menus-direction files, the baseline NavigationMenu/Menubar file — still do, exactly as their dev servers did). The Component Gallery's `dev-server.browser` test is the one legitimate dev-server suite (the dev server is what it tests); it now warms both documents in `beforeAll` — 21.0 s of its 30 s budget under the same load → 3.8 s.

**A sleep-then-read across a Playwright round trip is a race against the page, not a wait.** `navigation-data-live-demos`' rapid-cancellation test slept 40 ms in the test process and then read `data-state`, which under load outlived the whole exit animation (`expected 'closed' to be 'closing'`). It now records the exit IN-PAGE from the interrupting click to `closed` with a `MutationObserver`, timed on the page's own clock (`closedAfterMs >= 40`), the same shape as #268's dialog presence fix. A 5 ms exit still fails it (measured 5-10.5 ms against the 40 ms floor); a zero-duration exit fails the in-page retention check.

## No test retries (loose-h)

**No test in this repository retries, and `scripts/test/no-test-retry.test.ts` keeps it that way.** Vitest's `retry` re-runs a failed test and reports it green if any attempt passes, so it cannot tell a load transient from a race and never says which it absorbed. Five sites carried one (`@llui/agent-e2e` and `@llui/devmode-annotate` package-wide, two tests in `@llui/agent`'s `client/integration.test.ts`, both describes of `@llui/mcp`'s `playwright-e2e.test.ts`, and `vite-plugin`'s dirWatcher test), all justified the same way: "timing-sensitive under full-repo parallel load; a deterministic test passes first try". That sentence is unverifiable while retry is on. Taken off and run under measured load (sibling lanes plus 6–16 busy loops on 4 CPUs):

- **`devmode-annotate` "does not close/persist when the modal is closed" failed 10 of 10 runs** (load 3.7–23.9) — and alone, unloaded. It was never load. Every test removed its HUD's element in `afterEach` without `destroy()`, so the previous test's HUD stayed live (document `keydown`, console patch, debounced persist), and a PRODUCT bug let it coexist with its successor: `mountAnnotateHud`'s singleton guard finds the HUD by element, so a detached-but-live HUD was invisible to it and both mirrored into ONE localStorage key. Escape closed the orphan's invisible modal and persisted its state over the live HUD's. Retry hid it because the first attempt's Escape had already closed the orphan. Fixed twice, independently: the mount now reclaims a detached HUD (`liveHud` in `src/index.ts`, regression tests in `mount-reentrancy.test.ts` — removing the reclaim reddens them), and the suites tear down with `destroyMountedHud()` (`test/support/hud-teardown.ts`).
- **An I/O wait that passed only by test ORDER.** `install.test.ts`'s keyboard-trigger test waited one `setTimeout(0)` for a dynamic `import()`; it passed because the test above had warmed the module cache, and run alone (`-t "keyboard trigger"`) it failed every time. It now awaits the memoized `activate()` promise the trigger chained `open()` onto. Its sibling `dispose()` test was VACUOUS alone: with `dispose` mutated to a no-op the old test still passed (the import had not landed within the tick); it now asserts the trigger's synchronous `preventDefault()` instead, and the same mutant reddens it.
- **Sleeps and private deadlines standing in for protocol events that exist.** The agent server answers every `hello` with `hello-ack` in the same synchronous step that records it (`PairingRegistry.dispatch`), so `integration.test.ts` and the e2e `mintAndPair` await the ack and then make ONE request, where they used to poll `describe`/`connect_session` against private 10 s deadlines. The e2e host records every server frame in-page (`__lluiE2eFrames`, listener attached before the client's, same dispatch), so the `wait_for_change` tests wait for the `watch` frame instead of sleeping 100 ms: with the server's `watch` send delayed by 300 ms, the old tests failed 2 of 2 (`expected 'timeout' to be 'changed'`) and the new ones passed. The MCP Playwright harness waits for the relay's own `onopen` console line instead of `delay(1500)`: with `/__llui_mcp_status` delayed 2 s the old harness failed 3 tests (`RelayUnavailableError`) and the new one passed 11 of 11; its error counters were snapshots taken at the end of that delay and are now live. Playwright waits inside a test take the REST of the test's budget (`remainingBudget`, from `reportingDeadline` in `scripts/lib/wait-until.mjs`) so they fail named, before vitest's anonymous timeout.
- **Shared state.** `mcp-watch.test.ts` wrote the real workspace marker (`node_modules/.cache/llui-mcp/active.json`), shared with a developer's `llui-mcp` and any other run from the checkout; it now gets a private `LLUI_MCP_STATE_DIR` per test (#85's mechanism), and its dirWatcher wait is `waitUntil` on the test budget instead of an 8 s literal (whose only stated justification was the retry arithmetic). A harness that fails PARTWAY must still release what it started: the MCP harness tracks everything it launched and `afterAll` closes it even when `beforeAll` timed out — with the relay blocked, the run now fails in 2 x 60 s hook timeouts and exits.

After, without retry: devmode-annotate 20/20 (load 25.7–45.6) plus 5/5 with `--sequence.shuffle`, agent-e2e 20/20 (25.7–46.9), agent integration 20/20 (25.7–46.5), mcp Playwright 20/20 twice (29.4–43.2 and, final code, 19.1–26.0), mcp-watch 20/20 (43.0–46.9). Three sites (agent integration, mcp Playwright, mcp-watch) never failed before the fix either — 35, 18 and 35 loaded runs up to load ~30 — so for them the change is the removal of the fixed waits above, each backed by a mutation or latency injection rather than by a red run.

The guard has three layers: a TypeScript PARSE of every file vitest loads as test code (test files, support files, configs, `vitest.shared.ts`, `scripts/`, `@llui/agent-e2e`) for any `retry` property or `.retry =` assignment — a comment or string mentioning `retry: 2` is not a finding, nor is `@llui/effects`' `retry()`; `--retry` in any package script or workflow step; and, in `vitest-config-baseline.test.ts`, the RESOLVED value of `test.retry` in every config and inline project, which catches a computed or merged-in value the parse cannot see (measured: `...Object.fromEntries([['re' + 'try', 2]])` survives the parse and is caught there). Its allowlist is keyed by file, closed at both ends, and empty.

`scripts/lib/wait-until.mjs` (formerly `packages/vite-plugin/test/wait-until.ts`) is the one polling helper. Prefer awaiting an EVENT where the protocol has one; poll a condition only where it does not; use a duration only for a NEGATIVE assertion (`settle`). A fixed tick in front of a positive assertion is deterministic only while every remaining step of the awaited work is a microtask — `overlay.test.ts`'s 60 ms-against-a-30 ms-timer fade check stays because two timers in one process keep their expiry order under any load, and the timing IS the property there.

**A retained EXIT is a property of its start, and the page's clock owns it (loose-h2).** `navigation-data-live-render.browser.test.ts`'s "retains the accordion/collapsible closing case visibly" mounted the scenarios in one Playwright round trip and read the `closing` content's height in the next. Both skins run a 0.2 s `accordion-up` animation on `[data-state="closing"]` that collapses `block-size` to 0, and `exitCompletion` settles the item to `closed` on its `animationend` — so the read raced the animation. Measured at load 16–22 over 27 runs, it failed 2 times in BOTH predicted ways: the read landed at the end of the collapse (`accordion: expected 0 to be greater than 0`), and after the exit had completed (`Missing [data-state="closing"] for component:accordion`). The retention snapshot is now taken IN-PAGE, synchronously after the mount call (no frame can pass, so the animation is at its first keyframe by construction). The exit's END is no longer bounded by wall-clock time at all: an interim version asserted it ended no earlier than the computed `animation-duration`, which caught a "settle 50 ms after mount" mutant only while that timer beat the 200 ms animation — a probability that falls under load. The test now takes the animation's clock away from the browser through the Web Animations API (`pause()`, hold, `finish()`, and assert `closed` inside that `animationend` dispatch), which catches immediate, 50 ms, 5 s and never-completing mutants deterministically (10/10 each at load 17–19; healthy 40/40 at load 15–37). The method and its mutant table live in `docs/agents/verification.md` (retained exits); apply it to any test of an exit that is retained until its own animation ends.

**A fixture is not always the right home: when the cost is PER ITEM, split the item into its own test instead (q3).** `@llui/site`'s docs-integrity link check (#269) carried the whole corpus in one test: ~5.5 s of remark-parse + remark-gfm over 97 documents (the ~1.4 MB generated `site/content/api/components.md` alone ~1.5 s), and it paid the parse TWICE for every anchor target — once for links, again for heading ids. Measured interleaved on 4 CPUs: 6.7-7.4 s quiet, and at load ~25-47 (28 busy loops plus sibling lanes) 57-140 s — a failure every time. Each document is now parsed once (`parseDoc` in `site/test/support/doc-links.ts`: links read off the mdast, heading ids derived lazily from the SAME mdast through remark-rehype + rehype-slug; parity asserted against the old two-parse functions on all 192 tracked Markdown files), and the check is one `it` per file that parses its own document through a shared cache. The #246 shape — parse everything in `beforeAll` — was measured and REJECTED: the hook took 42-46 s of its 60 s budget at load ~25-31, because the corpus is still one bill, whereas per file the worst test (`packages/cli/README.md`, which anchors into the API page and so pays its first parse) measured 1.8-2.0 s quiet and 14.8-15.2 s at the same load. The six content mutants of the check (broken page link, broken anchor, broken README path, manual count, unknown gallery entry, removed API heading) redden it before and after; the last now reddens exactly the three files that anchor to the removed heading.
