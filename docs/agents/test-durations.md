# Test durations and load

_Detail behind the short rules in the root `CLAUDE.md` (Test durations). Moved here verbatim so the always-loaded instructions stay small; read this before changing the area it covers._

## Test durations (#193)

The workspace `testTimeout` is 30 s (#180), which cost the repo its accidental performance canary — the old 5 s default. The replacement is a per-file duration BASELINE, not a bigger/smaller timeout: `LLUI_TEST_DURATIONS=<dir>` makes every package emit vitest's stock `json` report, and `scripts/check-test-durations.mjs` folds those into per-file totals and compares them against `test-durations.baseline.json` **after dividing out a same-run load factor** (the median of all files' current/baseline ratios). A uniformly slower machine reports nothing; one file that got 6× slower still does.

Four properties are load-bearing and each was learned the hard way:

- **It is REPORT-ONLY, and that is enforced by `continue-on-error` in `ci.yml` — NOT by the absence of `--gate`.** An earlier revision gated and reddened on unchanged code (the baseline had been recorded on a loaded machine, so de-scaling inflated a file whose cost does not track load); add `--gate` only after several main-branch runs show it stable. But omitting `--gate` suppresses only the REGRESSION verdict: the script still exits 1 when it finds no reports, cannot read the baseline, or aborts on load. The step shipped under a comment asserting it "cannot fail the job" and then failed the job on its very first run, on the no-reports path. A step whose whole contract is "cannot fail the job" has to say so in the one place the runner reads.
- **The thresholds are CALIBRATED against measured noise, not chosen.** Pairs of identical-code runs were compared under TWO conditions — quiet (load ~20 on 18 cores) and loaded (~300). A +40 ms floor produced **39 false regressions** loaded; +50 ms is fine quiet but still fires 16 times loaded. `4x / +400 ms` is the only pair with **zero** false positives in BOTH, and it still catches the 6× case #193 names. Calibrating on quiet data alone would have shipped a floor that fires on every busy CI runner. The sweep is in the header of `scripts/lib/test-durations.mjs` — re-run it before touching either number.
- **The noise floor is an absolute DELTA (`--min-delta`), never a clamped denominator** (dividing by `max(baseline, floor)` rebases every cheap file against the floor, so a 4 ms file first reported at 150×). **But be clear what that buys: at the shipped defaults only 76 of 618 files are within resolution (against the current quiet baseline; the same thresholds covered 145 against a loaded one, because a quiet machine makes every file cheaper), and "a 5 ms unit test becoming 30 ms" — the example `vitest.shared.ts` cites — is NOT detected.** State the limit accurately, because "impossible" is too strong: measured over two identical runs, the per-file drift is p50 2.1 ms / p90 26.3 ms, and only 1.7% of sub-50 ms files drift by ≥ +25 ms — so +25 ms sits around the p97 edge of noise, and a much tighter `6x / +25 ms` does catch it at 0–2 false positives on a QUIET machine. It is not recoverable at zero false-positive cost, it flips with run order, and it is hopeless under load (the same +40 ms floor gave 39 false positives at load ~300). The old clamped-denominator design did not catch it either, and hid that it did not. Every run prints how many files are within resolution, so the coverage is stated rather than assumed. On quieter hardware, lower `--min-delta` and check the false-positive behaviour.
- **The noise guard uses QUARTILES (p75/p25), not p90/p10.** Regressions live in the top tail, so a p90-based spread is inflated by the very outlier being looked for and silences itself. Above `--max-spread` the tool prints "not comparable" and gives no verdict.
- **The baseline's recording conditions are stamped into it.** A baseline taken on a saturated machine has smear baked in; check `recordedUnder` before trusting a verdict, and re-record with `pnpm test:durations` on a quiet machine.

Turbo runs tasks in STRICT env mode, so `LLUI_TEST_DURATIONS` is declared in `turbo.json`'s `test.env`; without that a `turbo test` is green and emits nothing. (CI uses `pnpm -r`, so that declaration only matters for `pnpm turbo test`.)

**The budgets only bind a config that actually REACHES `vitest.shared.ts`, and one did not (#249).** `vitest.scripts.config.ts` — the root config behind `pnpm test:scripts`, a CI step of its own — defined itself standalone, so `scripts/test/**` ran on vitest's stock **5 s** `testTimeout` while every other suite ran on 30 s. Invisible by construction: each config is a separate module, `test:scripts` is green on a quiet machine, and it only bites under load, where a red reads as a flake rather than as a misconfiguration (two lanes in one batch hit it and both re-ran). Measured on 18 cores: `registry-attrs.test.ts`'s heaviest case 710 ms quiet → 2.77 s at load ~750, `tailwind-classes.test.ts` (a real Tailwind build) 684 ms → 3.59 s — 1.4x margin against 5 s, 8.4x against 30 s. `scripts/test/vitest-config-baseline.test.ts` now gates the config SET rather than that one file: every config must resolve the shared budgets (allowlisted per FILE **and** FIELD — a bare-field key excuses every config in the repo, measured), the scripts config must discover only `scripts/test/**`, and no config may carry a discovery glob whose directory does not exist. That last one is the general form of the trap: **`mergeConfig` CONCATENATES `test.include`**, so the obvious spelling of this fix leaves the shared `test/**/*.test.ts` glob in place beside the new one — harmless today, silently live the day someone adds a root `test/`. Spread instead (`{ ...shared, test: { ...shared.test, include } }`), as `packages/lexical-loro/vitest.stress.config.ts` already does.

**A load TRANSIENT is a different hazard from load, and the two want opposite fixes (#246).** Two more gates degrade under parallel load, by different mechanisms, and neither is answered by a bigger number. (1) `@llui/site`'s `documents every symbol exported by every public entry point` measured **1.0 s quiet and 32.8 s — a FAILURE against the 30 s budget — at load ~350**, i.e. a 33x load factor eating 30x of headroom. The cost is a FIXTURE, not an assertion: `ts.createProgram` parses 1280 files to resolve 182 entry points and the per-package export walk is under a millisecond, so the program moved into `beforeAll` (budgeted by the 60 s `hookTimeout`, sized for exactly this kind of unavoidable floor) and the assertion split into one `it` per package. Measured after, at the harsher load ~580: fixture 26.6 s of a 60 s hook, worst test 2.47 s, suite green. **That has a cost worth knowing generally: work moved into a hook LEAVES #193's metric without leaving the machine.** `aggregateDurations` sums `assertionResults[].duration` only, so at identical load this file went **6987 ms → 1247 ms REPORTED while its wall time stayed ~6.8 s** — a future regression in that `createProgram` is now invisible to `check:test-durations`, and a green duration report is not evidence that a fixture stayed cheap. Trimming the program is NOT the lever — `types: []` / `noLib` / both give a bit-identical export set and no reliable saving, and interleaved on a loaded machine the four variants ranged 591 ms to 8529 ms with the order of their medians unstable. (2) `@llui/lexical-loro`'s `projects in sub-quadratic time` is a wall-clock RATIO, not a timeout, so no budget applies at all — and **the observed noise exceeds the signal**: quadratic growth for its 4x size step is 16.0 and the flake has been seen at 16.47 and 29.53, so no threshold both tolerates the noise and rejects a quadratic. The mechanism is a burst, not saturation: under SUSTAINED load ~740 the ratio was min 3.07 / p50 4.07 / max 6.19 (0 of 8 over 12), because a steady slowdown scales both windows and cancels, while a burst landing in one window does not — and the large window is 4x longer, so the error is always UPWARD. Four cheaper estimators were measured in the same trials and all rejected: `process.cpuUsage()` (helped one tail, hurt another, read 19.20 in the flaking trial), equal-length windows (gain inside the noise, and doubles the test's cost), best-of-N (structurally wrong — the minimum lands on the DENOMINATOR too; max 16.35/37.39), and INTERLEAVING the two sizes (the most promising, by far the worst: p50 7.70, p90 40.30, 5 of 14 over 12, because alternating two working sets destroys each size's cache locality). **The estimator cannot be fixed; the SIZES can, and that is what shipped.** `{ retry: 2 }` looked free and is REJECTED on numbers: measured against a faithful quadratic mutant (`out.sort(...)` replaced by an insertion sort with identical output), 16 trials each at load ~220, healthy goes over 12 in **5 of 16** runs and the quadratic comes in UNDER 12 in **5 of 16** — a coin flip in BOTH directions — so retry cuts false reds to ~3% while raising MISSES from 31% to ~67%, buying quiet by more than doubling the thing the test exists to prevent. **Never read a perf-ratio flake as one-directional, and never measure only the healthy arm**: the same transient that reddens healthy code also greens a real regression, retry looks free until the mutant's distribution is measured, and the shipped 500/2000 configuration was missing a genuine quadratic **half the time** (12/24 under harsh bursts) while its comment claimed a 16x signal. The fix is BIGGER SIZES: at 500/2000 the projection's O(n) Loro reads still dominate the sort so the mutant medians ~13, while **1000/4000 improves BOTH directions** — false red 21% → 12.5%, miss **50% → 6%** — for **~6x** the wall time (0.33 s steady / 0.60 s harsh → 3.51 s p50 / 6.97 s max), i.e. headroom against the 30 s budget falling from ~10x to ~3–4x. Two methodology rules came out of it. **Measure THROUGH the shipped test, never a replica** — a standalone `tsx` harness copying `project()` line for line produced a plausible distribution matching the old numbers and was wrong, because `tsx` runs ~2x slower than vitest's build and compresses the quadratic signal back into the Loro-read floor. And **a ratio breaks on TRANSIENTS, not on load**: at sustained saturation it was 0 of 12 and 0 of 20 over 12, because a steady slowdown scales both windows and cancels.

**`LLUI_TEST_DURATIONS` must stay RELATIVE in `ci.yml`, and both sides must resolve it identically.** The `verify` job runs inside a `container:`, where the workspace is mounted at `/__w/<repo>/<repo>` — but `${{ github.workspace }}` still expands to the HOST path (`/home/runner/work/...`), which does not exist in the container. It shipped as `${{ github.workspace }}/.test-durations`, so the reports went one place and the reader looked in another, and the run reported "no duration reports" with a green suite behind it. Both `vitest.shared.ts` (writer) and `scripts/check-test-durations.mjs` (reader) now `resolve()` the value against the REPO ROOT, so a relative value means the same thing on both sides by construction; taking it raw on either side makes them agree only when it happens to be absolute.
