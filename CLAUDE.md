# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What is LLui

LLui is a compile-time-optimized web framework built on The Elm Architecture (TEA), designed for LLM-first authoring. It runs on a **signal** runtime (`@llui/dom` — a single import surface; there is no legacy runtime and no `/signals` subpath). There is no virtual DOM — `view()` runs once at mount, building real DOM nodes with reactive bindings. State changes drive a **chunked-mask reconciler**: each binding carries a sparse mask of the dependency-path chunks it reads; on update the runtime computes the dirty chunk-set from old→new state (reference-equality per path), gates out bindings whose mask doesn't intersect it, then commits only values that actually changed (output-equality). Structural primitives (`branch`, `each`, `show`, plus `unsafeHtml`/`lazy`/`virtualEach`/`foreign`/`portal`/`provide`) are **lazy `Mountable`s** — recipes that build their live nodes and register their reconcile spec / child scope at the point they are _placed_ (materialized by `populate` for element children and by `runBuild` for a build's returned array, both under a live build context), not at construction. So a `Mountable` captured in a variable and reused inside a toggling `show`/`branch` arm rebuilds fresh on every remount (spec lands in the placing scope); placing one twice yields two independent live instances. They reconcile arms/keyed rows and own child scopes.

The Vite plugin runs a **single signal transform** (`@llui/compiler`) via the TypeScript Compiler API: it lowers signal expressions in a component's DIRECT view to runtime helpers (`signalText`/`el`/`react`/`signalEach`/…) as an optimization, emits introspection metadata, and runs the signal lint rules as non-bypassable build errors. Anything it can't lower (view-helper functions, block-body views) runs via the real runtime authoring helpers (which consume signal handles), so both forms coexist.

## Committing (parallel worktrees)

- **Never run `git stash` in this repository.** `refs/stash` is ONE ref on the COMMON git dir — worktrees do not get their own — so two lanes stashing at overlapping times interleave on a single stack and a `pop`/`drop` acts on the wrong entry. Two lanes destroyed each other's entries this way in one batch of parallel agent work.
- The pre-commit hook is that hazard automated, which is why it is not left to convention: `lint-staged`'s backup IS a `git stash`, and it resolves its own entry's INDEX in one `git` call and uses it in the next (`stash drop <n>` / `stash apply --index <n>`), so a lane that pushes in between shifts the index and the second call lands on someone else's entry. The hook therefore runs through `scripts/pre-commit.mjs`, which serializes every worktree's `lint-staged` behind a lock on the common git dir (#179).
- **`SKIP_SIMPLE_GIT_HOOKS=1` DEFEATS THAT LOCK.** Its early exit lives in the wrapper `simple-git-hooks` generates, ahead of the line that invokes `scripts/pre-commit.mjs`, so exporting it does not merely skip formatting — it removes the serialization, and any lane that does so re-opens #179 for every lane racing it. Nothing in this repo can close that. It also loses the formatting gate outright (measured: an unformatted file commits and `prettier --check` then fails), which makes it strictly worse than `--no-stash`.
- Two other options were measured and rejected, both written up in the header of `scripts/pre-commit.mjs` — read it before revisiting this: `--no-stash` (removes every stash call and changes nothing about what gets committed, but on a FAILING task with a partially staged file the unstaged hunks silently leave the working tree and index — recoverable only via `.git/lint-staged_unstaged.patch`, which no git command offers you and which the next run overwrites), and `SIMPLE_GIT_HOOKS_RC` (genuinely _can_ serialize, but it is an env var: it cannot be committed and binds only shells that export it, and #179 needs two unprotected lanes).
- **The lock's stress tests are part of the contract, and their configuration is not decorative.** FOUR mutual-exclusion defects shipped past a GREEN version of `scripts/test/worktree-lock.test.ts`, each reachable only after the previous was fixed, and every one was found by contending harder rather than by reasoning. Do not lower the 48-process / ~0 ms-critical-section configuration, and do not drop the crash-recovery case (a third of contenders dying while holding) — that workload was absent, which is precisely why the fourth defect, on the stale-break path, was invisible.
- What the lock guarantees, precisely: mutual exclusion under normal contention and while recovering crashed holders, measured at 0 violations across 32–64 contenders with and without extra CPU load. The one residual is a FOREIGN-HOST record aged out by `staleMs`, whose owner may still be alive because no PID is readable across machines — inherent to a filesystem lock shared across hosts, and not reachable here, where every worktree is on one machine.
- Hooks are shared across worktrees, so a change to `simple-git-hooks.pre-commit` only reaches a lane after **that lane's** next `pnpm install`.
- **`pnpm --filter <pkg> build check lint test` is INVALID and silently corrupts the tree.** pnpm forwards `check lint test` as ARGV to the `build` script; for `@llui/components` that makes the build's `cp src/styles/*.css dist/styles/ check lint test` treat `test/` as the destination and drop four CSS files into `packages/components/test/`. Two lanes hit this from an orchestrator's brief in one batch. Run the scripts separately.
- **`pnpm --filter <pkg> build check lint test` is INVALID and silently corrupts the tree.** pnpm forwards `check lint test` as ARGV to the `build` script; for `@llui/components` that makes `cp src/styles/*.css dist/styles/ check lint test` treat `test/` as the destination and drop four CSS files into `packages/components/test/`. Two lanes hit this from an orchestrator's brief in one batch. Run the scripts separately.
- **Parallel agent lanes share ONE scratchpad directory, and a mutation harness with a hardcoded absolute `ROOT` will silently mutate ANOTHER lane's tree.** Measured in the #231 batch: one lane invoked what it believed was its own `mutate.py` and patched a sibling lane's worktree instead; it survived only because that harness happened to restore in a `finally`. A mutation number measured against a tree another lane is concurrently patching is worthless in a way that reads as a perfectly normal result — the same class as an unfaithful mutation, arriving through infrastructure. Three rules: put the harness under a per-lane subdirectory; **assert** the root (`git rev-parse --show-toplevel` equals this lane's worktree, and the branch is this lane's) before writing a byte, failing loudly otherwise; and restore in a `finally`. Verify a lane's tree with `git diff` on every file, **never a file count** — the batch's one real contamination was a stray `deps: ['']` left by a skipped restore, and a count showed the expected number of modified files and looked correct. The same trap has a verifier-side form: a leftover-mutation check whose needle occurs twice in the file reports a false positive (#158's two-occurrences trap, one layer out).
- **A test that WALKS the repo must not walk `.claude/worktrees/`, and a floor-shaped vacuity guard cannot tell you that it did.** That directory is gitignored and holds a FULL CHECKOUT of every sibling lane, so a `readdirSync` walk from the repo root sees every other branch's files as if they were yours. Measured: a config-sweeping test found **210** `vitest*.config.ts` from the main worktree, **180 of them foreign**, failed on 18 divergences (a sibling's `vitest.stress.config.ts` reporting `testTimeout 180000`, with every allowlist key repo-relative and therefore unmatchable against a `.claude/...` path), and took its own transform from 5.6 s to 171 s by `import()`ing 180 foreign modules — down entirely if a sibling was mid-edit. **CI never reproduces it** (fresh checkout, no worktrees), so it fires exactly on the local `pnpm verify` this file tells lanes to run before merging. Enumerate with `git ls-files --cached --others --exclude-standard` (tracked plus untracked-but-not-ignored, so a brand-new file is still covered and anything gitignored is structurally unreachable), not a directory walk. And assert the EXACT set, never `length > N`: a floor only detects under-collection and would have waved 210 through.
- **A generated file that every lane regenerates is not mergeable by text, and each lane passing `check:generated` alone proves nothing about the merge.** `site/public/llms-full.txt` is built from EVERY package's API page, so three lanes each regenerated it in isolation and git text-merged the three results, silently dropping one lane's whole block while reporting no conflict. All three lanes were individually green. The only correct resolution is to regenerate AFTER the merge and commit that — make it a step of the merge, not something a lane can own.

## Spawned `llui-mcp` and the parent watchdog (#192)

The CLI polls `process.ppid` and shuts down when the process that started it goes away, because nothing propagates a parent's death to a non-detached child and a killed `pnpm dev` / vitest worker otherwise leaves it alive at PPID 1 still holding its port (one was found 31 h old). It fires on the ppid CHANGING, not on it being 1, and does not arm when the process was started BY init. **It DOES arm under a shell** — `nohup llui-mcp … & disown` is not reparented by `disown`, so when that shell exits the server shuts itself down. Export **`LLUI_MCP_NO_PARENT_WATCH=1`** when deliberately daemonizing it; that is the only thing covering that case.

## Test durations (#193)

The workspace `testTimeout` is 30 s (#180), which cost the repo its accidental performance canary — the old 5 s default. The replacement is a per-file duration BASELINE, not a bigger/smaller timeout: `LLUI_TEST_DURATIONS=<dir>` makes every package emit vitest's stock `json` report, and `scripts/check-test-durations.mjs` folds those into per-file totals and compares them against `test-durations.baseline.json` **after dividing out a same-run load factor** (the median of all files' current/baseline ratios). A uniformly slower machine reports nothing; one file that got 6× slower still does.

Four properties are load-bearing and each was learned the hard way:

- **It is REPORT-ONLY, and that is enforced by `continue-on-error` in `ci.yml` — NOT by the absence of `--gate`.** An earlier revision gated and reddened on unchanged code (the baseline had been recorded on a loaded machine, so de-scaling inflated a file whose cost does not track load); add `--gate` only after several main-branch runs show it stable. But omitting `--gate` suppresses only the REGRESSION verdict: the script still exits 1 when it finds no reports, cannot read the baseline, or aborts on load. The step shipped under a comment asserting it "cannot fail the job" and then failed the job on its very first run, on the no-reports path. A step whose whole contract is "cannot fail the job" has to say so in the one place the runner reads.
- **The thresholds are CALIBRATED against measured noise, not chosen.** Pairs of identical-code runs were compared under TWO conditions — quiet (load ~20 on 18 cores) and loaded (~300). A +40 ms floor produced **39 false regressions** loaded; +50 ms is fine quiet but still fires 16 times loaded. `4x / +400 ms` is the only pair with **zero** false positives in BOTH, and it still catches the 6× case #193 names. Calibrating on quiet data alone would have shipped a floor that fires on every busy CI runner. The sweep is in the header of `scripts/lib/test-durations.mjs` — re-run it before touching either number.
- **The noise floor is an absolute DELTA (`--min-delta`), never a clamped denominator** (dividing by `max(baseline, floor)` rebases every cheap file against the floor, so a 4 ms file first reported at 150×). **But be clear what that buys: at the shipped defaults only 76 of 618 files are within resolution (against the current quiet baseline; the same thresholds covered 145 against a loaded one, because a quiet machine makes every file cheaper), and "a 5 ms unit test becoming 30 ms" — the example `vitest.shared.ts` cites — is NOT detected.** State the limit accurately, because "impossible" is too strong: measured over two identical runs, the per-file drift is p50 2.1 ms / p90 26.3 ms, and only 1.7% of sub-50 ms files drift by ≥ +25 ms — so +25 ms sits around the p97 edge of noise, and a much tighter `6x / +25 ms` does catch it at 0–2 false positives on a QUIET machine. It is not recoverable at zero false-positive cost, it flips with run order, and it is hopeless under load (the same +40 ms floor gave 39 false positives at load ~300). The old clamped-denominator design did not catch it either, and hid that it did not. Every run prints how many files are within resolution, so the coverage is stated rather than assumed. On quieter hardware, lower `--min-delta` and check the false-positive behaviour.
- **The noise guard uses QUARTILES (p75/p25), not p90/p10.** Regressions live in the top tail, so a p90-based spread is inflated by the very outlier being looked for and silences itself. Above `--max-spread` the tool prints "not comparable" and gives no verdict.
- **The baseline's recording conditions are stamped into it.** A baseline taken on a saturated machine has smear baked in; check `recordedUnder` before trusting a verdict, and re-record with `pnpm test:durations` on a quiet machine.

Turbo runs tasks in STRICT env mode, so `LLUI_TEST_DURATIONS` is declared in `turbo.json`'s `test.env`; without that a `turbo test` is green and emits nothing. (CI uses `pnpm -r`, so that declaration only matters for `pnpm turbo test`.)

**The budgets only bind a config that actually REACHES `vitest.shared.ts`, and one did not (#249).** `vitest.scripts.config.ts` — the root config behind `pnpm test:scripts`, a CI step of its own — defined itself standalone, so `scripts/test/**` ran on vitest's stock **5 s** `testTimeout` while every other suite ran on 30 s. Invisible by construction: each config is a separate module, `test:scripts` is green on a quiet machine, and it only bites under load, where a red reads as a flake rather than as a misconfiguration (two lanes in one batch hit it and both re-ran). Measured on 18 cores: `registry-attrs.test.ts`'s heaviest case 710 ms quiet → 2.77 s at load ~750, `tailwind-classes.test.ts` (a real Tailwind build) 684 ms → 3.59 s — 1.4x margin against 5 s, 8.4x against 30 s. `scripts/test/vitest-config-baseline.test.ts` now gates the config SET rather than that one file: every config must resolve the shared budgets (allowlisted per FILE **and** FIELD — a bare-field key excuses every config in the repo, measured), the scripts config must discover only `scripts/test/**`, and no config may carry a discovery glob whose directory does not exist. That last one is the general form of the trap: **`mergeConfig` CONCATENATES `test.include`**, so the obvious spelling of this fix leaves the shared `test/**/*.test.ts` glob in place beside the new one — harmless today, silently live the day someone adds a root `test/`. Spread instead (`{ ...shared, test: { ...shared.test, include } }`), as `packages/lexical-loro/vitest.stress.config.ts` already does.

**A load TRANSIENT is a different hazard from load, and the two want opposite fixes (#246).** Two more gates degrade under parallel load, by different mechanisms, and neither is answered by a bigger number. (1) `@llui/site`'s `documents every symbol exported by every public entry point` measured **1.0 s quiet and 32.8 s — a FAILURE against the 30 s budget — at load ~350**, i.e. a 33x load factor eating 30x of headroom. The cost is a FIXTURE, not an assertion: `ts.createProgram` parses 1280 files to resolve 182 entry points and the per-package export walk is under a millisecond, so the program moved into `beforeAll` (budgeted by the 60 s `hookTimeout`, sized for exactly this kind of unavoidable floor) and the assertion split into one `it` per package. Measured after, at the harsher load ~580: fixture 26.6 s of a 60 s hook, worst test 2.47 s, suite green. **That has a cost worth knowing generally: work moved into a hook LEAVES #193's metric without leaving the machine.** `aggregateDurations` sums `assertionResults[].duration` only, so at identical load this file went **6987 ms → 1247 ms REPORTED while its wall time stayed ~6.8 s** — a future regression in that `createProgram` is now invisible to `check:test-durations`, and a green duration report is not evidence that a fixture stayed cheap. Trimming the program is NOT the lever — `types: []` / `noLib` / both give a bit-identical export set and no reliable saving, and interleaved on a loaded machine the four variants ranged 591 ms to 8529 ms with the order of their medians unstable. (2) `@llui/lexical-loro`'s `projects in sub-quadratic time` is a wall-clock RATIO, not a timeout, so no budget applies at all — and **the observed noise exceeds the signal**: quadratic growth for its 4x size step is 16.0 and the flake has been seen at 16.47 and 29.53, so no threshold both tolerates the noise and rejects a quadratic. The mechanism is a burst, not saturation: under SUSTAINED load ~740 the ratio was min 3.07 / p50 4.07 / max 6.19 (0 of 8 over 12), because a steady slowdown scales both windows and cancels, while a burst landing in one window does not — and the large window is 4x longer, so the error is always UPWARD. Four cheaper estimators were measured in the same trials and all rejected: `process.cpuUsage()` (helped one tail, hurt another, read 19.20 in the flaking trial), equal-length windows (gain inside the noise, and doubles the test's cost), best-of-N (structurally wrong — the minimum lands on the DENOMINATOR too; max 16.35/37.39), and INTERLEAVING the two sizes (the most promising, by far the worst: p50 7.70, p90 40.30, 5 of 14 over 12, because alternating two working sets destroys each size's cache locality). **The estimator cannot be fixed; the SIZES can, and that is what shipped.** `{ retry: 2 }` looked free and is REJECTED on numbers: measured against a faithful quadratic mutant (`out.sort(...)` replaced by an insertion sort with identical output), 16 trials each at load ~220, healthy goes over 12 in **5 of 16** runs and the quadratic comes in UNDER 12 in **5 of 16** — a coin flip in BOTH directions — so retry cuts false reds to ~3% while raising MISSES from 31% to ~67%, buying quiet by more than doubling the thing the test exists to prevent. **Never read a perf-ratio flake as one-directional, and never measure only the healthy arm**: the same transient that reddens healthy code also greens a real regression, retry looks free until the mutant's distribution is measured, and the shipped 500/2000 configuration was missing a genuine quadratic **half the time** (12/24 under harsh bursts) while its comment claimed a 16x signal. The fix is BIGGER SIZES: at 500/2000 the projection's O(n) Loro reads still dominate the sort so the mutant medians ~13, while **1000/4000 improves BOTH directions** — false red 21% → 12.5%, miss **50% → 6%** — for **~6x** the wall time (0.33 s steady / 0.60 s harsh → 3.51 s p50 / 6.97 s max), i.e. headroom against the 30 s budget falling from ~10x to ~3–4x. Two methodology rules came out of it. **Measure THROUGH the shipped test, never a replica** — a standalone `tsx` harness copying `project()` line for line produced a plausible distribution matching the old numbers and was wrong, because `tsx` runs ~2x slower than vitest's build and compresses the quadratic signal back into the Loro-read floor. And **a ratio breaks on TRANSIENTS, not on load**: at sustained saturation it was 0 of 12 and 0 of 20 over 12, because a steady slowdown scales both windows and cancels.

**`LLUI_TEST_DURATIONS` must stay RELATIVE in `ci.yml`, and both sides must resolve it identically.** The `verify` job runs inside a `container:`, where the workspace is mounted at `/__w/<repo>/<repo>` — but `${{ github.workspace }}` still expands to the HOST path (`/home/runner/work/...`), which does not exist in the container. It shipped as `${{ github.workspace }}/.test-durations`, so the reports went one place and the reader looked in another, and the run reported "no duration reports" with a green suite behind it. Both `vitest.shared.ts` (writer) and `scripts/check-test-durations.mjs` (reader) now `resolve()` the value against the REPO ROOT, so a relative value means the same thing on both sides by construction; taking it raw on either side makes them agree only when it happens to be absolute.

## CI — where it differs from what you run locally

Reproducing CI means mirroring `.github/workflows/ci.yml` **step for step, filters included**. Two differences have already cost a red `main`:

- **`--filter=!@llui/site` applies to the BUILD step ONLY.** `pnpm turbo check` and `pnpm turbo lint` run UNFILTERED, so the site is type-checked and linted in CI even though it is excluded from the build. Carrying that filter across to `check` in a local pre-merge run is how a genuine break reached `main`. **`@llui/site` is the only workspace that type-checks a file importing `vitest.shared.ts`** — all **28** files named `vitest.config.ts` (26 packages + `registry/` + the site) import it, as do the two specially-named ones (`packages/lexical-loro/vitest.stress.config.ts` and the root `vitest.scripts.config.ts`, #249) for **30** configs in total, but the packages' and registry's tsconfigs include only `["src", "test"]`, while the site's additionally lists `"vite.config.ts", "vitest.config.ts"`. So the repo's root config is checked in exactly one place, by virtue of one `include` array. The instance: `vitest.shared.ts`'s duration reporters carried `as const`, making the inner `['json', {…}]` a `readonly` tuple, which vitest's `reporters` type (`ReporterName | Reporter | [name, options]`) does not accept. It compiled everywhere because almost nothing type-checked the file — and the site gained its `check` script (#176) in the same batch that added the reporter (#193), so the two halves landed together and neither lane's own verification could see it. Type root config against vitest's own exported config type rather than reaching for `as const`; the hygiene that looks free here is a type error at the one call site that checks it. (Widening the other `include` arrays would close the hole generally — nobody has, and the cost is unmeasured.) **`scripts/` gained two more importers of the shared config (#249) and the site is STILL the only place any of them is checked**, because NOTHING type-checks or lints `scripts/`: `turbo check`/`turbo lint` run per PACKAGE and the root is not a workspace member, while `tsconfig.benchmarks.json` names an explicit `files` list of benchmark tooling only. A `check:scripts` gate is a real follow-up, not a free one — but **quote the invocation with the number, because it swings by an order of magnitude**: extending the root `tsconfig.json` with `types: ["node","vitest/globals"]` over `scripts/**/*.ts`, `checkJs: false` gives **15 errors in 4 files**; flipping `checkJs: true` pulls in the `.mjs` those tests import for **116 in 10**; adding `scripts/**/*.mjs` to `include` gives **163 in 20**. `vitest.scripts.config.ts` and `scripts/test/vitest-config-baseline.test.ts` are clean under all three.
- **`verify` fails FAST, and its step order hides the rest.** `Type check` runs ahead of `Test`, `Test root scripts` and `Smoke-test example bundles`. A run that goes red at `Type check` has told you **nothing** about the suite — do not read it as "only the types are broken". Run the later steps locally before assuming they pass.

After merging branches locally, run `pnpm install` in the main worktree before believing any failure it reports: a stale `node_modules` resolves a different dependency graph than the lockfile describes (a merged-but-uninstalled tree resolved `vite@6` for the site while the lockfile said `vite@8`, producing two pages of `Plugin<any>` incompatibility that did not exist in CI).

## Development Approach

- **Test-driven development:** Define the type/shape first, write one or more failing tests, then implement until they pass.
- **Tests live in a separate `test/` folder** within each package (e.g. `packages/core/test/`), not alongside source files.
- **No `any` types** unless strictly unavoidable. `as unknown as X` is a code smell — find a better type or restructure.
- **Nothing is sacred.** There is no legacy code or backward compatibility concern. When changing assumptions, update the docs in `site/content/` (published to [llui.dev](https://llui.dev)) to match.
- **No shortcuts.** Engineering economy, expedience, or "good enough for now" must never drive decisions. The drivers are engineering excellence, sound solutions, correctness, and developer experience. If the correct fix is harder, do the harder thing.

### Mutation testing: an UNFAITHFUL mutation reads as coverage

Mutation testing is this repo's main defence against vacuous tests, and every lint-rule, reconciler and quota change is expected to arrive with a mutation table. In ONE batch (PRs #158–#180) four agents reported a mutation number that was wrong — in every case because the MUTATION was malformed, not because the tests were weak. All four were caught by hand (two by the author, two by review); a green suite catches none of them. The trap is counter-intuitive: **a badly-formed mutation usually reddens MORE tests, not fewer, so it reads as strong coverage.**

- **Verify the mutation reached live code before reading the result** — print or assert the applied diff. PR #158 patched a line whose text appeared TWICE in the file and landed on `replaceUrl` instead, never reaching the code under test; the resulting false "12 green" read as WEAK tests. When a mutation reddens NOTHING, suspect the patch before concluding the test is weak.
- **A mutation must be FAITHFUL: it changes exactly the property under test and leaves every invariant around it intact.** PR #168 dropped the `reserveSlot` guard but left `releaseSlot` unpaired, so `reserved` went NEGATIVE and MASKED the unbounded growth the test existed to expose — green against a genuinely unbounded resurrect, where removing reserve AND release killed it. PR #170's "host stops publishing" written `(() => {})()` put `undefined` into the disposer array, so every test additionally died in teardown with `TypeError: dispose is not a function`: a reported 10/10 red where the faithful mutation gives 7/10. If the mutation also breaks paired bookkeeping, a teardown contract, or throws where the real defect would not, the number measures the breakage, not the property.
- **A mutation cannot redden a test whose assertion the mutation SATISFIES.** A fail-closed mutation cannot kill a test asserting the closed direction, yet two PRs reported "all N red" for suites containing exactly such tests — a number that could not have been measured. Stating per row WHY a survivor survives is what makes a table trustworthy; a partial score (`tag-send-drift`'s 65 of 66, below) is the normal shape of an honest one.
- **Re-run mutations against the FINAL committed code.** One figure in the batch was measured before a TypeScript fix that later widened an assertion, so the number never described the tree that shipped.

### Focus/overlay verification: avoid vacuous passes

Focus evidence needs the same discipline as a faithful mutation: first prove the probe can distinguish the broken behavior. Three traps have already produced green results for the wrong reason:

- **Do not use Playwright's `page.focus()` for the action in a focus-restoration probe.** It can re-assert focus after the action and overwrite the restoration being measured. Call the element's raw `HTMLElement.focus()` inside `page.evaluate`, perform the close or teardown there, and observe `document.activeElement` there. `packages/components/test/components/dialog-nested-focus.browser.test.ts` is the executable example.
- **Spread the actual attribute bag, not a wrapper around it.** Part bags may be nested: `MenuItemPartsOf<Scope>` is `{ item: MenuItemAttrs<Scope> & { role: 'menuitem' } }`, so the fixture wiring is `button({ ...parts.item('a').item }, ...)`, not `button({ ...parts.item('a') }, ...)`. The latter silently emits `item="[object Object]"` and omits `role`, `data-part`, and `tabindex="-1"`; assert those expected attributes before interpreting any focus result. `packages/components/test/browser/context-menu-ownership.fixture.ts` exercises the real shape.
- **Make a focus-trap membership assertion cross the boundary it claims to test.** If focus starts on the trap's first focusable, forward Tab can select that same element with or without the disputed container and therefore proves nothing in jsdom. Use the wrap direction that enumerates the disputed edge (for example, Shift+Tab from first to last), or a real-browser scenario whose observed traversal crosses it. `packages/components/test/components/overlay-engine-focus.integration.test.ts` and `context-menu-ownership.browser.test.ts` pin both forms.

- **Control characters in string literals are written as ESCAPES (`\0`), never as raw bytes.** git has no file-type database — it sniffs, and ONE NUL in the first 8000 bytes makes it call the file binary, after which `git diff`, `git log -p` and GitHub's PR review hide every change to it by default. That is how `packages/markdown/src/keying.ts` (the re-render decision for reused prefix blocks) and `packages/vite-plugin/src/notes/trusted-tasks.ts` (the marker gating an agent spawn) both went unreviewable (#94). Both encodings produce the same string at runtime; only one is diffable. `scripts/test/source-encoding.test.ts` fails the build if a raw NUL comes back
- Configured via `.prettierrc` and `eslint.config.ts` (flat config)

## Architecture Concepts

**Component shape:** `component<State, Msg, Effect>({ name, init, update, view, onEffect? })`. State must be JSON-serializable. Msg and Effect are discriminated unions with a `type` field. `init()` takes NO arguments. `view` receives a `{ state, send }` bag where `state` is a `Signal<State>` — read it with `state.map(s => …)` (derive a reactive value), `state.at('field')` (narrow to a sub-path signal), or `state.peek()` (one-shot read in handlers/effects). Element + structural helpers (`div`, `button`, `text`, `each`, `show`, `branch`, …) are module imports from `@llui/dom`, NOT bag members.

**Composition:**

- **View functions (default):** factor sub-views as plain functions that take signal handles — `header(state.at('header'), send)` or `header(state.map(s => s.header), send)`. They run via the real runtime authoring helpers (which consume handles), so they compose without compilation. Annotate their return as `Renderable` (a list, `readonly Mountable[]`) or `Mountable` (a single element) — NOT `Node`/`Node[]`. Every authoring helper (`el`/`text`/`each`/`show`/…) returns a lazy `Mountable`; the cross-file compiler walker recognizes `Renderable`/`Mountable` (and legacy `Node` shapes) as view-helper returns. A helper called for a side effect (notably `onMount`) is now inert unless its returned `Mountable` is PLACED in the view array — discarding it registers nothing.
- **Library components:** the `connect(state: Signal<Slice>, send, opts?)` + `overlay({ state, send, parts, content })` pattern (see `@llui/components`) returns Signal-handle part bags the consumer spreads onto elements. WHICH state a `connect` reads is the three-tier choice: T1 static (no state after build) is `connect(constant(v), noSend, opts)`, T2 local (private/transient) is `island({ def })`, T3 hoisted (URL, undo, persistence, a sibling reads it) is `connect(state.at('x'), send)`. `island()` is on the MAIN barrel and is the ordinary answer for private widget state, not an escape hatch — it was `subApp` at `@llui/dom/escape-hatch`, which is now a deprecated alias whose subpath, module header and mandatory `reason` all framed the capability as an anti-pattern and hid it (#231). Measured at N=500 leaves in jsdom: ~2.4x at mount (22.0ms → 53.3ms), ~2x CHEAPER over 50 host updates (2.19ms → 1.14ms), because an island is not a child scope the host reconciler walks — mount cost for update isolation. Props go IN declaratively (`props: state.at('x')` + `onProps: (v) => msg`, a real host-scope binding so it is mask-gated, and the change becomes a MESSAGE rather than a poke at the island's state); messages come OUT through `onHandle`.

**Reactivity (chunked mask):** there is no path ceiling. Each binding carries a sparse mask of the dependency-path chunks it reads; on update the runtime builds the dirty chunk-set from old→new state (reference-equality per path), gates out non-intersecting bindings, and commits only changed values (output-equality). Structural primitives reconcile and own child scopes. (This replaces the deleted two-word-bitmask / `elSplit` / `__dirty` model.)

**Effects as data:** `update()` returns `[newState, effects]`. The core runtime does NOT special-case any effect type — every effect is passed to the component's `onEffect` handler; with no handler an emitted effect is dropped (the runtime warns in dev). The `@llui/effects` package provides the effect builders (`http`/`cancel`/`debounce`/`sequence`/`race`/`timeout`/`interval`/`delay`/`log`/…) and `handleEffects<E>().else(handler)` (adapt to `onEffect` via `asOnEffect`). `delay(ms, msg)` (alias of `timeout`) and `log(message)` replace the old built-in core `delay`/`log` effects.

**`send()` is synchronous:** in the signal runtime each `send()` runs the reducer and applies the update immediately (no microtask batching). `handle.flush()` is a no-op under the default synchronous scheduler (kept for harness/agent parity); in `raf` mode it force-commits synchronously. **`batch(fn)`** (on the handle AND in the view/`onEffect` bag, alongside `send`) coalesces a burst of `send`s into ONE reconcile: every reducer still runs in order and effects still fire per message, but the DOM commit + subscriber notification are deferred to a single pass against the final state when the outermost `batch` returns. State is applied by the time `batch` returns, so the synchronous contract holds at the boundary — this is the opt-in burst/streaming fast path (drain a websocket frame of N ticks as one re-render; ~2.4× on a 1k-tick burst). The compiler also auto-wraps provably-safe straight-line multi-`send` handlers (a block of only `send(...)` calls) in `batch(...)` and injects `batch` into the bag. There is NO microtask/rAF auto-batching by default (it would break sync predictability). The OPT-IN frame-scheduled mode shipped: `mountApp(container, def, { scheduler: 'raf' })` keeps reducers/effects synchronous (the data contract holds) but coalesces the DOM commit + subscriber notification to one reconcile per animation frame (microtask fallback off-browser; `handle.flush()` forces a synchronous commit) — measured at vanilla parity on the 1k-burst ticker op (5.9ms vs 14.1 per-send).

## Invariants & landmines

Load-bearing rules a change must not violate, and traps a fresh contributor (human or LLM) reliably falls into. When touching the relevant subsystem, treat these as hard constraints — several are unenforced by types/CI and caused real bugs.

**Runtime invariants (`@llui/dom`):**

- **Build-once.** `view()` runs exactly once and builds a static graph of reactive bindings — there is no re-render. Reactivity is the chunked-mask reconciler. A value read outside a binding (e.g. `state.peek()` in a slot) is frozen forever.
- **ARIA state attributes are ENUMERATED, not boolean, and `applyAttr` special-cases them.** `aria-checked` / `aria-expanded` / `aria-pressed` / `aria-selected` take the literal strings `"true"` / `"false"`; an empty value is INVALID (assistive tech reports no state) and an absent one is worse still — a `role="switch"` with no `aria-checked` has no state at all. The HTML boolean rule (`true` → `attr=""`, `false` → remove) is correct for `disabled`/`hidden` and wrong for these in BOTH directions, which is what a part bag doing the natural `'aria-checked': state.map((s) => s.checked)` hit: measured across the registry demo, SEVEN part families announced nothing — radio-group item, switch root, toggle root, toggle-group item, rating-group item, tabs trigger, accordion trigger. `applyAttr` now renders a boolean under an `aria-` name as the string; `null`/`undefined` still REMOVE, because that is how a part bag spells "not applicable" (`s.disabled ? A DECLARATION is deliberately NOT in the predicate: `function f(){}`/`class C{}` bind in the ENCLOSING scope, which the `Block` branch (and, at module scope, `HelperBindings.fromSourceFile`) already own — for `Block`, `SourceFile`, function bodies and arrow blocks, at any nesting depth, verified per consumer. The one container owned by NEITHER is a `ModuleBlock`: `namespace N { function div(){}; div({}, []) }` still fires `empty-props`. Pre-existing and left open — namespaces are effectively absent from this workspace — but the sentence is "the `Block` branch and `fromSourceFile`", not "every enclosing scope". What #153 also lists as a third false positive is not one: `tagSend(send, ['open'], function send() {})` still reports the over-declaration, identically to the anonymous `() => {}` — the report is direction 2 doing its job on a handler that provably dispatches nothing, not the shadowing gap, and it is pinned as a parity test so a later 'fix' cannot silence direction 2 for every empty handler. DECLARED-BUT-NEVER-DISPATCHED is reported ONLY when the dispatch set is provably COMPLETE, because "I did not see it" is not "it does not happen": `tagSend(send, ['commit'], (e) => commitFromEvent(e))` dispatches one call away. Completeness survives exactly one thing besides a readable dispatch — a zero-arg `e.preventDefault()`-family call on a handler parameter, an ALLOWLIST (`isInertParameterMethodCall`), because every other call, tagged template, `new`, returned function or bare mention of the dispatcher can reach it. Forgiving any call ROOTED at a parameter instead rejected ten shapes of valid code (`cb()`, `ctx.commit()`, `opt.onSelect?.()`, `emit({type:'pick'})`, `e['go']()`, …). The allowlist's own cost lands on the OTHER side and is worth stating to library authors: a non-allowlisted event method on a handler parameter (`e.persist()`, `e.composedPath()`) silently switches the over-declaration check off for that call site — a missed lint, never a broken build, but silent either way. A sound generalization needs a `ts.Program`/checker the string-edit transform does not have; nothing syntactic separates `e.persist()` from `ctx.commit()`. **When the two directions disagree about a shape, BAIL** — an unreported drift is a missed lint, a false positive is a build broken for a consumer who did nothing wrong; every knob above is pinned by a mutation-checked test for that reason. Evidence: over the ~220 `tagSend` call sites in this repo's sources the rule reports ZERO. A faithful per-file mutation of one literal declared variant makes it fire in **65 of 66** files. The sole survivor is `packages/components/src/components/tooltip.ts`: both sites intentionally pass the named `dismissOnEscape` handler, whose body this syntax-only analysis cannot attribute. The corpus is 65 production files with mutable literal variant lists plus `packages/dom/test/signals/handle-parity.test.ts`; the latter is the relative-import fixture made reachable by #146. That fixture now uses a no-op handler to prove its descriptor came from `__lluiVariants` without making valid compiler input lie about a dispatch. Helper identity follows IMPORT PROVENANCE: canonical/aliased/namespace `@llui/dom` imports, a resolved file whose nearest package identity is exactly `@llui/dom`, or a barrel export recursively traced to one of those roots. Cyclic, ambiguous, unresolved, type-only, and unrelated same-named imports fail closed; filenames and suffixes grant no trust. The list itself is read through `as const`/`satisfies` (the same `unwrapCasts` the dep analyzer uses), because the narrowed signature is exactly what pushes authors to write `as const` and bailing on it switched the rule off for the spelling the type asks for; the unwrap does NOT resolve bindings, so a hoisted `VARIANTS` is still unreadable.
- **A DOM write from a view's own event handler is a build error (`imperative-dom-mutation`, #231), and its SCOPE is three syntactic conditions — not "inside a component view".** A consumer app reasoned from build-once views to the opposite conclusion: "the label is a STATIC node, no signal binding depends on it, so the reconciler never rewrites it and swapping its `textContent` from the click handler is safe." It is not — the node is owned by the scope that built it, and `show`/`branch`/`each` may move, reuse or tear it down on any later commit, at which point the write is silently lost or lands on a recycled row. The rule fires only when all three hold: (1) the write is inside an `on<Upper>` prop of a call `HelperBindings` resolves to a `@llui/dom` ELEMENT helper (`ALL_ELEMENT_HELPERS` + `el('tag', …)`) — that call IS the reconciler boundary, whoever wrapped it. Scoping to an enclosing `component(` instead would cover the nodes built inside a `component()` literal and not the identical ones built one function out in a view HELPER, which the plugin routes down its NON-component branch — hence `lintImperativeDomSource` beside `lintTagSendSource` there. (That argument is structural: #231 prints its FIX, not its incident module, so the consumer's file shape is not recoverable and is not offered as evidence.) (2) The handler resolves to a function the rule can read — INLINE, wrapped in `tagSend`, or a module-scope NAME — and (3) the mutated node is ROOTED at one of that handler's own parameters or at a `const` alias of one. **The three handler spellings are not polish.** Measured against #231's own incident body, an inline-only rule fired on ONE of the four spellings it can be written in, and the two recoverable misses are the two most idiomatic here (`tagSend` alone has ~220 call sites and is the house idiom for handlers on library controls); a verdict that turns on whether the author inlined the arrow teaches "name your handler", not "don't mutate the DOM". Name resolution is refused for a `let`/`var` binding, for any name the module ASSIGNS to (a `function` declaration's binding is mutable), and at a SHADOWED use site (`isShadowed`, exported from `helper-bindings.ts` for this — never a hand-rolled ancestor walk); handlers are deduped by node identity so a name installed on two elements reports once. Sinks are WRITES only — `textContent`/`innerHTML`/`innerText`/`outerHTML`/`className`, `style.*` and `dataset.*` property writes, `classList.{add,remove,toggle,replace}`, `style.{setProperty,removeProperty}`, `{set,remove,toggle}Attribute`. The read/write split, not an allowlist, is what keeps it off valid code: `const tex = (e.target as HTMLElement).textContent ?? ''` appears three times in `@llui/markdown-editor`'s plugins and must stay silent, and a faithful mutation dropping only `isAssignmentOperator` makes exactly that fixture fire. The `classList`/`style` RECEIVER name is required — `add`/`remove`/`toggle` are far too generic to attribute alone (`e.dataTransfer.items.add(f)` is not a class mutation). The root walk traverses CALLS (`btn.querySelector('.label').textContent = …` is #231's own line, and stopping at the call switches the rule off for the incident it exists to catch) but NOT a hop through `DOCUMENT_ESCAPE_MEMBERS` (`ownerDocument`, `document`, `defaultView`, `view`, `window`, `top`, `parent`, `frames`, `opener`, `getRootNode`). That narrowing is not hygiene: without it a theme toggle (`e.currentTarget.ownerDocument.documentElement.style.setProperty('--theme','dark')`) and a scroll lock (`e.view.document.body.style.overflow = 'hidden'`) were both FALSE POSITIVES, and reaching the document that way is the MORE defensive spelling (iframes, portals, jsdom, multi-document SSR) of an idiom `@llui/interactions/src/remove-scroll.ts` writes with the global `document`. The list is generous by design — an omission is a broken build, an extra entry only a missed lint — and `parentNode`/`parentElement`/`closest` are deliberately NOT in it. Aliases extend through `const` ONLY: a `let` can be reassigned to an unrelated node between the declaration and the write, which a syntax-only analysis cannot see. Shadowing is pruned with `scopeIntroduces`, never re-derived. `foreign()`, `island()` and `subApp()` are skipped WHOLE — they are imperative by design and are the two fixes the message names, so firing inside them would contradict the diagnostic. (`island` is a `@llui/dom` BARREL export; `subApp` survives only on the `@llui/dom/escape-hatch` subpath, so a fixture must import each from the subpath it actually has — the first cut imported `subApp` from the barrel and proved the bail for an import no consumer can write.) The pre-check regex is DERIVED from the sink sets rather than restated, because a sink added to a set but not to the gate is a rule that silently stops firing with a green suite behind it. REMAINING BLIND SPOTS, all in the safe direction and all labelled as absence-of-coverage in the tests rather than as false-positive guards: an opaque props bag (`div(props, …)` — the object may be mutated between construction and use), a computed prop key, an IMPORTED handler, and any handler attached with `addEventListener` rather than a view prop. **The bug class is NOT closed by this rule**: `tabs.watchTabIndicator` and `navigationMenu.watchNavMenuIndicator` write `indicator.style.setProperty(…)` on view-built nodes from an `onMount` watcher — identical in kind, zero coverage, and deliberately not widened to, since an `onMount` body is the sanctioned place to touch a live node. Evidence: 0 reports over 1531 TS/TSX files in `packages/`, `registry/`, `examples/` and `site/`; under the SHIPPED pre-check that is 95 handlers collected across 22 files, 50 parameterless (returned before scanning) and **37 handler evaluations with a live root set**, plus a clean `pnpm turbo build` of every example app through the plugin. Quote the scanned figure, not a bypassed-gate count: the first write-up said "67 handlers reach the walk", which was measured with the pre-check DISABLED and overstated the corpus by ~2×. 21 faithful mutations, all killed — except that no mutation reddens the `addEventListener` fixture, whose property is enforced structurally by `elementEventHandlers` requiring an object-literal props bag. **Five of the rule's own negative tests were VACUOUS before that was measured** — they carried neither pre-check token, so the walk never ran and a faithful mutation of the guard each one named left them green; the fixtures now append both tokens in a comment so each test is about the analysis rather than the gate.
- **Framework lint rules are COMPILE-TIME ERRORS in `@llui/compiler`, never ESLint** — LLMs (and humans in a hurry) ignore warnings, so a non-bypassable build error is the only effective channel. Do NOT reintroduce `@llui/eslint-plugin` or recreate rules as ESLint rules.

**Styling & the component registry (`registry/`, `@llui/cli`):**

- **A class string that no build compiles is not tested, however many assertions it has.** `packages/components/src/styles/classes/*` was 62 files of Tailwind recipes with 62 test files asserting `expect(cls).toContain('max-w-lg')`, zero consumers in this repo, and **116 utility occurrences across 55 of those files that emitted NO CSS at all** — every transition instant, every dialog/popover/tooltip unstacked. The suite was green throughout, and `tailwindcss` was not installed anywhere in the repo. The layer is DELETED; recipes now ship as registry source, and `scripts/test/tailwind-classes.test.ts` runs the REAL Tailwind build over every class the registry emits and fails on one that produces no rule. Do not add a class-string layer without that check, and do not weaken the check into a substring assertion.
- **Tailwind v4 namespace names are load-bearing and three of them are not what they look like.** Durations come from `--transition-duration-*`, z-indexes from `--z-index-*`, spacing from `--spacing-*`. `--duration-*` / `--z-*` / `--space-*` are NOT namespaces: they emit a perfectly good custom property (so `var(--duration-fast)` in a plain CSS rule works, which is why `theme.css`'s own `[data-scope]` rules never broke) while `duration-fast` / `z-dialog` compile to nothing. That asymmetry is the entire reason this went unnoticed for a release: the stylesheet half was fine and only the utility half was dead. The docs' namespace table is ABRIDGED — verify a namespace by compiling it, not by reading the table.
- **Registry recipes are shadcn/ui's, ported VERBATIM — do not "simplify" them into LLui inventions.** Measured at a mean 98% class-set match across the 45 components with an upstream counterpart, 38 of them at 100% (`registry/README.md` carries the breakdown); the shortfall is almost entirely classes that CANNOT be ported (Radix positioning vars like `origin-(--radix-…-transform-origin)`, and `cmdk`'s `[&_[cmdk-*]]` selectors). Byte-identical recipes are what make a shadcn theme, screenshot or tutorial still describe what you get. The shared idioms recur on every control: focus is `focus-visible:border-ring ring-[3px] ring-ring/50` (NOT a 2px solid ring); hover is an ALPHA of the base colour (`hover:bg-primary/90`), never a `--primary-hover` token; control borders are `border-input`, not `border-border`; `shadow-xs`, not `shadow-sm`; invalid is `aria-invalid:border-destructive aria-invalid:ring-destructive/20`. The derived tokens in `theme.css` exist for the BASELINE stylesheet and are not used by recipes. Note `active:` appears nowhere — shadcn does not use it either, so its absence is parity, not a gap.
- **A recipe that names an attribute its machine never publishes is dead CSS, and `scripts/test/registry-attrs.test.ts` is the only thing that finds it.** This is the registry's most expensive bug class: the class compiles, the part spreads, the type-check passes, and the rule simply never matches. FIVE shipped at once — `scroll-area` styled `data-[orientation=…]` against a machine publishing `data-axis` (the thumb rendered at ZERO pixels); `carousel`'s indicator used `data-[state=active]` against a bare `data-active` (the current dot never highlighted); `calendar` used react-day-picker's `data-[state=…]` throughout (no today marker, no selection fill, no range, no focus ring on any day, under a comment claiming that spelling was "the shape the machine publishes"); `rating-group` styled `data-[highlighted]`/`data-[state=half]` against `data-fill`; `steps` styled `data-[state=complete]` against a `data-status` whose values are `pending|current|completed|error`. A SIXTH was the machine's fault, not the skin's: `menu-machine` published `data-state="highlighted"` while `select`, `combobox`, `listbox`, `tags-input`, the baseline stylesheet AND every registry menu recipe use a bare `data-highlighted`, so every dropdown/context-menu/menubar item had no highlight at all. Three rules for that test: (1) it is ONE-DIRECTION — a recipe naming an attribute nobody emits is always a bug, while a machine publishing an attribute nothing styles is normal; (2) its allowlist is keyed **`file.ts: attr`, never by attribute name alone**, because a bare-name entry switches the check off everywhere — allowing `calendar`'s upstream `data-[state=today]` globally would have silenced the `carousel` bug the test exists to catch, measured; (3) an upstream-parity allowance must name the LLui spelling that carries the same state as `pairedWith`, and the test then requires that spelling to be present too — without it, deleting the working half leaves only the dead upstream spelling and the allowance approves it (measured: the `scroll-area` bug replayed green until the pairing was added). The MACHINE_OF map has its own vacuity test so a new skin cannot silently fall out of coverage.
- **The attribute cross-check has TWO arms, and the second one is about VALUES.** A recipe can name the right attribute and still match nothing, because upstream and LLui spell the same boolean state differently: shadcn writes `data-invalid="true"` / `data-disabled="true"`, and every boolean `data-*` in `@llui/components` is published BARE (`'' | undefined`) — the package-wide convention, used by roughly forty machines. `field.ts` shipped THREE such rules and the NAME arm was green on all of them: the `Field` root's `data-[invalid=true]:text-destructive`, and `group-data-[disabled=true]/field:opacity-50` on both `FieldLabel` and `FieldTitle`. An invalid field never turned red and a disabled one never dimmed, against machines that were publishing the state correctly the whole time. The fix is the documented bind-both pattern (`registry/README.md`), not picking a side. Four rules for the value arm, each measured: (1) `data-part` / `data-scope` are SKIPPED — they name a part, not a state, and a registry component legitimately declares parts of its own (`select-value`, `sidebar-menu-action`); (2) an attribute with a NAME-level allowance is skipped too, because that allowance already says it is not machine state in that file; (3) an OPEN declared type gets NO VERDICT rather than a guess — but "open" no longer means "not spelled inline" (#248, CLOSED, see the next bullet); (4) `VALUE_ALLOWED`'s `pairedWith` is checked against the BARE spelling set, never the attribute-name set — the dead bracketed form contributes its own name, so a name-level pairing would be satisfied by the very rule it is meant to justify.
- **A NAMED type is FOLLOWED to its union, and what the resolver still declines is PINNED (#248, CLOSED).** "No verdict on an open type" is right, but it used to fire on a type that was not open at all — merely named. `meter` declared `'data-state': Signal<MeterThreshold>`, so the value arm was silent while the shipped skin styled `data-[state=critical]` / `data-[state=suboptimal]` against a machine emitting `low`/`optimal`/`high`: the range painted `bg-primary` in every state for a release, NAME arm green throughout (#235). The exposure was **66 declarations / 19 distinct aliases** across `components/` + `patterns/`, `aria-*` included — where a wrong value is an accessibility defect, not merely dead CSS. `scripts/lib/registry-attrs.mjs` now follows a name through the file's own top-level `type X = …` and through RELATIVE imports and named re-exports inside the SAME package, recursively. Spelling all 66 inline (the `ChartParts` idiom) was the other option and it loses on measurement AND on principle: it is ~66 mechanical edits that trade a readable alias for a guard's convenience at every site, and nothing stops the 67th from being an alias again. Four things to keep straight. (1) **It FAILS CLOSED, and that direction is not negotiable** — a wrong verdict here is a build failure for a consumer who did nothing wrong. Declined: a bare/cross-package specifier, a path leaving the package root, a missing file, a GENERIC alias or any reference carrying type ARGUMENTS, a type PARAMETER, an interface/mapped/conditional type, and a cycle. A candidate that resolves to a DIRECTORY is SKIPPED rather than read — that one is not a decline but a fall-through, and it is in this list because omitting it was a CRASH: an extensionless `./sub` made candidate 0 the directory itself, which `existsSync` accepts and `readFileSync` rejects with `EISDIR`, so a guard whose whole contract is to fail CLOSED failed LOUD instead. With the `isFile()` stat it falls through to `sub/index.ts`, the answer TypeScript gives. Latent while nothing under `packages/components/src` imports extensionlessly — and the residue pin below exists precisely to push new declarations through this resolver, so an enumerated decline list has to be TOTAL rather than merely correct about the cases in the tree today. The type-parameter check is the one that is load-bearing on its own rather than redundant: everywhere else a parameter also fails the alias lookup, but a parameter SHADOWING a module-level alias of the same name (`type Scope = …` beside `interface P<Scope extends string>`) would otherwise resolve to a completely different type. (2) **The companion guard is the residue pin** — `UNRESOLVED_ALLOWED` lists every `file.ts: attr` whose declared type NAMES something unfollowable, with a reason, so a NEW aliased declaration the resolver cannot read fails the build instead of silently re-opening the hole at site 67. Today it is two entries: `menu-machine`'s `data-scope` (a genuine type parameter) and `table`'s `data-row-index` (`typeof HEADER_ROW_INDEX`). A plain `string`/`number`/`boolean` is deliberately NOT residue — it is honestly open, and listing 200 of them would drown the pin. Its vacuity check asserts every allowance is still MATCHED, because a reporter that returned `[]` for everything would otherwise pass. (3) **Resolution introduced exactly ONE false-positive shape and it is per-file allowlisted, not generalised away**: a DESCENDANT selector names another machine's state — `field.ts`'s `has-data-[state=checked]` is upstream's checkbox-row highlight, and `checkbox`/`radio-group`/`switch` all publish it, while the value arm resolves `data-state` against the field's own `FormStatus`. Do NOT "fix" that by skipping `has-`/`group-`/`peer-` candidates: `field.ts`'s own `group-data-[disabled=true]/field` bug is exactly that shape, and a faithful mutation confirms the arm judges those pairs today. (4) **The gain is 46 recipe pairs moving from unchecked to checked** — every overlay's `data-state=open|closed`, every drawer/sheet `data-side`, `steps`' four `data-status` values, `rating-group`'s `data-fill`, `image-cropper`'s handles, `slider`/`tabs`/`toolbar`/`resizable` orientation — 45 of them already live, plus the one false positive above.
- **The BASELINE STYLESHEET had a name arm and no value arm, and that asymmetry cost the same thing on the other styling path.** Adding `themeAttrValuesByScope` found TWO live dead rules the day it was written: `[data-scope='menu'][data-part='item'][data-state='highlighted']` and the identical `context-menu` rule, against a `menu-machine` that publishes a BARE `data-highlighted` — while `select` and `combobox`, four rules away in the same file, already used the bare spelling. **The keyboard-highlighted item in a baseline-styled dropdown or context menu had no highlight at all**; only the `:hover` rule beside it worked, so a mouse user saw the component behaving and a keyboard user saw nothing. This is the residue of the machine-side fix for that same bug (the "SIXTH" one two bullets up, where `menu-machine` was changed to publish bare) in the surface that fix did not reach — which is the standing argument for making a check symmetric across BOTH styling paths at the time it is written, rather than adding the second arm a release later. It is keyed per SCOPE (`THEME_VALUE_ALLOWED`), not by bare attribute name — the NAME arm beside it reads `ALLOWED['*: ' + attr]`, a global bare-name key of exactly the shape the registry arm's per-file keying exists to avoid, and per-FILE keying is meaningless in a one-file corpus so per-scope is the analogue. Splitting a component to "expose the pieces" trades a real footgun for flexibility nobody asked for; the class guard and the attribute guard are both blind to it, and only a render shows it.
- **Two systematic translations, and only two.** `focus:` → `data-[highlighted]:` on every menu-like surface (dropdown, context menu, menubar, select, combobox, command): Radix moves real DOM focus onto the highlighted item, LLui keeps focus on the CONTENT and tracks the highlight in state (`aria-activedescendant`), so a ported `focus:` would never match. And `data-slot=` → `data-part=`. A leftover `data-slot` is dead CSS that can never match — `navigation-menu` shipped with one.
- **Icons come from the Iconify HTTP API by `prefix:name`, and the response is UNTRUSTED MARKUP.** `registry/llui/ui/icons.ts` no longer inlines geometry: `icon('lucide:star')` names any Iconify glyph and the body is fetched at mount, batched to ONE request per prefix per tick. (1) The result is a real `<svg>` element — never an `<img>` and never the `iconify-icon` web component, both of which would break every `[&_svg:not([class*='size-'])]:size-4` hook in the recipes silently, exactly the way an un-rewritten `data-slot` does. (2) The body is NEVER assigned to `innerHTML`; every node is REBUILT from an element and attribute allowlist that fails closed, so a `<script>`, an `onload`, an `href` or a `style` in the response is dropped rather than passed through — `registry/test/icons.test.ts` pins each. - **An exit animation on a node that is never unmounted RESTS AT THE START VALUE, and the class guard cannot see it.** Every shadcn overlay pairs `data-[state=…]:animate-out` with Radix UNMOUNTING the node once the animation ends — `hidden`/`closed` is a state it passes THROUGH, never one it rests in. A part that stays mounted (because nothing can unmount a node after its own exit animation) inverts that: the default `animation-fill-mode: none` releases the animation's hold the instant it finishes, so the element snaps back to the cascade — measured on `navigation-menu`'s indicator, which faded out and returned to `opacity: 1`, fully visible with `data-state="hidden"`. Stacking a static `opacity-0` under the animation fixes the resting state and then plays the exit ONCE AT MOUNT, flashing the element in on every page load, because the `exit` keyframes start from `--tw-enter-opacity` (1). Both guards are blind to this: the class compiles and the attribute is published, so `tailwind-classes.test.ts` and `registry-attrs.test.ts` are green on an element that is visibly wrong. It was found by rendering the page — and NOT by the first computed-style read of it, which reported `opacity: 1` for the closed state in a hidden tab where the transition was frozen mid-flight (the hidden-tab trap above, in its other direction: strip the `transition-*` class and re-read to get the cascade value).

Consequence: `theme.css` REQUIRES Tailwind v4 (as it already did), and `theme-dark.css` activates on `.dark`, `[data-theme='dark']` AND `prefers-color-scheme`.

On a dark OS the library's own block therefore outranked the consumer's for EVERY preference and regardless of source order, INCLUDING an explicit `'dark'` where the consumer's selector matches perfectly well and still loses. It is now `:root:where(:not(…)):where(:not(…))` — (0,1,0), so source order decides. **Do not wrap `:root` itself**: `:where(:root)` is (0,0,0), loses to `tokens.css`'s own `:root`, and breaks dark mode outright while every override assertion stays green. The selector STAYS in the stylesheet because `next-themes`/shadcn tooling set the class themselves and a generator-verbatim block then wins in every cell; dropping it would take dark mode away from those consumers. The residue is structural and no CSS change can remove it: under `'system'` on a dark OS there is no attribute and no class, so NOTHING a consumer can select on is present — the twin block under the media guard stays the documented answer for that one cell. **Lowering the guard has a consequence to state to consumers**: a `:root`-only override now reaches dark mode in every cell, where before it leaked on a light OS and was overruled on a dark one. `components-demo` overrode `--destructive` in `:root` and relied on being overruled; after the fix the light red sat under the library's dark near-black foreground at **3.750:1**, below AA, until the dark twin listed it. `packages/components/test/styles/token-cascade.test.ts` pins the specificity RELATIONSHIP (a parser, self-checked against hand-computed values — a string assertion on the selector cannot see any of this) and `token-cascade.browser.test.ts` measures the real six-cell cascade in Chromium.
- **Derived interaction tokens are `color-mix()` toward `--foreground`, never a second palette.** `--primary-hover`, `--accent-strong`, `--border-hover`, `--primary-soft-foreground` and `--destructive-hover` are LLui additions the baseline sheet needs and shadcn expresses per-component. Mixing toward `--foreground` makes the SAME expression darken in light mode and lighten in dark, so they need no `.dark` override and are defined once, OUTSIDE the blocks a theme generator overwrites. Do not restate them in a dark block; a generator that emits them is emitting noise.

- **The state-driven styling idiom is `data-*`, not a computed class.** Every `connect()` part bag already emits `data-state` / `data-disabled` / `data-orientation` / `data-side` (624 `data-part`, 124 `data-state` across the package) and **no `connect()` emits a `class`** — which is what makes a skin layer purely additive and unable to regress focus, dismissal or ARIA. **Charts (`@llui/components/chart`, `utils/scale.ts` / `utils/path.ts` / `utils/projection.ts`):**

- **A chart PROJECTS; it does not branch on its coordinate system.** `scale.ts` maps data into normalized space (`u ∈ [0,1]` along the independent axis, `v ∈ [0,1]` for magnitude) and knows no pixels; `projection.ts` maps normalized space onto the screen and is the ONLY place cartesian and polar differ. `Projection` is one interface (`point`/`line`/`area`/`band`/`gridline`/`tick`/`valueTick`/`locate`) with two implementations, and `chart.ts` never reads `.kind`. That is what makes `coord` one state field: switching it re-projects every mark, gridline, tick, hit test and tooltip anchor from the same series and data — a line becomes a radar outline, a bar a wedge, a rule a ring. Putting the two-way decision inside each mark instead spreads it across line, area, bar, gridline, tick and hit-test code where the six copies drift; see `docs/adr/0003-charts-project-rather-than-branch.md`.
- **`monotone` and `step` are functions of the INDEPENDENT axis, and `horizontal` moves it from x to y.** `path.ts`'s `CurveAxis` names which coordinate plays `t`, and `cartesianProjection` passes `horizontal ? 'y' : 'x'` to `curvePath`/`areaPath`. Running them along x regardless offsets every control point along the wrong axis: measured, a rising four-point series emitted `M150,0C190,25 230,75 270,75`, where the second control already sits at the segment's END instead of two thirds along it, and the next segment then walked backwards. Note what does NOT catch it — the ENDPOINTS are correct in both orientations, so asserting the path advances monotonically passes on the broken output; the property that breaks is where the CONTROLS sit, and the test asserts the exact ⅓/⅔ positions. The `area` half needs the axis threaded too and is easy to miss: a test counting subpaths and checking for a trailing `Z` is green either way, so `test/utils/chart-geometry.test.ts` anchors the area's opening run against `projection.line(...)` instead.
- **`polarProjection` declines `monotone` and `step` and draws `linear`.** Not a gap — monotone cubic's guarantee is that it never overshoots between two samples, and it is defined on `y = f(x)` with increasing `x`. A closed angular loop has no such ordering, so honouring the request draws values nobody measured. `Projection.curves` states the supported set so the limit is introspectable; do not "fix" this by mapping the request onto a cardinal spline.
- **Every path coordinate goes through `path.ts:fmt`.** The reconciler commits on output-equality, so a path recomputed from unchanged data must be BYTE-IDENTICAL or every mark re-commits on every unrelated state change — `0.1 + 0.2` reaches a path as `0.30000000000000004` from one route and `0.3` from another. `fmt` also maps a non-finite coordinate to `0`: one `NaN` voids the WHOLE path element, taking every later command with it.
- **A full circle is TWO arcs, and a full-turn sector is a ring.** A single 360° arc is degenerate — its endpoints coincide and SVG draws nothing, which is the classic vanishing polar gridline.
- **A pie is not a mark type — it is `domain: 'share'`, which moves the magnitude from `v` to `u`.** `ChartState.domain` picks how the INDEPENDENT axis is allocated: `value` gives every category an equal slot (`bandExtent`) and reads magnitude off `v`; `share` allocates each a slot proportional to its value (`shareExtents`) and lets `v` span the whole depth. Polar renders that as a pie/donut, cartesian as one full-width 100%-share bar — the SAME state, so `coord` still re-projects one dataset. A `'pie'` mark was rejected for exactly that reason: it is meaningless under a cartesian projection, so it would have to force polar or draw nothing, which is the invariant ADR 0003 exists to protect. Radial bars needed no new field — `polarProjection` now honours the existing `horizontal` flag, reading "the independent axis moves off its default screen axis" as "off the angle, onto the radius". Three declines go with it, each the same call as polar refusing `monotone`: a share axis has NO padding (the slot is the datum, so a gap makes every slice misstate its share and a full turn stop being 100%); a NEGATIVE value takes no arc (a share of a negative is undefined, and both silent readings either invent data or push the total past 1); and `line`/`area` are DECLINED under a share domain, since an axis whose spacing already encodes the magnitude would put every point at a position meaning something else. Two traps a test will not catch. The pointer hit test must be CONTAINMENT (`nearestShare`), not the nearest-centre `nearestBand` uses — slices tile with no gaps, so a thin wedge beside a wide one loses its own interior to nearest-centre. And the last slice must close at exactly 1 rather than at the accumulated sum: for most inputs the cumulative float sum lands on 1 by luck, so a test with round numbers passes either way — `[310, 779, 45]` is one that genuinely reaches 0.9999999999999999, which on a full turn is a hairline seam of background at 12 o'clock. **`horizontal` under a share domain is a DIFFERENT chart, not a rotation of the same one**: with the slice extents on the independent axis, leaving it off runs them left-to-right across one bar, while turning it on stacks stripes vertically with their HEIGHTS proportional. Both are honest; only the first is what a pie unrolls into, and the geometry probes pass on both — it was caught by looking at the rendered page.
- **Unstacked bar series are laid out SIDE BY SIDE inside each band**, and the slot stays reserved when the legend isolates a series so nothing moves. Overlaying them hides the shorter series AND reads as a stacked chart, so the picture does not merely omit data — it misstates it.
- **Geometry is derived, never stored.** `geometry(state)` is memoized on state identity with `deriveOnce` (as `date-picker` memoizes its day grid). `width`/`height` are user units feeding the `viewBox`, so the whole thing is a pure function of state: no layout read, no `ResizeObserver`, SSR-identical. The bounds `min`/`max` follow #177's UNBOUNDED-CAPABLE idiom — OMIT the key, never `undefined`/`null`/`±Infinity`.
- **Accessibility is a real `<table>`, not the WAI-ARIA graphics roles.** The `<svg>` is `role="img"` named through its own `<title>`/`<desc>` (hence `svgTitle`/`svgDesc` in `@llui/dom`); the numbers live in a visually-hidden `<table>`. `aria-activedescendant` is invalid on `role="img"`, so the keyboard cursor is announced through the tooltip's `role="status"` live region instead. And every drawn layer NAMES A PART (`layer`/`grid`/`axis-label`/`dot`/`mark`) — the first cut did not, so the container's `[data-part='grid']` rules were dead CSS in exactly the way the registry guard exists to catch.

**Forms (`@llui/components/patterns/form-field`):**

- **Validation is a REDUCER concern and Standard Schema is the seam** (`docs/adr/0002-validation-is-a-reducer-concern.md`). `patterns/form-field` is LLui's react-hook-form: a `validate`/`validateAsync` message runs any Standard Schema, issue PATHS map to flat field names, and `connect` derives every id and every reactive ARIA attribute. The registry's `form` item is shadcn's five recipes re-bound to that part bag — you do not strip RHF, you substitute it. There is deliberately no `FormControl`: upstream's is a Slot forwarding `id`/`aria-describedby`/`aria-invalid` onto its child, and `{...field.control}` already carries exactly those.
- **A part bag must be SPREADABLE.** `formField`'s `errorText` used to carry `message` and `issues` alongside its attributes, making it the one bag in the package a consumer could not spread — spreading it bound a Signal-of-string and a Signal-of-array as DOM attributes, so every call site destructured them back out first. It is now attributes only, plus its own reactive `hidden` (the `date-input` convention); the content moved to a sibling `error: { message, issues, visible }`. Keep the live region MOUNTED and hidden rather than wrapping it in `show(...)`, which unmounts and rebuilds it on every transition.

**Meter reference ranges (`@llui/components/meter`, #235):**

- **`bands` is the ONE quality model, and the native `<meter>` spelling compiles into it.** `MeterState` carries `bands: MeterBand[]`; `low`/`high`/`optimum` are INIT OPTIONS that `init` turns into three positional segments (`low`/`middle`/`high`) whose TONES follow the HTML gauge rule — the segment holding `optimum` is `optimal`, the one next to it `suboptimal`, the far one `critical`. Nothing reads `state.low` any more, and `MeterThreshold`/`thresholdState` are gone: the vocabulary is `MeterTone = optimal | suboptimal | critical | neutral` and the derivations are `bandAt` / `toneAt`. `neutral` is the ABSENCE of an opinion, deliberately not a synonym for `optimal` — `init()` with no thresholds used to answer `'optimal'`, i.e. a plain disk gauge claiming the reading was good. The one boundary that MOVED: `value === high` now reads as the UPPER segment (it was the middle one), because edges are uniformly half-open.
- **Edges are `[from, to)`, first match in author order, with the top of the track inclusive.** Half-open is what lets adjacent bands tile with no ambiguity, so a lab range whose upper edge is inclusive is written as the NEXT band's `from`. The one exception is `value === to` where `to >= max` — without it a full-scale reading falls in no band at all, which is the one place the uniform rule gives a useless answer, and it is scoped to the TRACK's top rather than to "the last band". A value below every band, above every band, or in a GAP is in NO band, and `data-band` plus `aria-valuetext`'s name are then ABSENT — never the nearest band, because inventing membership misstates a lab result. Nothing is sorted, merged or repaired: overlaps resolve by author order (reversing the list reverses the answer), an INVERTED band matches nothing and lays out at zero width, and duplicate ids both survive with the first winning.
- **Band edges are #177's unbounded-capable idiom one level down** — an unusable edge is OMITTED, so the band reads as open on that side and the JSON round trip stays an identity; normalized at `init` AND at `setBands`. A band with no string `id` is DROPPED: the id is what `parts.band(id)` addresses and what an `each` row keys on.
- **`aria-valuetext` names the band, and only from an explicit `label`.** That is the accessibility win the model exists for — a bare `aria-valuenow` of 47 says nothing about whether the reading is in range. An author-written band defaults its `label` to its `id`; `label: ''` suppresses. The synthesized native segments carry NO label, so `low`/`middle`/`high` are never read out and `aria-valuetext` is byte-unchanged for every pre-band consumer.
- **Geometry is derived, never stored, and the `deriveOnce` cell lives in the `connect()` closure** — not at module scope the way `chart`'s does, because a page of static meters is the motivating case and one shared cell would let two mounted meters evict each other on every update. `parts.bandProps` takes the ROW HANDLE `each` passes and returns SIGNALS, so the bag spreads as is; `chart`'s `markProps` takes a snapshot instead and every call site has to `peek()` the row and re-bind the fields that move.
- **A static meter needs no runtime**: `connect(constant(state), noSend, opts)` resolves the whole part bag, banded track included (`test/stateless-connect.test.ts`). There is deliberately no per-component `geometry()` entry point — #235 asked for one like `chart`'s, and the DECISION is that `constant()` answers it generally rather than adding a 72nd per-component export (#231 is the general ladder). The plain-values half is `peek()`: `constant` is the one handle whose `peek()` reads the captured value rather than a live component state, so `parts.bands.peek()` hands back `MeterBandGeometry[]` outside any view. Write it as two statements — an INLINE `constant(…).peek()` is what `peek-in-slot` reports (#245), while a `const` receiver is silent.
- **The banded `MeterMarker` is clipped by ONE pixel at 0% and 100%, and that is a measured decision.** `-translate-x-1/2` centres a 2px rule on the value, so at the extremes one of its two columns leaves the track and `overflow-hidden` clips it — measured in headless Chromium (1 of 2 painted columns at each end, 2 of 2 in the interior), not reasoned about. The marker stays visible; `overflow-hidden` is what clips the band washes to the rounded track; and the structural alternative splits one recipe into an outer positioned box plus an inner clipping one, which is the `command`-filter-field footgun above. Dropping the translate is strictly worse — the box then sits fully outside the track at 100% and is clipped away entirely.

**Packaging landmines:**

- **`@llui/dom` (and any package owning the render context) MUST be a `peerDependency` (`workspace:^`) + `devDependency`, NEVER a `dependency`.** As a hard dep, `pnpm publish` pins the resolved version; a consumer on a different `@llui/dom` gets two physical installs, each with its own module-scoped `currentContext`, and every `provide()`/primitive from the consumer's view throws `provide() can only be called inside a component's view()` even though it is. This caused a production outage; the fix is the peer-dep pattern, not `pnpm.overrides`.
- **`typescript` is a `peerDependency` (`>=5.0.0 <7.0.0`) + `devDependency` of `@llui/compiler`, `@llui/compiler-ssr` and `@llui/vite-plugin`, NEVER a `dependency`** (issue #64). Same failure shape as the `@llui/dom` rule above: a hard dep pins the published version, so a consumer with its own TypeScript gets a second physical install and the compiler analyses their sources with a DIFFERENT `ts` than they compile with — two `SyntaxKind` tables, one silently wrong dep mask. The floor is 5.0 because the newest API in use is `ts.isSatisfiesExpression` (TS 4.9); the ceiling is a major because TypeScript does not follow semver. All three must carry the SAME range (they install together), and it must stay REQUIRED — `import ts from 'typescript'` runs at module load, so an optional peer trades an install warning for a MODULE_NOT_FOUND while Vite loads the config. `packages/compiler/test/typescript-peer-dependency.test.ts` fails the build if any of this drifts.
- **`tsc` does not clean `dist/`.** Deleted-source artifacts linger and ship unless cleaned before pack (`scripts/publish.sh` now `rm -rf dist` before building). Cross-package `@llui/*` refs are `workspace:*` (pnpm rewrites at pack). `__llui_deps.json` is no longer emitted into tarballs (see Active proposals).
- **The compiler↔runtime metadata ABI must move in lockstep, and its names must be FINAL at emit time.** `@llui/compiler` WRITES the six agent/devtools property keys (`$ms`/`$es`/`$ss`/`$ma`/`$sh`/`$cm`) onto every compiled `component({...})` literal; `@llui/dom` (debug registry) and `@llui/agent` (LAP handshake) READ them. Writer and readers land in DIFFERENT bundle chunks under any vendor split — stock `manualChunks: { vendor: ['@llui/dom'] }` is enough — so nothing may rewrite the name after emission. A post-bundle rename pass scoped to chunks containing compiled modules did exactly that and left the runtime chunk reading the old name: every schema silently `undefined` in production `agent: true` builds, with no error anywhere (issue #45). The table is declared TWICE — `packages/compiler/src/emit-names.ts` and `packages/dom/src/signals/compiler-keys.ts` — because `@llui/dom` must stay dependency-free while the compiler pulls in `typescript`; `packages/dom/test/signals/compiler-metadata-abi.test.ts` fails the build if the two diverge. Change a key in BOTH, and treat any value change as breaking: a consumer on a new compiler with an old runtime reproduces #45 and the runtime CANNOT detect it (an absent key is indistinguishable from a build that emitted no metadata). `@llui/vite-plugin` therefore carries a `@llui/dom` peer range so the package manager catches the skew; `@llui/compiler` cannot declare one — a dev-dep edge back to `@llui/dom` would make the workspace graph cyclic, since `@llui/dom` dev-depends on the compiler for its tests.
- **Do NOT resurrect deleted code.** Off-limits (git history has it if ever needed): the v2c compiler-module registry (`module.ts`/`ModuleRegistry`), the introspection/devtools factories, the `@llui/compiler-{introspection,devtools}` packages, the cross-file walker (`walkProgram`/`cross-file-walker.ts`), the second dep analyzer (`collect-deps.ts` / `accessor-resolver.ts` / `track-utils.ts`, #92), `@llui/eslint-plugin`, and the two-word bitmask / `elSplit` / `__dirty` reactivity model. Docs live in `site/content/` — `docs/designs/` was removed; do not reference it.

**Protocol:** LAP is at **v2** (breaking): frames are zod-validated, `expiresAt` is milliseconds on the wire, and version skew terminates the pairing. Bump the app's shipped `@llui/agent` client and its server together.

**Maintainer workflow skills** (in `.claude/skills/`) encode the exact, easy-to-get-wrong procedures for adding a structural primitive, a compiler lint rule, a headless component, or a package. Consult the matching one before that kind of change. (`llui-app-dev` is the _consumer_-facing skill for app code, not internals.)

## Active proposals

Major architectural changes in flight. Read before touching the relevant packages:

- **v2 Compiler Architecture** (`docs/proposals/v2-compiler/`) — partially realized by the signals migration: `@llui/compiler` is a standalone package (extracted from `@llui/vite-plugin`), and cross-file Msg/State/Effect analysis is live (`cross-file-resolver.ts`, wired into the vite-plugin). The **live** transform path is `transformSignalComponentSource` (a single string-edit signal transform); it emits agent/devtools metadata **inline** (its own `sharedMetaProps`), NOT through a registry.

  **Superseded/removed (do not resurrect without a reason):**
  - The v2c compiler-module registry (`module.ts` `CompilerModule`/`ModuleRegistry`), the introspection/devtools factories (`introspection-factory.ts`), and the `@llui/compiler-{introspection,devtools}` packages were **deleted** — they were only ever driven by the `transformLlui` orchestrator, which the signals migration replaced with `transformSignalComponentSource` (inline metadata emission). The extraction functions live in `@llui/compiler` (`msg-schema.ts`, `state-schema.ts`, `msg-annotations.ts`, `schema-hash.ts`, `binding-descriptors.ts`) and are called inline by the transform.
  - The legacy cross-file dep-analysis **walker** (`walkProgram`/`crossFileAccessorPaths` in `cross-file-walker.ts`) was **deleted** — it was the v2b transform path, removed from the live route when the signal transform became the only compilation route. The live cross-file work uses `cross-file-resolver.ts` (Msg/State/Effect schema resolution) + the signal transform's own dep analyzer (`analyze-deps.ts`/`extract-deps.ts`).

  **Dormant-but-kept:** The cross-package library ABI (`__llui_deps.json`, schema v2). The producer tooling (`build-manifest.ts`, `scripts/emit-deps.mjs`) is kept in-repo but **no longer emitted into published tarballs** — `scripts/publish.sh` stopped shipping it (it was ~191 KB of dead weight across the stack for a consumer that doesn't exist). The **consumer** narrowing is **not wired into the live transform** (it needs a `ts.Program`/checker the string-edit transform lacks; phase 3 was evidence-closed 2026-06-10 — zero qualifying call sites in real consumers). `manifest-resolve.ts` is kept as dormant forward-compat. The producer's per-parameter read analysis is `signals/analyze-deps.ts`, the one live analyzer — it used to be `collect-deps.ts` / `accessor-resolver.ts` / `track-utils.ts`, which #92 **deleted** (see the compiler invariants above); nothing in the repo imports them and they must not come back. If a checker-backed consumer ever lands, re-enable the emit in `publish.sh` (producer + consumer + E2E test together). See the status note in `docs/publishing-a-precompiled-library.md`.

  Note there is no runtime `track()` _primitive_ in `@llui/dom` — only the compiler annotation. The proposal predates the signal runtime, so its references to the legacy runtime (`update-loop.ts`), the deleted `@llui/eslint-plugin`, and the two-word bitmask are historical — read it for the module-system direction, not the runtime model.
